# 1. 项目总览与最终定位

## 1.1 正式名称

**AI Game Design Agent Workbench｜AI 游戏策划与研发 Agent 工作台**。

名称保持多品类中性表达，不改成“AI 小游戏策划工具”或“AI RPG 剧情生成器”。小游戏及休闲游戏是当前优先研究和优先验证的市场方向，不是产品唯一服务的对象。产品长期采用“通用能力底座 + 游戏类型专属模块”的架构，支持不同游戏类型通过独立 Schema、规则包、知识配置和评测集接入工作台。

## 1.2 一句话定位

面向游戏策划、独立开发者和小型研发团队，提供一套可扩展的 AI 辅助设计与生产工作台，将自然语言设计需求转化为可编辑、可检查、可诊断、可审核、可交付的结构化游戏设计产物；当前重点研究小游戏及休闲游戏研发场景，同时保留 RPG、MOBA、FPS、模拟经营等品类的扩展能力。

## 1.3 产品愿景与当前任务的区别

产品愿景是帮助专业团队和个人创作者从游戏创意走向可玩的作品。长期来看，工作台不仅能够辅助设计任务、玩法、关卡和数值，还可以通过接口、模板和工具调用，与游戏引擎、AI 编程工具、素材生产工具和测试工具协作，帮助个人创作者制作自己的原创小游戏，并探索商业化。

当前项目阶段不负责完整游戏引擎、全自动商业游戏生成、全部美术音频资产生产、实时 NPC 运行时系统、游戏发行运营平台或广告投放系统。第一阶段的任务是做出一个真正可用的游戏策划与设计工作台 MVP，验证至少一个具体设计场景的完整闭环。个人制游和盈利是长期应用验证，不是当前阶段的验收指标。

## 1.5 当前项目成功的定义

第一阶段完成时，项目应达到以下状态：能够明确说明目标用户与首期设计场景；有真实访谈证据支撑核心问题；有产品信息架构和交互原型；有一条可运行的 Agent 工作流；能够生成首期品类的结构化设计产物；能够执行品类规则检查并定位问题；用户可以修改、审核、留痕和导出；有固定测试集、明确的 GT 和可重复的评测记录。

“支持多品类”在第一阶段仅表示架构有清楚的扩展边界，不表示所有品类已实现。项目是否有效，以首期场景的真实价值与可复现表现为准，不以功能数量或页面数量作为成功标准。

# 2. 项目目标、价值与边界

## 2.1 三个相互关联的目标

**职业发展目标。** 将项目作为 AI 游戏产品经理、游戏研发工具产品经理、游戏策划 Agent 产品经理的作品集案例，证明能够理解专业用户工作流、抽象复杂业务、设计 Agent 编排、建设知识与规则资产、定义评测标准并完成产品验证。备选求职出口是通用 B 端 AI 产品、AI Agent 产品和 AI SaaS 产品。

**产品建设目标。** 建立一个多品类游戏设计工作台，具备项目资料管理、需求解析、设计内容生成、规则检查、问题诊断、人工审核、版本管理和结构化导出能力。通用能力复用，品类知识和规则按模块隔离。

**个人应用目标。** 长期以自己作为第一位真实用户，使用工作台辅助原创小游戏设计和制作，积累玩法验证、关卡迭代、用户测试和发行尝试经验。该目标能够反向提供工作台改进需求，但不得挤占当前 MVP 的核心范围。

## 2.2 核心产品价值假设

当前待验证的价值假设包括：减少策划从创意/Brief 到初版结构化设计产物的整理时间；减少关卡、任务、玩法和配置中的结构性错误；更早发现设计约束冲突和逻辑不可执行问题；减少跨文档、表格和聊天工具之间的重复搬运；让设计产物更容易被程序、QA 或其他协作人员理解和接收。

S2 第一轮进一步提示：跨设计对象的引用关系、变更影响面和一致性核对，可能比单纯“生成更快”更值得优先验证。该问题目前来自三份游戏行业样本的探索性归纳，并非行业普遍结论。上述价值必须通过目标用户访谈、真实或脱敏工作样例、原型测试和基线对照实验验证。不得只用模型生成速度或主观演示效果证明价值。

## 2.3 与既有 AI SaaS 客户需求分析工作台的区别

本项目不能只是把之前的客户需求分析工作台替换行业词汇、换一套 Prompt 和知识库。两者的核心任务与最终交付物不同。

| 比较项 | AI 客户需求分析工作台 | AI 游戏策划与研发工作台 |
|---|---|---|
| 核心用户 | 产品、售前、业务分析人员 | 游戏策划、关卡/系统/数值设计人员、独立开发者、小型研发团队 |
| 输入 | 会议转写、客户需求材料、聊天记录 | 游戏创意、玩法需求、关卡目标、项目资料、设计约束、参数和配置 |
| AI 主要任务 | 提取、分析、分类、优先级评估、证据关联 | 设计规划、内容生成、结构化建模、规则检查、诊断和迭代 |
| 核心输出 | 需求分析报告、优先级与追问清单 | 可编辑的游戏设计资产、关卡/玩法配置、规则检查报告和交付数据 |
| 质量判断 | 事实准确、需求覆盖、证据引用、优先级一致性 | 规则是否成立、关卡是否可完成、参数是否越界、设计约束是否满足、内容是否可用 |
| 产品价值 | 辅助业务决策：应该做什么 | 辅助生产：如何把设计做出来、检查好并交付 |

本项目必须拥有真正的游戏设计对象和专业编辑体验，例如关卡网格、目标配置、资源循环、状态条件、地图路径或任务结构。最终产物不能只有一份分析报告，而应当可以被用户继续编辑、验证和交接。

## 2.4 产品非目标

第一阶段不开发完整游戏引擎，不替代 Unity、Unreal、Godot、articy:draft、Ink、Twine 等现有工具；不承诺完整支持所有游戏品类；不开发实时语音 NPC 或复杂角色运行时系统；不自动生成并发布一款成熟商业游戏；不做大型美术、3D、动画、音频生产平台；不做复杂多人实时协作、企业级权限系统和多租户管理；不首发开放式自由工作流市场；不把“能够调用大模型”本身视为核心产品价值。

# 3. 用户、角色与核心工作任务

## 3.1 目标用户范围

| 用户角色 | 典型工作 | 关注结果 | 当前优先级 |
|---|---|---|---|
| 小游戏/休闲游戏策划 | 玩法、关卡、目标、障碍、节奏和难度设计 | 关卡可玩、难度合理、产物可配置 | 当前优先研究 |
| 系统/数值策划 | 资源、成长、消耗、奖励、数值区间和经济循环 | 参数可控、循环成立、数值无明显冲突 | 当前优先研究 |
| 玩法策划/游戏设计师 | 核心循环、规则、交互、玩家目标和体验 | 机制清楚、规则完整、体验目标一致 | 当前优先研究 |
| 独立开发者/小团队 | 一人或少量人员承担设计与实现 | 降低重复工作、缩短原型试错时间 | 重要研究对象 |
| 主策划/制作人 | 评审设计方向、控制质量与排期 | 风险可见、版本可追溯、交付完整 | 次级用户/审核者 |
| 程序/技术策划/QA | 接收设计数据、实现规则、验证边界 | 数据结构清楚、错误可定位、验收可重复 | 下游协作角色 |
| RPG/MOBA/FPS 等其他品类策划 | 各自品类的任务、技能、地图和战斗设计 | 品类规则正确、工具贴合流程 | 后续适配研究 |

## 3.2 首期用户假设

首期优先研究小游戏和休闲游戏研发团队中的关卡策划、系统/数值策划、玩法策划，以及独立开发者和小型团队。具体首期角色仍需 S2 访谈确认，不预先认定所有这些用户都存在相同痛点。

MVP 初始采用单一项目、单人主要操作的工作流。主策划可以作为审核者，程序和 QA 作为下游接收者。暂不实现复杂组织权限和实时多人协作。

## 3.3 核心 JTBD

当策划需要设计一段玩法、一组关卡或一套参数配置时，他希望把自然语言需求、现有项目资料和明确约束转化为结构化的设计产物，并能快速查看规则问题、理解问题原因、修改设计并交付给下游，从而减少重复整理、配置遗漏和反复返工。

该 JTBD 是工作台的总体任务描述。首期 MVP 必须进一步收敛到一个具体场景，例如“根据关卡 Brief 生成首版关卡配置并检查通关条件”，但该例子仅为候选，不代表已经决定首期做关卡编辑器。

## 3.4 需要验证的痛点假设

- 设计需求、规则、历史版本、参考素材或配置表分散在多个工具中，导致重复整理。
- 自然语言设计意图转化为结构化数据时容易遗漏字段或约束。
- 设计产物有明确规则和参数约束，但现有检查依赖人工逐项核对或运行试玩。
- AI 可以生成内容，但生成结果未必满足玩法约束、数值边界或项目已有设定。
- 修改一个设计条件后，关联对象和下游配置可能需要同步修改，容易发生版本不一致。
- 设计问题缺少可定位的原因说明，导致策划只能凭经验反复尝试。

以上均需按证据强度管理。S2 第一轮目前能够支持的较强线索是：设定/对象冲突确实存在，以及不同设计对象之间存在需要核对的关系；但高频程度、单次工时、显著返工成本和 Brief 解析成本尚未验证。不能在作品集或产品介绍中将其写成行业普遍痛点。

## 3.5 S2 第一轮对核心问题的修正

S2 第一轮的三个游戏行业样本分别涉及叙事关卡、放置类活动和大型项目剧情。它们的设计对象不同，但都出现了关系核对或联动问题：角色与剧情承接、活动机制与已有机制的联动、角色经历/人物关系/时间线核对。当前可形成的产品问题假设是：**当一个设计对象发生变更时，策划需要判断哪些关联对象、规则、任务或下游产物会受到影响。**

这意味着产品的核心价值假设需要从“提供品类模块化能力”进一步聚焦到“读取结构化游戏设计数据，分析引用关系与变更影响面”。品类模块化仍然是技术架构和扩展机制；变更影响分析则是当前优先验证的跨品类问题与产品差异化候选。二者不是替代关系。

本结论只代表第一轮探索性研究：游戏行业相关样本为 3 份，其中一份来自公开论坛回复，样本角色、团队类型和信息完整度并不相同。不能写成“游戏策划普遍存在此痛点”，也不能据此推断问题发生频率或返工工时。

# 4. 产品主链路：五段职责与 Agent 编排

## 4.1 五段主链路

三个能力不是三个候选产品方向，而是同一条生产链上的职责。工作流负责串联，生成负责产出，检查负责发现问题，诊断负责让问题可理解和可处理，审核交付负责将结果纳入真实工作流程。

| 环节 | 职责 | 输入 | 输出 | 归属 |
|---|---|---|---|---|
| ① 需求解析 | 将 Brief 中的目标、约束、缺口转为结构化需求 | 设计 Brief、项目资料 | 结构化需求、约束清单、待确认问题 | 通用框架 + 品类字段 |
| ② 设计生成 | 结合项目知识和品类规则生成内容或配置 | 结构化需求、知识库、Schema | 品类专属设计产物 | 通用生成调度 + 品类策略 |
| ③ 质量检查 | 执行结构、参数、状态和语义检查 | 设计产物、Schema、RulePack | 问题清单、检查结果 | 通用执行框架 + 品类规则 |
| ④ 诊断与修复建议 | 定位冲突、分析变更影响、解释原因、给出可复核的候选修改 | 问题清单、引用关系、规则证据、设计上下文 | 违反点、受影响对象/路径、修复建议 | 通用影响分析框架 + 品类规则 |
| ⑤ 人工审核与交付 | 由用户确认、修改、锁定、留痕和导出 | 设计产物、问题与修复建议 | 可交接设计资产、版本与审查记录 | 通用能力 |

## 4.2 Agent 工作流是贯穿链路的编排主干

Agent 工作流不等于在每一步都创建一个自主 Agent。首版采用单一编排器管理任务状态、调用顺序、工具、重试和人工确认；不同步骤调用明确的模型节点或确定性工具。只有当单一编排器的职责边界确实无法管理时，才考虑拆分多个 Agent。

各节点应有清晰的输入输出契约、执行状态、错误类型和可观测日志。模型负责理解、规划和生成；程序负责结构校验、参数边界和可以确定计算的逻辑；用户负责设计方向、审美、玩法体验和高风险判断。

## 4.3 一条典型工作流

1. 用户创建或打开游戏项目，确认当前分发渠道、玩法品类和设计领域。
2. 用户通过表单或自然语言提交设计 Brief。
3. 系统解析目标、约束、禁止项、缺失字段和交付要求。
4. 对关键缺失信息提出澄清问题，不得自行补造决定性业务要求。
5. 检索项目资料、已有规则、术语和相关设计版本，展示引用来源。
6. 结合品类 Schema 与已知对象关系，生成设计计划或结构草案。
7. 用户确认主要结构和约束后，系统生成完整设计产物。
8. 系统运行 Schema 校验、确定性规则检查和适用的语义检查。
9. 对问题给出位置、原因、证据、受影响对象/路径和候选修复建议；对于用户主动修改的对象，额外生成变更影响清单；高风险修改需要用户确认。
10. 用户修改、采纳、忽略或退回，系统记录版本差异。
11. 只有满足导出条件且用户确认后，才生成 JSON、CSV、Markdown 或其他品类格式。

## 4.4 三项核心能力的关系

| 能力 | 产品定位 | 可复用范围 |
|---|---|---|
| Agent 工作流 | 编排主干，组织步骤、工具、状态和人工确认 | 流程框架可跨品类复用；具体步骤由品类模块配置 |
| AI 内容生成 | 生产能力，生成设计内容和配置 | 调度框架可复用；Prompt、Schema、生成策略按品类适配 |
| 质量检查与诊断 | 质量能力，发现错误、解释原因并给出候选修复 | 问题模型和执行框架可复用；规则、语义标准和 GT 按品类隔离 |

# 5. 产品架构：通用底座与品类专属模块

## 5.1 总体架构原则

产品采用“通用能力底座 + 游戏类型专属模块”。通用底座负责跨品类的项目管理、资料管理、Brief 管理、Agent 编排、模型调用、工具契约、运行日志、问题对象、审核、版本和导出机制。品类模块负责该类游戏的设计对象、Schema、生成策略、业务规则、语义检查标准和评测集。

多品类是架构方向，不是首期功能承诺。界面上出现品类选择器，不等于对应品类已经实现。只有当该品类具有可用的 Schema、规则包、设计编辑器或配置界面、测试集和验收结果，才可以称为已支持。

## 5.2 通用底座

| 通用模块 | 主要职责 | 第一阶段要求 |
|---|---|---|
| 项目管理 | 项目、品类、平台/渠道、版本、启用模块 | 单项目或少量项目基础管理 |
| 知识与资料管理 | 文档、设计资料、术语、来源、版本、标签 | 支持结构化文件与基础检索 |
| Brief 管理 | 接收设计意图、必需项、限制、输出要求 | 支持模板表单和自然语言补充 |
| Agent 编排 | 状态流转、调用步骤、重试、人工暂停 | 单一工作流编排器 |
| 模型服务 | 统一 API 适配，隔离供应商差异 | 模型节点不直接绑定厂商 SDK |
| 依赖关系与影响分析 | 记录设计对象之间的引用、前置依赖、触发关系和变更影响范围 | 通用关系/影响分析框架，关系语义由品类适配器定义 |
| 校验执行器 | 调用 Schema 和 RulePack 并聚合结果 | 通用执行接口，规则按品类加载 |
| 问题对象 | 记录错误 ID、目标位置、严重程度、证据、状态 | 跨模块统一问题结构 |
| 审核与版本 | 用户动作、评论、变更原因、前后版本 | 单人审核和版本留痕 |
| 导出 | 结构化数据、文档和配置 | JSON/CSV/Markdown 起步 |

## 5.3 品类专属模块

每个品类模块至少应包含：设计对象模型、Schema 版本、Brief 模板、生成策略、知识组织方式、RulePack、语义审查标准、专业编辑器/配置界面、测试集和导出配置。

可能的品类设计对象示例：

| 品类/方向 | 典型设计对象 | 可能的检查方向 |
|---|---|---|
| 休闲益智 | Level、Board、Tile、Obstacle、Goal、MoveLimit | 目标可完成、对象数量合法、障碍与路径约束、步数约束 |
| 合成类 | Item、MergeChain、Order、Energy、ResourceSource | 合成链完整、资源产出消耗关系、订单可完成、资源约束 |
| 塔防类 | Map、Path、Wave、Enemy、Tower、Placement | 路径可达、波次配置、部署限制、目标可完成 |
| 模拟经营 | Building、Resource、Recipe、Upgrade、Task、Economy | 资源循环、前置依赖、产出消耗、成长节奏 |
| RPG | Quest、Node、Edge、Character、Location、StateVariable | 任务图、状态条件、角色知识边界、剧情一致性 |
| MOBA | Hero、Skill、Effect、Cooldown、Item、MapObjective | 技能字段、状态冲突、规则约束和数值区间 |
| FPS | MapRegion、SpawnPoint、Route、Weapon、ModeObjective | 路径、出生点、模式目标和设计约束 |

以上是候选设计对象示例，不表示这些模块已经实现。最终对象字段应以目标用户真实交付物和项目场景为准。

## 5.4 必须区分“小游戏市场/平台”与“游戏玩法品类”

“小游戏”通常指向产品形态、分发渠道或市场入口；“消除、合成、塔防、模拟经营”等才是更具体的玩法类型或品类方向。它们不能在数据模型中混为一个字段。

因此，项目元数据建议至少区分：

- `distribution_channel`：发布或运行渠道，例如小程序、H5、移动 App、PC 等；实际选项以后续需要为准。
- `genre`：游戏玩法品类，例如益智消除、合成、塔防、模拟经营、RPG 等。
- `design_domain`：当前任务涉及的设计领域，例如关卡、玩法、系统、数值、任务、剧情等。

在项目对象中至少分别保存 `distribution_channel`、`genre`、`design_domain`。例如“微信小程序 + 合成玩法 + 经济数值设计”应分别记录为渠道、玩法品类和设计领域，不应把“小程序”当成一个游戏玩法品类。

小游戏是当前市场优先级，不代表只有一个小游戏玩法 Schema。不同玩法仍需独立定义设计对象和规则。

## 5.5 扩展边界

扩展第二个品类时，优先新增 Schema、RulePack、Brief 模板、生成策略、测试集和必要的专属编辑界面；不应为了接入第二个品类而重写通用编排器、统一问题对象和校验执行框架。如果通用层确实需要调整，必须说明原因和影响，不得把“只改配置文件”当作未经验证的口号。

# 6. 游戏品类与市场优先级策略

## 6.1 当前市场优先级

当前提高小游戏及休闲游戏方向在 JD 归类、岗位研究、用户访谈和首期场景候选中的优先级。20 条 JD 初筛时有 6 条被标记为小游戏相关，但二次按目标岗位职责和求职相关性筛选后，可比目标岗位为小游戏/休闲设计 3 条、RPG/剧情相关 2 条。该结果仅反映当前样本的岗位筛选结果，不代表完整招聘市场或市场份额，也不能直接证明小游戏研发团队存在某个具体工具需求。具体筛选依据见第 10.2 节。

产品并不专门做小游戏。RPG、MOBA、FPS、模拟经营等仍属于长期可能适配的游戏设计领域，但首期开发资源优先投向经过用户调研确认的小游戏场景。

## 6.2 当前优先研究的小游戏候选

| 候选方向 | 可能的设计对象 | 需要验证的问题 |
|---|---|---|
| 休闲益智/消除 | 棋盘、格子、障碍、目标、步数、关卡参数 | 关卡是否存在可计算的可完成性约束；难度如何评估 |
| 合成类 | 合成链、物品等级、订单、能量、资源循环 | 资源链配置是否复杂；目标是否可达；是否需要反复平衡 |
| 塔防类 | 地图路径、敌人波次、塔防单位、资源和目标 | 路径和波次是否能程序化校验；设计者的主要返工在哪 |
| 模拟经营 | 资源、建筑、生产配方、升级、任务 | 资源经济和依赖关系是否具有可检查的约束 |
| 其他小游戏 | 按 JD 和访谈发现 | 不预先假定所有小游戏有相同需求 |

当前不直接决定消除、合成、塔防或模拟经营中的某一个作为首期。S2 访谈要找出具体的高频工作任务，再由 S4 冻结。

## 6.3 RPG 的位置

RPG 不删除，也不继续默认作为首期开发场景。既有 RPG 数据结构、Q001–Q013、原创世界观和状态搜索研究可以保留为一个已有的品类研究成果和技术参考。它可以在未来成为 RPG 模块，也可以作为第二品类验证候选，但不能因为已经投入时间和内容资产就强行让它成为首期。

Q013 仍有价值，但它是 RPG 任务状态约束能力的一部分，不是工作台的独占技术创新。其价值要看是否能够产生策划可理解、可定位、可修复的诊断信息。

## 6.4 长期品类路线

当前顺序建议为：先确定一个小游戏具体设计场景做完整闭环；工作台稳定后，选择另一个不同设计对象的品类做轻量扩展验证；以后是否增加 RPG、MOBA、FPS 或更多模拟经营场景，取决于用户证据、资源和产品价值。

# 7. 首期场景候选与选择框架

## 7.1 首期不是选一个“游戏类型名称”，而是选一项具体设计任务

例如“休闲游戏”仍然过宽；“根据关卡目标和障碍约束生成一组可检查的消除关卡初稿”才更接近可定义的产品任务。又如“合成游戏”仍然过宽；“根据订单目标和资源产出规则生成合成链配置，并检查资源需求是否可达”才更接近可验证场景。

首期场景必须能清楚回答：谁在什么情况下输入什么材料；系统产出什么设计对象；哪些规则可以确定地检查；哪些问题必须交由策划判断；最终输出会被谁使用。

## 7.2 六个选择维度

| 维度 | 评估问题 | 证据来源 |
|---|---|---|
| 结构与规则复杂度 | 设计对象是否足够结构化，有没有可以明确判断的约束和失败状态 | 设计样例、配置表、技术/策划访谈 |
| 岗位与市场关联 | 招聘岗位是否明确涉及该工作任务或相邻能力 | 20 条 JD 矩阵及后续补充 |
| 个人能力与内容匹配 | 是否能够理解领域对象、构造原创数据并独立推动项目 | 个人学习和实践情况；不得用兴趣替代业务证据 |
| 访谈可得性 | 能否联系到实际做过该任务的人，并获得具体案例 | 邀约、有效访谈数量和样本背景 |
| 评测可构造性 | 是否能够构造正例、负例、边界样本和人工 GT | 样本设计试验 |
| 第二场景扩展成本 | 新品类接入是否主要通过 Schema、规则包和适配器完成 | 架构验证和实现记录 |

## 7.3 场景评分纪律

每项可按 1–5 分作初步排序，但分数必须附带证据和可信度。不能把没有数据的维度填成 3 分，也不能把主观兴趣当作市场需求。评分只用于帮助比较，不能取代访谈原话、工作样例和可复核的事实。

## 7.4 首期场景决策卡必须包含的内容

- 目标用户角色和团队类型。
- 具体触发场景与当前操作流程。
- 当前输入资料和最终设计交付物。
- 最耗时或最常返工的两个问题。
- 当前工具链和人工处理方式。
- 可交给 AI 的环节，以及必须由人决策的环节。
- 首期设计对象和最小 Schema。
- 首期确定性规则、语义检查标准和 GT 样本。
- 成功指标、成本约束和不做事项。
- 选择该场景的证据、尚未验证的假设和样本局限。

# 8. 产品形态与交互设计：借鉴 ComfyUI 但不照搬

## 8.1 为什么参考 ComfyUI

ComfyUI 的参考价值在于节点式流程表达：用户能看到一个复杂生产任务由哪些步骤构成，每个节点负责什么、输入输出是什么、执行结果和错误出在哪里；可复用的子流程可以封装为模块，模板可以让用户从已有工作流开始。

本项目可以借鉴节点、连线、节点配置、执行状态、结果预览、模板和模块复用等交互思想。但 ComfyUI 主要面向 AI 内容生成工作流，而游戏策划工作台还要表达专业设计对象、关卡/玩法数据和领域规则，因此不能把整个产品简化成一张无限节点画布。

## 8.2 两种画布必须分开

**工作流画布（Workflow Canvas）**描述 AI 和程序如何执行任务：需求解析、知识检索、内容生成、Schema 校验、规则检查、语义审查、诊断、人工确认和导出。它关注的是执行步骤、依赖关系、输入输出、运行状态和失败恢复。

**游戏设计画布/编辑器（Design Editor）**描述游戏本身：例如消除关卡的棋盘网格、合成链的资源关系、塔防地图和路径、RPG 任务节点图。它关注的是游戏设计对象、变量、参数和玩法结构。

两种画布服务不同的问题，应分别设计、分别验收。工作流画布不能替代关卡编辑器，关卡编辑器也不能代替 Agent 执行可视化。

## 8.3 建议的工作台主界面

| 区域 | 主要内容 | 主要交互 |
|---|---|---|
| 左侧项目栏 | 项目、品类/渠道、资料、设计资产、模板、历史版本 | 切换项目、管理资源和模块 |
| 中央主工作区 | 工作流画布或当前品类设计编辑器 | 查看执行链、查看/编辑设计对象 |
| 右侧属性面板 | 当前节点或设计对象的字段、参数、条件、Prompt/工具配置 | 修改配置、查看字段说明、保存 |
| 底部运行区 | 执行日志、节点输入输出、错误、成本、耗时、校验结果 | 查看运行记录、重试、跳转问题位置 |

在 MVP 中，中央区域应根据用户任务切换为工作流视图或专业设计编辑器，不要求把两种画布同时挤在同一个复杂界面。

## 8.4 工作流画布的分阶段开放

| 版本阶段 | 画布能力 | 用户需要做什么 |
|---|---|---|
| MVP | 固定工作流可视化展示；节点显示状态、输入输出和错误；关键参数可以配置 | 选择模板、填写需求、运行流程、查看结果和问题 |
| 后续版本 | 可配置节点参数、启用/禁用某些步骤、复用子流程模板 | 在受控范围内调整流程 |
| 长期版本 | 在有真实用户需求时开放节点添加、连线和更自由的工作流编排 | 高级用户自定义工作流 |

第一版不开发完整的自由节点编辑器，不做复杂画布拖拽、任意连线、撤销重做、节点市场和多 Agent 协作。先让用户看懂、能运行、能配置，验证画布是否能帮助他们理解过程。只有用户研究证明自由编排有价值，才扩大交互范围。

## 8.5 ComfyUI 借鉴边界

| 借鉴内容 | 本项目的使用方式 | 不照搬的部分 |
|---|---|---|
| 节点与连线 | 展示工作流执行步骤及依赖 | 第一版不开放任意拓扑编辑 |
| 节点输入输出 | 解释每一步处理的输入和产物 | 不要求用户理解所有技术参数 |
| 子图/模块封装 | 将检索、生成、校验等组合成可复用模板 | 不预先做复杂工作流市场 |
| 运行状态和日志 | 展示执行中、成功、失败、等待人工确认 | 不让执行日志代替专业设计结果 |
| 模板 | 用户从预置品类/任务模板开始 | 不把模板数量当作产品价值 |
| App Mode 思路 | 为普通策划提供简化操作入口 | 不强迫普通用户进入高级节点编排界面 |

# 9. 信息架构与核心页面

## 9.1 信息架构建议

1. 项目与工作区：项目列表、项目基础设置、品类与分发渠道、版本。

# 10. JD 研究：目的、结论与作品集映射

## 10.1 JD 研究的目的

JD 研究不是直接决定产品做什么，也不是通过岗位数量证明市场需求。它主要回答：企业招聘什么类型的人；这些岗位要求哪些能力；哪些要求是硬门槛、哪些是能力项；个人已有能力和差距是什么；作品集项目应该提供哪些证据。

JD 反映企业的招聘需求，不等于游戏团队真实的工具需求。招聘某类策划岗位，也不代表企业一定需要 AI 关卡生成器；岗位方向出现得多，可以提高对应业务调研的优先级，但产品需求仍要通过实际用户工作流程和返工案例验证。

## 10.2 当前 JD 工作状态

用户已经完成 20 条 JD 的收集，并反馈第 6 章六项完成标准已通过。初筛时，6 条 JD 曾被标记为“小游戏相关”，但二次按目标岗位类型和实际求职相关性筛选后，不能把 6 条全部当成小游戏策划岗位。当前可比口径为：小游戏/休闲设计相关目标岗位 3 条（米可世界、片刻工坊、钛铼海外休闲方向）；RPG/剧情相关目标岗位 2 条（紫龙剧情策划、腾讯互动叙事相关岗位）。原始 6 条中的其他 3 条分别存在校招身份限制、岗位实质为项目管理、或工作内容偏评测打标而非游戏设计等问题。

因此，当前目标岗位样本的可比结果是 3:2，而不是 6:0。这个比例只描述用户已经收集的 20 条样本经岗位筛选后的目标岗位数量，不代表市场招聘份额、行业规模或岗位竞争程度。它支持小游戏方向提高研究优先级，但不足以排除 RPG，也不能单独证明任何一类产品需求。岗位名称、岗位实际职责、校招/经验要求和投递资格必须在 JD 矩阵中逐条标注。

本轮不要求继续无限增加 JD 数量。下一步重点是完成能力模型、岗位分层和项目证据映射，必要时仅补充与目标岗位高度相关的缺口样本。

## 10.3 JD 分析字段

公司与职位、工作城市、招聘类型、发布日期/更新时间、采集日期、链接和来源类型、是否确认在招、原文职责、经验和学历硬门槛、游戏业务要求、AI 技术要求、研发工具要求、跨团队协作要求、加分项、岗位类别、游戏品类/方向、能力标签、个人现状、项目映射。

提取时严格区分：A. 原文明示要求；B. 根据岗位职责合理推断的能力；C. 原文未提及、不能判断的内容。不能把研发工程师岗位误归为产品经理，也不使用没有权重依据的“岗位匹配度 80%”。

## 10.4 岗位能力模型与项目证据

| 能力层 | 企业希望看到什么 | 本项目可以提供的证据 |
|---|---|---|
| 业务理解 | 理解游戏策划角色、流程、产物和上下游 | 用户访谈、业务流程图、真实/脱敏产物样例 |
| 产品设计 | 将模糊问题转成清晰场景、需求和范围 | JTBD、PRD、信息架构、原型、状态和异常设计 |
| Agent 设计 | 任务拆解、工具调用、状态管理、暂停和恢复 | 工作流图、工具契约、执行日志、异常处理 |
| 知识与规则 | 组织项目资料、品类 Schema 和 RulePack | 数据模型、来源引用、规则说明和版本记录 |
| 质量评测 | 建立测试集、GT、错误分类和指标 | 测试样本、对照实验、Bad Case 和回归结果 |
| 协作与交付 | 让专业人员修改、审核、交接和追踪 | 审核记录、版本差异、导出包、用户测试 |

## 10.5 JD 阶段最终交付

- 20 条 JD 原文和来源归档。
- 对“小游戏相关 6 条”进行二次目标岗位筛选，形成小游戏/休闲设计岗位 3 条、RPG/剧情相关岗位 2 条的可比口径，并保留其余岗位不纳入比较的原因。
- 岗位分类与岗位分层：冲刺、主攻、备选。
- 5–7 个重复出现的能力要求及其对应岗位。
- 硬门槛、能力项和个人差距清单。
- 作品集能力映射表：每项能力对应具体功能、文档、指标或演示证据。

完成上述交付后，JD 阶段可以冻结，不因后续每次产品改动而重新收集大量岗位。

# 11. S2 用户调研：访谈计划、问题与证据标准

## 11.1 S2 的目的

S2 不是证明“小游戏需要 AI”，而是了解实际策划任务从需求到交付的过程：谁做、何时做、输入是什么、输出是什么、现有工具是什么、哪里耗时、哪里返工、怎样检查、谁负责最终决策。当前优先研究小游戏及休闲游戏团队，但不把所有小游戏视为同一种设计工作。

## 11.2 访谈对象规划

建议首轮完成 3–5 次有效访谈，优先接触小游戏/休闲游戏相关人员，其中尽量包含关卡策划、玩法策划、系统/数值策划和小团队/独立开发者。若可行，可另访谈 1–2 位其他品类从业者（例如 RPG 或其他游戏设计角色）作为参照，帮助理解通用工作流与品类差异。对照样本不是必须与小游戏样本数量完全相等；若数量不等，报告必须标明样本不平衡，不能做强比较结论。

“有效访谈”是指受访者确实做过相关设计工作，能讲清最近一次具体任务的流程、输入、产物和问题；泛泛表达“AI 很有用”不算有效访谈。

## 11.3 访谈前准备

- 准备一页中性研究说明，只介绍研究主题，不展示完整产品方案，避免诱导用户赞同。
- 先询问最近真实发生的设计任务，不从“你需要 AI 吗”开始。
- 征得同意后才录音或截图；不记录公司机密、未公开内容和个人敏感信息。
- 尽量收集公开或脱敏的设计文档、关卡表、配置表、测试反馈、错误截图和流程样例。
- 访谈结束后 24 小时内整理原话、展示事实、分析推断和待验证问题。

## 11.4 核心访谈问题

| 主题 | 访谈问题 | 需要记录的证据 |
|---|---|---|
| 角色与场景 | 你负责哪类游戏和什么设计工作？最近一次完整任务是什么？ | 角色、项目类型、最近任务背景 |
| 工作流程 | 从拿到需求到交付，中间具体经过哪些步骤？ | 流程顺序、参与人、工具和等待点 |
| 输入资料 | 设计前通常拿到什么资料、规则和历史版本？ | 文档、表格、配置、参考素材 |
| 设计产物 | 最终交付什么文档、表格、配置或可运行内容？ | 字段、格式、接收者和验收方式 |
| 时间与返工 | 最近一次返工是什么原因？花了多久？发生多频繁？ | 时间、频率、返工轮数、影响 |
| 错误类型 | 最近一次明确的设计或配置错误是什么？如何发现？ | 可复核的失败案例和定位方式 |
| 现有工具 | 目前使用哪些编辑器、引擎、表格和协作工具？ | 已解决的能力和缺口 |
| 参数与规则 | 哪些约束能用明确规则判断，哪些靠手感和经验？ | 可程序化检查的边界 |
| AI 使用边界 | 哪些步骤可以由 AI 生成，哪些必须人决定？ | 可交给 AI 的环节及风险 |
| 最小价值 | 如果只解决一个问题，你最愿意先试什么？为什么？ | 具体使用意愿、触发条件 |

## 11.5 针对小游戏的补充问题

- 一关从立项/需求到能玩，实际经历哪些步骤？
- 关卡目标、地图/棋盘、障碍、步数、资源和难度参数分别由谁维护？
- 难度如何判断，是靠数值、测试数据、试玩反馈还是策划经验？
- 最近一次关卡过难、过易、无法完成或资源配置异常是什么时候？如何发现和修复？
- 是否存在一份能够表示关卡配置、目标、对象和约束的结构化文件？
- 当一个参数改变时，哪些关卡、对象或后续配置会受到影响？
- 程序和 QA 如何验证策划设计可以实现、可以通关？
- 如果工具提示“这个目标在当前参数下无法完成”，用户希望看到什么证据才会相信？
- 哪些设计判断不能完全自动化，例如趣味性、节奏、视觉感受和玩家体验？

## 11.6 痛点优先级

每个痛点从发生频率、处理耗时、错误影响、现有工具缺口、可结构化程度/可检查程度、AI 可辅助程度六个维度做 1–5 分初评。评分必须附证据，不得用单个受访者的主观偏好替代重复案例。优先考虑发生频率高、返工成本清楚、输入和规则可获得、错误可被复核的场景。

## 11.7 S2 通过标准与决策纪律

建议至少完成 3 次有效访谈，争取 3–5 次；至少有两个独立受访者提到同一类具体问题，或有一个高可信的实际工作样例能够充分说明问题的频率、耗时和影响；至少重建或取得一份可公开/脱敏的任务交付物或字段清单；确认用户愿意试用的最小能力，而不是只获得“听起来不错”的反馈。

如果某个具体子场景只有 1 位受访者支持，就只能标记为个体线索。如果两个候选场景的访谈数量差异很大，不应直接宣布数量更多的一方“需求更强”。样本不足时可以继续访谈，或只做技术探索原型，不得包装成市场结论。

## 11.8 S2 第一轮实际结果（2026-11-09）

本节并入《S2 用户与业务访谈·第一轮结论》，共五份样本：三份游戏行业样本、两份电力行业跨领域对照。游戏行业样本分别覆盖小型、中型和大型团队，但每种规模只有一个样本，且工作岗位和设计对象不同；因此只能说明第一轮样本覆盖了不同规模，不能据此得出“团队规模影响痛点结构”的因果或比较结论。

| 编号 | 对象 | 规模 | 方向 | 采集方式 | 信息完整度/证据限制 |
|---|---|---|---|---|---|
| 01 | 汽机检修从业者 | 未说明 | 电力跨行业对照 | 聊天、回忆整理 | 工作票制度信息较完整，事故细节缺失 |
| 02 | 高压电工 | 未说明 | 电力跨行业对照 | 聊天、回忆整理 | 仅确证有唱票机制 |
| 03 | 叙事关卡策划 | 小型团队 | 叙事/内容结构 | 对话、同步整理 | 机制描述较清楚，无工时数字和事故细节 |
| 04 | 放置类活动策划 | 中型团队 | 数值/机制/配比 | 贴吧公开回复 | 有流程描述和一次轻量事故；证据等级低于正式一对一访谈 |
| 05 | 剧情策划（米哈游） | 大型团队 | 叙事/世界观 | 文字问答 | 信息相对完整，涉及三级核对机制 |

**核心观察：不同设计对象出现了相似的关系核对问题。** 样本 03 的工作对象是角色、剧情和关卡，关注角色关系、剧情承接以及剧情与关卡的切分，原话为“这一步怎么去和关卡去做切分”；样本 04 的工作对象是机制、活动和奖励，提到新机制与已有机制的联动“一般都是靠灵光乍现”；样本 05 的工作对象是设定、大纲、剧情和任务，重点核对角色经历、人物关系和时间线，原话为“剧情积累越多越容易出现细节遗漏”。

三份样本共同形成一个需要继续验证的问题：**设计对象发生变化时，如何识别哪些关联对象和下游设计内容需要同步检查？** 这可以暂时称为“变更影响分析”假设。当前证据能支持该问题在这几份样本中出现，但不能证明它在游戏行业普遍、高频发生，也不能证明所有小游戏团队都有同样问题。

### 11.8.1 假设状态

| 假设 ID | 假设 | 第一轮状态 | 依据与限制 | 后续处理 |
|---|---|---|---|---|
| H-01a | 存在高频、耗时的重复步骤 | 未验证 | 有关系核对、锚点、机制联动等方向线索，但五份样本没有可靠工时数字 | 不再把单次耗时作为首轮主要价值指标；改看问题发现阶段与返工次数 |
| H-01b | 相关步骤的质量可以被判断 | 已验证（当前样本范围） | 存在三级核对/多层 Review，说明受访者有判断“对不对”的标准；不代表已有统一量化指标 | 后续为首期场景制定可复核 GT 和质量标准 |
| H-02 | Brief 解析与重复整理成本明显 | 未验证 | 五份样本均未直接谈及需求解析成本 | 降为次要价值论点，不作为首期主卖点 |
| H-03a | 设定/对象冲突确实存在 | 已验证（当前样本范围） | 大型项目剧情样本明确确认设定冲突，另有样本描述关系和承接检查 | 纳入变更影响分析与一致性检查的问题假设 |
| H-03b | 冲突造成显著返工成本 | 未验证 | 没有可靠返工时长；受访者不便展开内部事故细节 | 本轮不再追问；报告写“问题存在，成本未量化” |
| H-04 | 游戏品类差异会影响设计对象与痛点结构 | 已验证（探索性） | 放置活动样本不涉及叙事规则；三个岗位的设计对象不同，但出现关系核对线索 | 保持品类 Schema/RulePack/GT 隔离；不把规则跨品类复用 |

### 11.8.2 可写与不可写的结论边界

可以写入报告的表述必须限定到具体样本，例如“一位大型项目剧情策划描述，公共设定变更需要同步给剧情、任务和演出相关负责人，并保留历史版本”；“一位叙事关卡策划描述，每个关卡有锚点，触发后才引出下一步，某 NPC 需要完成前置任务后才能认识”；“一位放置类活动策划描述，固定活动按开服天数推进，并提到奖励产出占比 1:10:100、中间档需固定人数”。这些内容只能作为各自样本的直接陈述，不得扩展为行业统一流程。

不能写成“游戏策划普遍存在该痛点”“设定冲突每天发生”“该问题每年造成 X 小时返工”，因为当前样本没有足够频率和工时数据。火影相关的二手“策划说”材料不是策划本人自述，只能作为公开行业信息，不得混入受访者原话。

访谈中有人对内部设定管理和事故细节表示不便透露，这是研究边界与信息敏感性的观察，**不是需求存在、问题频率高或行业没有标准方案的直接证据**。不能写成“因为问不出来，所以需求一定存在”。

### 11.8.3 对产品定位的影响

1. **优先问题从泛化的品类模块化转向变更影响分析。** 多品类模块化仍是产品架构，但第一轮最有价值的跨岗位线索，是引用关系、对象依赖和修改后的影响范围。
2. **通用大模型是现实替代品。** 样本反映策划会使用大模型讨论设计瓶颈，但当前样本中的差异化假设不是“也使用 AI”，而是工作台能够读取项目中的结构化表格、前置条件、角色关系、规则和依赖数据，回答“改这一处会影响哪里”。该能力仍需原型验证。
3. **版本管理不是当前核心痛点。** 样本中已有历史版本追溯做法，因此版本管理可以作为必要的基础设施，但不应作为主要差异化卖点。

### 11.8.4 剩余缺口与本轮处理

| 缺口 | 对产品的影响 | 第一轮决定 |
|---|---|---|
| H-03b 返工成本数字 | 限制价值/ROI 论证 | 不再追问；标记“问题存在，成本未量化” |
| H-01a 工时数字 | 限制效率提升结论 | 不以单次耗时作首轮核心指标；改记录问题发现阶段和返工次数 |
| H-02 Brief 解析成本 | 限制生成环节的主价值论证 | 降为次要论点 |
| 真实数据格式 | 影响 Schema 设计 | 先通过原型反推，标记为“假设格式”，获得样例后再冻结 |

第一轮调研到此收口。继续追问同类内部事故和成本信息可能损害访谈关系；剩余缺口通过原型测试、公开资料和后续自愿提供的脱敏样例补充，不继续依赖追问。

### 11.8.5 本轮结论如何影响首期场景

S2 第一轮没有足够证据选定具体小游戏玩法。放置类活动策划样本是一条有价值线索，但来源为公开论坛回复，不能单独支撑首期立项。下一轮优先寻找关卡/玩法/系统数值策划的直接工作样例，验证“变更影响分析”在小游戏场景中的具体对象、数据格式、检查规则和实际使用意愿。首期场景仍由 S4 决策，不因本轮有线索就自动冻结。

# 12. S3 竞品研究：类别、边界与差异化

## 12.1 竞品研究目的

竞品研究不是为了证明“别人做不到”，而是弄清楚现有工具已经解决什么、用户仍需手工做什么、哪些能力值得借鉴、哪些能力不应重复建设。比较必须区分公开资料、产品实测、用户报告和推断。未打开原文或未跑通的功能不得写成确定事实。

## 12.2 四类竞品

**一、传统叙事编辑与脚本工具。** 代表包括 articy:draft、Ink/Inky、Twine 和 Arcweave。它们已经具备不同程度的剧情节点组织、角色/对象管理、变量、条件分支、流程预览和路径模拟能力。articy 的 Simulation/Analysis Mode 可以在指定 Journey 中模拟条件变化、跟踪变量并显示当前流程中的无效分支；Arcweave 可以通过 Play Mode 测试条件分支。公开资料尚不能证明它们具备自动穷举全局状态空间并证明所有节点在所有合法状态下可达的能力。研究重点是检查覆盖范围、路径分析深度、诊断信息、工作流集成和用户实际使用方式。

**二、AI NPC 与实时叙事平台。** 代表包括 Inworld、Convai 和 NVIDIA ACE。主要围绕角色对话、记忆、行为、情绪、动作、运行时交互和引擎接入展开。Inworld Character Studio 退役不能推导整个赛道失败；相关能力迁移到 Agent Runtime 的范围需要以官方资料为准。Convai Narrative Design 的目标、决策和触发器能力也不能直接等同于 RPG 任务质量验证。研究重点是区分运行时 NPC 行为与研发阶段的任务设计、规则检查和内容生产。

**三、AI 游戏生成与研发引擎。** 代表包括 Rosebud AI、Summer Engine 等。它们从自然语言描述生成可玩内容，能力可能覆盖场景、脚本、NPC、运行、测试、迭代和发布。不能简单写成“生成完就交付、不验证”。研究重点是生成结果能否进入真实项目、能否被程序化修改、运行时测试覆盖到哪里，以及是否具备针对策划约束、状态逻辑和领域规则的专门诊断。

**四、叙事结构分析与校验工具。** 代表项目包括 IntelliVNG、Kleene，以及待核实的 ToolsFYI Interactive Story State Author。已公开展示的相关能力包括孤立节点、死胡同检测、路径枚举、结构约束检查、问题节点定位，部分项目还展示了将问题节点交给 Agent 重新生成的流程。ToolsFYI 在原文和实际运行未独立核实前不得进入正式结论。通用死路检测、路径枚举和有限状态搜索不能作为本项目独占创新。

## 12.3 三条差异化方向

| 方向 | 需要证明什么 | 当前证据状态 |
|---|---|---|
| 结构化设计数据与变更影响分析 | 能读取项目对象、引用关系和约束，识别变更后可能受影响的对象与下游内容 | S2 有探索性线索；真实格式、覆盖范围和用户价值待原型验证 |
| 品类专属 Schema 与规则集 | 能理解具体游戏设计对象和领域约束，避免通用分析误判 | 需要首期品类规则测试集证明 |
| 可解释、可修复的诊断与工作流闭环 | 不止报告失败，还能定位对象、原因、影响范围和候选修改，并嵌入用户确认、留痕与交付 | 当前是产品设计目标，尚未实现；需用户测试 |

“4–5 级签发、唱票复诵”等来自高风险工业流程的机制不直接作为游戏策划差异化，人工确认、审核记录和版本追踪可以保留，但审批层级必须由真实访谈决定。“中文 RPG 语境”或中文游戏语义适配应作为本地化能力方向，不应在证据不足时写成竞争壁垒。

## 12.4 articy 检查能力的证据边界

目前较准确的描述是：articy 已有路径级模拟、变量跟踪与条件分析；自定义函数需要手动输入预期返回值；公开文档尚未证明其支持自动穷举全局状态空间。不能写成“articy 做不到”，只能写“公开资料未证实，仍需实测确认”。

若开展实测，可设计两个内置变量用例：A. 存在两条替代路径，验证是否能自动分析未选中的替代路径；B. 变量最大值为 1，但目标条件要求大于等于 2，验证能否不经人工逐条试走而判定目标在所有合法状态下不可达。尽量使用内置变量和条件，不引入自定义函数。若未报错，只能记录“本次测试未观察到全局不可达诊断”，不能断言软件不支持。

## 12.5 竞品结论的使用纪律

- 未打开原文或未实际运行的功能，标记“据公开描述”或“待核实”。
- 区分“已有类似实现”和“已经达到成熟产品级”。开源项目也足以推翻“只有我们能做”，但不等同于成熟商业策划工具。
- 不因竞品已有功能就否定自己，也不因自己需要某个功能就贬低竞品。判断标准是目标用户在真实工作中是否需要、是否愿意使用。
- 引用案例必须补足边界。例如《骇游侠探》开发复盘指出 Articy 自定义函数的语法/参数检查存在缺口，但团队后来自建插件补上；只能证明官方能力在该场景有缺口，不能称 Articy 完全没有校验能力。
- Q013 降级但不砍掉。它是 RPG 模块的状态条件质量能力之一，价值取决于诊断结果是否能被策划理解和修复。
- 竞品矩阵中的待核实项继续在工作簿“待核实线索”页维护，不将未核实内容写成正文事实，不阻塞 S2/S4 主线。

# 13. S4 品类与 MVP 决策闸门

## 13.1 S4 解决三个问题

第一，确定产品结构：多品类工作台、通用底座与品类模块。第二，确定隔离机制：品类 Schema、RulePack 和评测集必须分离。第三，确定首期具体设计场景：这一项不能仅凭 JD 或个人偏好决定，必须结合 S2 用户研究和 S3 竞品边界。

## 13.2 已确定的产品结构

产品是一个多品类的 AI 游戏策划与研发工作台。Agent 工作流、AI 内容生成和质量检查是同一条生产链上的不同职责。通用层提供编排、检索、生成调度、校验执行、问题对象、人工审核、版本和导出；品类层提供专属设计对象、Schema、Prompt/生成策略、规则、语义标准和评测集。

## 13.3 已确定的市场优先级

小游戏及休闲游戏是当前重点市场和首期场景研究的优先方向，但产品不专门服务小游戏，也不提前锁定某一种玩法。具体是消除、合成、塔防、模拟经营还是其他小游戏设计场景，待访谈验证。其他游戏类型仍可以接入产品架构，但未实现模块必须明确标注为规划中。

## 13.4 当前场景判断（引用第 7.2 节六维标准）

六个评估维度及其定义统一以第 7.2 节为准，本节不重复定义。结合当前 JD 和 S2 第一轮，当前可得判断如下：

| 维度 | 当前观察 | 状态 | 对决策的含义 |
|---|---|---|---|
| 结构与规则复杂度 | 不同玩法/岗位的设计对象差异明显；RPG 有成熟的状态规则资产，小游戏需按具体玩法建立规则 | 部分有证据 | 不能将 RPG 规则直接套到小游戏；需比较首期任务的可检查程度 |
| JD 岗位关联 | 目标岗位细筛后，小游戏/休闲设计 3 条，RPG/剧情相关 2 条 | 有限样本已整理 | 小游戏优先，但不能据此排除 RPG |
| 个人能力与内容匹配 | RPG 有既有内容积累；小游戏需要补足具体玩法与参数设计知识 | 已知个人准备情况 | 只能作为执行成本参考，不作为市场证据 |
| 访谈可得性 | 目前 3 份游戏行业样本，角色/规模不同；放置活动样本来自公开回复 | 部分证据 | 需要针对目标小游戏场景补充直接访谈 |
| 评测可构造性 | RPG 已有 Q001–Q013；小游戏规则和 GT 必须按具体玩法重建 | 部分证据 | 需先选具体设计任务，再判断测试集可构造性 |
| 第二场景扩展成本 | 依赖数据模型、RulePack 和通用影响分析框架的边界 | 未验证 | 留待工程轻量验证，不预先承诺改动量百分比 |

当前不做“RPG 3 项、小游戏 3 项”之类的主观计数排名。场景评分需回到证据来源、样本质量和目标用户实际工作案例。

## 13.5 决策规则

建议采用以下最低决策纪律：

1. 至少有 3 次有效访谈，优先来自小游戏/休闲游戏设计相关角色；
2. 至少两个独立受访者反复提到同一类具体问题，或有一个高可信工作样例能说明问题的频率、耗时与影响；
3. 如果要选定某个具体小游戏子类型，最好有至少 2 名直接从事该场景的受访者，或一份高度可信的实际工作样例加一次原型验证；
4. 若样本不够，继续补访谈或只做技术探索，不能用“没有访谈”当成 RPG 自动胜出的证据；
5. 若小游戏访谈显示现有工具已充分解决问题，或问题无法被结构化/检查，需重新比较其他游戏设计场景；
6. 不因已经写了 RPG 文档、构造了原创内容或投入技术实验而强行继续 RPG。

以上是本整合稿建议采用的工作门槛；若后续用户研究计划改变样本设计，应在决策记录中说明，而不是静默改变标准。

## 13.6 S4 的正式交付

- 《首期场景决策记录》：选定场景、证据、备选项、否决理由和限制。
- 《目标用户与 JTBD》：目标角色、触发场景、输入、输出和关键痛点。
- 《MVP 范围清单》：Must/Should/Could/Not in MVP。
- 《首期数据模型与 Schema 草案》：最小设计对象与字段。
- 《首期 RulePack 草案》：阻断、高、中等级规则及适用范围。
- 《成功指标与测试计划》：GT、样本、对照方案和验收标准。
- 《交互原型范围》：工作流画布和专业设计编辑器的第一版边界。

# 14. MVP 范围、非目标与验收标准

## 14.1 MVP 核心目标

MVP 不是一个可自由搭建任何 Agent 的工作流平台，也不是一款游戏引擎。MVP 是一个围绕单一首期设计场景、可以从 Brief 走到结构化设计产物，并提供质量检查、诊断、人工审核和导出的最小可用工作台。

## 14.2 MVP 必须具备的能力

| 模块 | MVP 必须实现 | 暂不实现 |
|---|---|---|
| 项目与资料管理 | 项目、品类、渠道、资料、来源、版本和基础检索 | 大型企业权限、复杂知识图谱 |
| Brief | 品类专属字段、约束、禁止项、缺失字段识别 | 语音和多模态输入 |
| Agent 执行 | 固定工作流、状态、日志、工具调用、暂停和人工确认 | 多 Agent 自主协商、开放工作流市场 |
| 设计生成 | 生成首期场景所需结构化对象和内容 | 一次生成完整商业游戏 |
| 专业编辑器 | 对首期设计对象进行列表/表单/可视化编辑 | 完整替代专业编辑器或引擎 |
| 规则检查 | Schema、引用、参数和首期品类规则 | 全部游戏品类规则 |
| 语义审查 | 对照项目知识和设计约束提出疑点，返回证据 | 自动裁决趣味性或艺术质量 |
| 诊断建议 | 定位问题、说明原因、给候选修复方向 | 未经确认自动改写所有设计 |
| 审核与版本 | 采纳、修改、忽略、退回、版本差异和锁定 | 多人实时协作 |
| 导出 | JSON/CSV/Markdown 或首期需要的格式 | 未验证的引擎原生集成 |

## 14.3 MVP 首期范围需要冻结的对象

首期场景确认后，必须冻结：输入 Brief 的字段；项目知识资料类型；设计对象与 Schema；生成流程与用户确认点；规则包与问题严重程度；输出格式；30 条首轮评测样本的初步设计；首期验收门槛；模型和 API 预算；暂不实现的功能。

## 14.4 MVP 验收条件

- 端到端流程可重复运行，不依赖人工在后台直接改数据。
- Brief 缺少关键约束时会澄清，不会自行补造决定性要求。
- 生成结果符合首期 Schema，失败时返回明确错误或进入修复流程。
- 规则检查可以稳定识别预先设计的阻断异常。
- 问题报告包含对象位置、规则 ID、原因和可复核证据。
- 修复建议不能静默覆盖已确认内容；重大修改必须由用户确认。
- 用户可以编辑、审核、生成新版本并导出。
- 评测结果记录测试集、GT、模型、Prompt、Schema、RulePack 版本和运行成本。

# 15. 数据模型、Schema 与规则隔离机制

## 15.1 核心对象

| 对象 | 作用 | 层级 |
|---|---|---|
| GameProject | 项目、`distribution_channel`、`genre`、`design_domain`、版本和启用模块 | 通用 |
| GenreProfile | 品类、设计领域、Schema、RulePack 和导出配置 | 通用适配配置 |
| KnowledgeEntry | 项目资料、规则、术语、来源、版本和标签 | 通用容器，内容字段按品类扩展 |
| DesignBrief | 设计目标、约束、禁止项、交付要求 | 通用容器，字段由品类模板扩展 |
| DesignArtifact | 设计产物容器，保存品类、类型、Schema 版本和数据 | 通用容器 |
| ValidationIssue | 规则问题、级别、目标对象、证据、解释、建议和状态 | 通用问题对象 |
| ReviewRecord | 审核动作、评论、前后版本、时间和操作者 | 通用 |
| ExportPackage | 导出格式、Schema 版本、校验状态和产物版本 | 通用 |
| Genre-specific objects | Level、Board、Obstacle、Quest、Node、Skill、Map 等 | 品类专属 |
| DependencyRelation | 设计对象之间的引用、前置条件、触发、资源依赖和影响关系 | 通用关系容器，关系类型由品类适配器定义 |
| ImpactAnalysisResult | 某对象变更后的潜在受影响对象、路径、依据和确认状态 | 通用分析结果，依赖规则按品类解释 |
| RunRecord | 一次工作流运行的输入摘要、节点状态、日志和成本 | 通用运行记录 |

## 15.2 通用机制与通用规则的区别

通用校验引擎可以提供 ID 唯一性、引用完整性、字段必填、数据类型、版本匹配等基础校验能力；但具体校验范围和约束必须由当前品类 Schema 声明。不能因为“ID 唯一性”看起来通用，就默认任何品类都以同一种对象范围、命名空间和唯一性规则执行。

例如：节点 ID 可能要求在单个关卡内唯一；资源 ID 可能要求在整个项目中唯一；某些参数是否必填，也需要由首期设计对象声明。通用的是执行机制和问题输出结构，具体规则含义由 Schema 和 RulePack 决定。

## 15.3 RulePack 隔离机制

每个规则包至少声明以下信息：

| 字段 | 用途 |
|---|---|
| rulepack_id | 规则包唯一标识 |
| applicable_genres | 适用游戏品类 |
| design_domain | 适用设计领域，如关卡、系统、任务 |
| schema_version | 对应数据结构版本 |
| rulepack_version | 规则包版本 |
| rules | 规则列表、严重级别、输入字段和执行器 |
| evaluation_profile | 对应测试集和验收口径 |

加载规则包时必须同时检查 `project.genre`、`design_domain` 和 Schema 版本。未声明适用品类或版本不匹配的规则默认不执行，并在日志中说明原因，而不是默认对所有品类开放。

## 15.4 规则分层

- 通用校验机制：提供执行器、输入输出契约、问题对象、日志和结果聚合。
- 通用结构约束：只有在具体 Schema 明确声明后，才执行 ID、引用、类型、必填等检查。
- 品类规则：检查关卡可完成性、合成链、资源循环、塔防路径、RPG 任务状态等领域逻辑。
- 语义审查：根据品类定义的知识、设计目标和 GT，输出疑点和证据，不能替代确定性程序判断。

## 15.5 跨品类规则调用

默认禁止把一个品类的规则包混入另一个品类正式检查。确实需要借用其他品类的规则作参考时，必须显式声明来源和用途，并把结果标为“参考提示”，不得写入该品类正式校验通过率。

## 15.6 评测数据隔离

每个品类和设计领域建立独立测试集、GT、Bad Case 分类和验收门槛。不同品类的测试样本不能简单混算成一个“整体通过率”。通用底座的通用性能可以单独统计，品类内容质量必须分开报告。

# 16. Agent 工作流、状态管理与人工确认

## 16.1 最小架构

首版采用“单一工作流编排器 + 确定性工具 + LLM 调用 + 人工审核 + 品类适配器”。通用编排器管理状态和运行顺序，品类适配器提供 Brief 字段、生成配置、Schema、RulePack 和专属编辑器配置。模型节点通过统一服务接口调用，业务代码不直接绑定某一家模型 SDK。

## 16.2 工作流状态

| 状态 | 进入条件 | 允许动作 | 离开条件 |
|---|---|---|---|
| draft | 用户创建任务 | 编辑和保存 Brief | 必填信息完整 |
| brief_ready | Brief 结构完整 | 解析、检索、提出澄清问题 | 用户确认解析摘要 |
| planning | 需求已确认 | 生成设计计划和对象结构 | 用户确认主要结构 |
| generating | 结构方案已确认 | 生成详细设计内容和参数 | 结构化输出通过 Schema |
| validating | 数据已生成 | 执行规则与语义检查 | 检查报告完成 |
| diagnosing | 存在问题 | 定位原因、生成候选修复 | 诊断结果可复核 |
| needs_review | 等待人工决策 | 修改、采纳、忽略、退回或要求重新生成 | 高风险问题处理完毕 |
| approved | 用户确认 | 锁定版本、导出 | 导出成功 |
| exported | 文件生成 | 下载、再次导出 | 当前版本结束 |

## 16.3 人工确认点

- 需求解析后确认目标、关键约束、禁止项和输出要求。
- 设计计划/主要结构生成后确认，再进行大规模内容生成。
- 高风险规则冲突、语义冲突或不确定诊断必须交由用户判断。
- 任何修复建议在应用前展示变更内容和影响范围。
- 导出前检查阻断级问题；存在未解决问题时阻止或要求明确确认。
- 用户已经锁定的内容不能被重新生成静默覆盖。

## 16.4 异常与恢复

每个节点应定义超时、模型错误、结构解析错误、检索为空、规则未覆盖、搜索上限触发、用户取消和重试行为。重试必须保留原始输入和失败记录。不能通过静默忽略错误让流程显示成功。

# 17. 质量检查、诊断修复与评测方案

## 17.1 检查和诊断分层

检查、变更影响分析、诊断和修复建议是不同能力。检查回答“有没有违反规则”；变更影响分析回答“一个对象发生变化后，哪些引用对象、前置条件、联动机制和下游产物可能受影响”；诊断回答“问题在哪里、为什么发生”；修复建议回答“有哪些候选修改可以解决问题”。四者需要分别定义输出和验收，不得用一个“校验通过率”概括所有能力。

| 层次 | 输出 | 验收重点 |
|---|---|---|
| ① 状态/规则判定 | PASS、FAIL、SAT、UNSAT、UNKNOWN 或品类专属结果 | 规则判定与 GT 一致 |
| ② 变更影响分析 | 变更对象、直接/间接受影响对象、引用链和影响依据 | 用人工 GT/案例确认影响对象召回与误报；不能把潜在关系写成确定后果 |
| ③ 冲突原因定位 | 违反点、对象/边/参数位置、约束来源和影响范围 | 每个关键失败能给出可复核原因；只报告失败但没有定位视为诊断未通过 |
| ④ 修复建议 | 一个或多个候选修改、预期影响和风险 | 建议可解释、可编辑；应用前需要用户确认 |

## 17.2 Q013 的定位

Q013 是 RPG 任务模块的有限状态条件可满足性检查能力，不是整个工作台的独占技术创新。它保留在 RPG 专属规则体系中，不能未经重新定义就用于小游戏关卡或其他品类。

Q013 应分成三个独立验收层：

1. **状态可满足性判定：** 判断路径上的状态条件是否存在合法状态组合；输出 SAT、UNSAT 或 UNKNOWN。
2. **冲突原因定位：** 对 UNSAT 输出至少一个可复核的违反点，例如某目标需要 2 条线索、但所有合法路径最多只能获得 1 条，并指出关联节点/边/变量。
3. **修复建议生成：** 首期只做规则化模板建议，例如调整门槛、增加可获得资源的路径或修改前置条件；不做未经确认的开放式自动改写。

RPG 状态搜索约束沿用既有设计：变量仅允许布尔值和有限整数域；显式声明初始状态；条件计算时机明确；一条边允许包含多个原子状态变更；单次搜索默认上限 5 万个状态，触顶返回 UNKNOWN 并记录原因。UNKNOWN 不算通过，也不能被当成 UNSAT。

## 17.3 小游戏首期的规则设计原则

如果 S4 最终选定小游戏场景，必须根据该场景重新建立 Schema、RulePack 和 GT。可以参考的候选检查方向包括：对象和引用完整、参数在允许范围、目标条件明确、关卡资源配置一致、路径/目标可达、资源产出与消耗关系成立、难度参数满足预设边界等。具体规则必须来自真实设计对象和用户确认的规则，不能从 RPG 直接复制，也不能凭空定义。

## 17.4 对照评测方案

在首期场景适用的前提下，保留六组方案作为效果拆解方法：

| 组别 | 方案 | 观察目标 |
|---|---|---|
| H0 | 人工独立完成，不使用生成式 AI | 人工工作基线 |
| A | 单轮 Prompt 直接生成 | 最简单模型基线 |
| B | 结构化 Prompt，先解析再按 Schema 生成 | 观察结构约束影响 |
| C | B 加项目资料检索和来源引用 | 观察知识依据影响 |
| D1 | C 加确定性规则校验 | 单独观察规则引擎贡献 |
| D2 | D1 加 LLM 语义检查 | 观察语义审查增量；D2 对 H0 用于产品整体效果对照 |

每次对比只改变一个关键因素，使用同一批 Brief、同一版项目资料、相同模型配置和同一质量标准。H0 不使用生成式 AI。H0 需要保留三类记录：①问题首次被发现的阶段（设计阶段、生成后自查、规则检查、联调/试玩、QA/用户反馈等）；②返工次数或重大修改轮数；③最终质量评分与结构性错误数量。

历史方案还曾记录单个任务的实际完成耗时，但 S2 第一轮没有获得可靠工时数据，因此当前不将单次耗时作为首轮核心指标，也不据此宣称效率提升。若后续能够稳定计时，可作为探索性辅助数据单独报告。H0 的人工投入与时间记录不计入 API 预算；API 预算只计算 A、B、C、D1、D2 五组。若模型版本、温度、Prompt 或检索配置变化，必须记录。

## 17.5 测试集规模和保留集

既有方案设定首轮 30 条样本，其中 24 条开发集、6 条保留集。该规模继续作为当前规划目标；但样本类别必须在首期具体场景确定后重建，不能沿用 RPG 的“角色知识越界、隐藏结局”等类别去测试小游戏关卡。测试预算按 30 条总样本 × 5 个 AI 组（A/B/C/D1/D2）× 每组重跑次数估算；H0 是人工对照，不占用模型 API 调用组数。

保留集在 Prompt、Schema、RulePack 和评测标准冻结前不得反复用于调参。若保留集被反复查看并据此修改规则，应记录为开发数据，另建新的保留集。

第二品类轻量验证可以先使用 5 条手工样本，只验证最小 Schema、3–5 条关键规则和适配流程，不与首期 30 条样本混算。

## 17.6 验收口径

- 可导出的任务包/设计产物必须 100% 通过其 Schema 校验，阻断级问题为零。
- 规则检查器测试要求预先注入的阻断级异常 100% 检出，同时正常样本零误报。这里的 100% 衡量检查器判定正确性，不是要求所有测试样本本身都合法。
- 对 UNKNOWN 单独报告，不能当作通过。
- 语义检查 Precision/Recall、人工接受率、修改量、耗时和成本先在开发集标定，再冻结门槛。
- 效率比较以 H0 为基线；若 H0 只有本人完成，结论只能表述为个人对照实验，不能推广为行业效率结论。
- 每项结果报告样本、GT、模型版本、Prompt 版本、Schema 版本、RulePack 版本、运行成本和失败分布。

## 17.7 第二品类验证

第二品类只做轻量验证：最小 Schema（建议 3–5 个核心对象）、3–5 条规则、5 条手工样本和一个简单检查界面或命令行入口。首期工作流、主编排器、统一问题对象和校验执行框架尽量不改。验收重点是是否主要通过品类 Schema、RulePack、配置和适配器接入；不以源码行数改动比例作为唯一通过条件。若确有公共层修改，记录必要性和影响。

## 17.8 API 预算五科目与控制方式

API 预算需要在确定模型和单价后填写真实金额上限。当前先恢复预算科目与计算口径，不编造金额。

| 预算科目 | 记录内容 | 预算计算/管理方式 |
|---|---|---|
| 开发预算 | Prompt 调试、需求解析、生成、检索和 Agent 多步调用 | 记录每轮 token、调用次数、失败重试与实际金额 |
| 测试预算 | 固定样本集在 A/B/C/D1/D2 五个 AI 组中的调用 | 30 条样本 × 5 个 AI 组 × 每组重跑次数；H0 人工基线不计 API 费用 |
| 回归预算 | Bad Case 重跑、规则修改后的回归和模型升级后的复测 | 记录全量/局部回归范围和调用金额 |
| 预留预算 | 失败重试、模型更换、长文本超限补跑及不可预期调用 | 单独留出，不挪用后默认追加功能 |
| 总预算上限 | 项目允许的最高 API 支出 | 在开发前按模型单价、调用规模和预留比例填写；触顶即停止扩展，转向验证和包装 |

H0 的人工耗时和人力成本单独记录，不混入 API 账单。模型价格、输入/输出 token、平均调用次数和重试率确定后，再计算金额上限；未填写金额前不得将“有预算控制”描述为已完成。

# 18. 技术方案与实现路径

## 18.1 技术原则

先确定业务对象、规则边界和用户流程，再决定技术框架。不要为了使用 LangGraph、Dify、Coze、MCP 或某个前端库而反向设计产品。首期优先把业务逻辑和校验做成可测试的独立模块，前端只负责用户操作与结果可视化。

## 18.2 建议的首期技术栈

| 层级 | 首期建议 | 作用 | 何时升级 |
|---|---|---|---|
| 数据存储 | SQLite + FTS5 | 项目、知识、设计对象和关键词检索 | 多用户、多项目或检索质量成为瓶颈时调整 |
| 数据校验 | Pydantic / JSON Schema | 结构字段、类型和数据约束 | 根据实际 Schema 复杂度调整 |
| 工作流 | 纯 Python 状态机 | 单一 Agent 工作流和状态流转 | 状态复杂度明显上升时再引入编排框架 |
| 模型调用 | 统一 API 适配层 | 解耦供应商，支持 A/B 实验 | 按模型服务和成本需求增加路由 |
| 后端逻辑 | Python 模块化服务 | 生成、校验、诊断、版本和导出 | 随功能边界扩展 |
| 前端 MVP | Streamlit 或经原型验证后的轻量 Web UI | 快速实现工作台、表单、列表和运行展示 | 需要更强画布交互时再换专门前端 |
| 原型 | Figma | 验证信息架构、页面和操作流程 | 根据用户测试迭代 |
| 测试 | Pytest | 单元测试、规则测试、回归测试 | 增加端到端测试 |

以上为默认选型建议，不代表必须一次性使用所有技术。若用户证据表明需要特定编辑器或部署方式，应通过变更记录调整。

## 18.3 检索策略

初期项目资料规模较小，可从结构化文件、元数据过滤和关键词检索开始。每条资料维护 ID、类型、来源、版本和标签。只有当实际检索任务频繁失败，才引入向量检索、混合检索和重排；不为了“有 RAG”而引入复杂向量数据库。

## 18.4 工作流画布实现策略

第一版可以先将预设工作流展示为只读节点图或步骤视图，支持查看节点输入输出、运行状态、错误和可配置参数。自由节点拖拽和连线不进入首期。若未来用户确实需要自定义流程，再考虑 React Flow 等交互组件；是否采用 ComfyUI 类似的自由画布，应由原型测试与使用场景决定。

## 18.5 开发协作纪律

使用 WorkBuddy、Trae、Codex 或其他 AI 编程助手时，每次只执行一个明确任务。先让助手阅读项目方案、当前数据模型、任务和验收用例；先输出实施计划、预计修改文件、数据变化、风险和测试方案；确认后再改。修改后运行单元测试和对应回归，不得通过修改 GT 或测试预期掩盖 Bug。已确认内容不能被重新生成覆盖。文档、代码、测试集、Prompt、Schema 和 RulePack 版本要同步管理。

S1 和 S2 原则上可以并行，但当前 S1 的 20 条 JD 已基本完成。下一步应以 S2 为主，必要时用 JD 线索帮助寻找受访者，而不是继续大量收集岗位。

## 19.2 当前最近的执行顺序

1. 统一主方案中的产品定位：多品类工作台，小游戏优先，不是小游戏专用工具。
2. 整理 20 条 JD 的岗位类别、小游戏相关职责和可证明能力，形成最终能力映射。
3. 建立小游戏/休闲游戏受访者名单，优先寻找关卡、玩法、系统/数值策划与独立开发者。
4. 发出第一批 3–5 个访谈邀约，围绕最近真实任务开展访谈。
5. 整理真实流程、输入输出、返工案例、现有工具和可检查规则。
6. 对比候选小游戏设计场景，必要时补少量其他品类访谈作为参照。
7. 通过 S4 决定首期具体设计任务，冻结 MVP 范围。
8. 建立首期 Schema、RulePack、GT 和交互原型。
9. 以一个完整场景实现工作流、生成、检查、诊断、审核和导出。
10. 通过评测和第二品类轻量验证证明产品能力。

## 19.3 M0–M9 开发迭代建议

| 迭代 | 开发内容 | 验收重点 | 暂不做 |
|---|---|---|---|
| M0 原型 | 项目首页、资料、Brief、工作流视图、设计编辑、检查、导出 | 关键点击路径完整 | 真实模型调用 |
| M1 数据骨架 | 通用对象、首期品类 Schema、RulePack 元数据 | 可以保存/读取/校验样例 | 多品类完整 Schema |
| M2 Prompt 基线 | Brief 直接生成首期设计对象 | 有基线输出和错误记录 | 复杂 Agent 和检索 |
| M3 项目检索 | 检索项目规则、资料和历史设计 | 输出能引用来源 | 大型知识图谱 |
| M4 结构化生成 | 先规划、人工确认、再生成细节 | 产物符合 Schema 且可编辑 | 全自动完整游戏生产 |
| M5 确定性检查与影响分析 | 实现首期 RulePack 的结构/参数/规则检查，并建立首期对象引用与变更影响分析 | 注入异常能稳定命中规则；变更影响结果可与人工 GT 对照 | 用 LLM 替代确定性逻辑；未经证据支持的自动影响推断 |
| M6 语义审查 | 对照项目资料检查内容冲突和设计疑点 | 问题有位置、证据和说明 | 自动裁决主观体验 |
| M7 诊断、审核和版本 | 诊断建议、采纳/修改/忽略、版本差异和导出 | 用户修改不会被覆盖 | 复杂多级审批 |
| M8 整体回归 | 固定测试集、成本、时延、失败恢复和完整流程 | 结果可重复、限制清楚 | 无数据支撑的效果宣传 |
| M9 第二品类轻量验证 | 新 Schema、RulePack 和少量样本 | 验证通用层是否可复用 | 第二品类完整开发 |

这里的 M2 “Prompt 基线”是开发迭代名，与 M4/M2 降级交付等级不要混淆。降级交付等级可以另称“研究验证包 / 最低产品原型包 / 完整 MVP 包”。

## 19.4 交付等级

- **研究验证包：** Prompt 基线、结构校验、少量测试样本和对比报告。属于研究型交付物，不等同于产品 Demo。
- **最低产品原型包：** 可点击原型、首期 Brief 到结构化设计对象的真实生成流程、最小 Schema、规则集和已知限制。没有完整评测数据时必须明确说明。
- **完整 MVP 包：** 端到端工作流可运行、检查诊断、人工审核和导出完成，固定测试集和对照评测可复现。

# 20. 个人使用、小游戏制作与长期商业化愿景

## 20.1 将个人创作者作为长期真实用户

未来用户不仅可能是商业游戏团队，也可以包括独立开发者和个人创作者。用户本人可以成为工作台第一位真实使用者：用工作台生成和检查游戏设计资产，再借助游戏引擎、AI 编程工具和素材工具将设计转成可玩版本。个人制作过程中的失败、返工和用户反馈可以反向改进工作台。

## 20.2 两条可能的商业路径

| 路径 | 商业对象 | 可能价值 | 需要验证的关键问题 |
|---|---|---|---|
| 用工作台制作自己的游戏 | 玩家和游戏用户 | 通过原创游戏本身获取收入 | 玩法质量、用户获取、留存、广告/内购转化和发行成本 |
| 将工作台产品化 | 游戏团队、独立开发者、小型工作室 | 通过工具服务获得收入 | 高频使用、付费意愿、部署方式、支持成本和持续价值 |

两条路径共享部分技术底座，但商业模式、用户体验和成功指标不同。当前优先做出工作台并验证自己能否用它完成一个真实设计任务；等工具可用后，再选择一款小规模原创游戏做个人制作实验。不能把“能生成设计文档”直接等同于“能制作并盈利”。

## 20.3 从设计工作台到可玩游戏的后续能力

长期可能需要连接游戏引擎或轻量运行环境、代码生成/修改工具、素材生成工具、构建打包、运行测试、玩家反馈收集和数据分析。它们属于工作台外部协作能力或后续扩展，不要求第一版全部自研。

工作台的长期角色更像游戏生产的设计组织与质量控制中心，而不是必须亲自实现每一个生产环节的游戏引擎。

## 20.4 第一款个人游戏的原则

等首期工作台闭环完成后，再选择一款玩法循环清晰、范围小、可快速试玩的原创小游戏进行制作。先验证核心玩法是否有趣、能否完成、用户是否愿意继续玩，再考虑扩展关卡、广告、内购或其他商业化方式。第一款游戏的目标可以是积累真实制作经验和用户反馈，不预设必须盈利。

# 22. 风险、停止条件与变更纪律

## 22.1 主要风险与应对

| 风险 | 可能表现 | 应对 |
|---|---|---|
| 市场判断过早 | 因 JD 出现小游戏就假设所有小游戏团队有同样需求 | 通过 S2 还原真实工作流和返工案例 |
| 范围过大 | 同时做多个品类、自由画布、引擎、素材和发行 | 首期一个具体任务完整闭环 |
| 产品形态错误 | 直接照搬 ComfyUI，普通策划看不懂节点 | 原型测试固定流程视图与自由编排差异 |
| 与既有工具重叠 | 重新造剧情编辑器或简单流程图 | 聚焦设计生产工作流、领域规则、诊断和审核 |
| 生成结果不可靠 | 参数错误、配置缺失、内容冲突 | Schema、确定性规则、语义审查和人工确认 |
| 诊断不可信 | 只报错误，不给证据和位置 | 将判定、诊断、修复建议拆开验收 |
| 评测失真 | GT 由模型生成、保留集反复调参 | 人工 GT、开发/保留集隔离、记录版本 |
| 技术实现失控 | 过早引入复杂前端、多 Agent 或向量数据库 | 先用轻量架构验证，按瓶颈升级 |
| 版权与数据风险 | 复制现有游戏 IP 或未公开商业资料 | 使用原创素材和公开/脱敏资料 |
| 求职表达夸大 | 把未实现的引擎集成写成已经完成 | 明确实现范围、测试规模和限制 |
| 商业化预期过高 | 认为工具能生成游戏就一定能盈利 | 独立验证游戏留存、获客和变现 |

## 22.2 暂停或转向条件

- 经过有效访谈仍找不到重复出现的高价值设计问题。
- 现有工具已充分解决该问题，工作台无法形成可验证的增量价值。
- 用户不能提供任何可脱敏工作样例，也无法通过原创数据构造可信 GT。
- 关键质量判断只能依赖 LLM 自评，无法设计独立规则或人工评审。
- 实现价值必须依赖现阶段无法获得的商业游戏内部接口或完整引擎插件。
- 首期场景过于主观，无法定义输入、输出和可验证的质量标准。

触发暂停不等于项目失败，应回到 S4 调整场景或缩小功能范围，而不是继续扩大开发投入。

## 22.3 变更纪律

任何影响产品定位、首期场景、数据结构、Schema、RulePack、测试集、评测标准、开发范围或成功指标的变更，都必须记录：变更原因、证据来源、影响章节、影响页面、影响数据对象、影响测试集、是否改变验收标准、是否需要重新评审。未经确认，AI 编程助手不得擅自扩展业务功能或改变 GT。

每个阶段形成冻结版本。旧版本保留归档，不覆盖；新版本应有变更记录和回归结果。

# 附录 F：RPG 专属 Q001–Q013 规则资产（完整保留）

本附录恢复 v1.2.1 中的 RPG 任务规则定义，作为已有品类资产归档。Q001–Q013 不属于当前小游戏首期规则，不能直接应用于其他品类。只有在未来决定建设 RPG 模块时，才按对应 Schema 版本、RulePack 版本和测试集重新启用。

| 规则 ID | 检查内容 | 建议严重级别 | 典型失败示例 |
|---|---|---|---|
| Q001 | 任务必须且只能有一个起始节点 | 阻断 | 没有 start，或存在两个 start |
| Q002 | 所有节点 ID 唯一 | 阻断 | 两个节点共用 N03 |
| Q003 | 所有边的 from/to 节点均存在 | 阻断 | edge 指向不存在的 N99 |
| Q004 | 任务至少有一个 end 节点 | 阻断 | 所有路径都没有终点 |
| Q005 | 所有必需节点从 start 可达；仅检查图结构，不判断条件能否成立 | 阻断 | 隐藏结局节点没有任何结构路径连接 |
| Q006 | 所有 choice 至少有两个有效选项/出口 | 高 | 选择节点只有一条出口 |
| Q007 | 条件引用的变量必须定义 | 高 | 使用 clue_count 但未定义 |
| Q008 | 角色 ID、地点 ID、任务 ID 引用必须存在 | 阻断 | 对话引用未定义角色 |
| Q009 | 任务目标必须有完成条件 | 高 | 目标写“调查矿洞”，但没有完成判定 |
| Q010 | 失败/放弃路径需有明确状态或说明 | 中/高 | 失败后任务没有后续状态 |
| Q011 | 不能存在未解释的死路或软锁 | 高 | 某选择后无后续且未定义失败结局 |
| Q012 | 节点内容需满足 Brief 的必需元素 | 高 | 要求 3 个 NPC，实际只引用 2 个 |
| Q013 | 任务路径条件可满足性：路径上的状态条件是否存在合法取值组合使其同时成立 | 阻断 | 隐藏结局要求 clue_count ≥ 2，但全任务最多只能获得 1 条线索；或要求 secret_revealed 为假，而前置剧情必然揭示该秘密 |

## F.1 Q013 三层独立验收

| 能力层 | 定义 | 最低验收要求 |
|---|---|---|
| 状态可满足性判定 | 沿任务图搜索合法状态，输出 SAT/UNSAT/UNKNOWN | SAT 必须存在可复核路径；UNSAT 必须由完整搜索证明；触顶或规则未覆盖返回 UNKNOWN |
| 冲突原因定位 | 输出造成 UNSAT 的变量、约束、节点/边和证据 | 每条 UNSAT 至少提供一个可复核违反点；只输出“不可满足”不算诊断通过 |
| 修复建议生成 | 提供调整阈值、增加合法路径或修改前置条件等候选方案 | 首期只采用规则化模板；用户确认前不自动改写已锁定内容 |

## F.2 RPG 状态变量与搜索规范

变量只允许布尔值和有限整数域；每个变量显式声明类型、取值上下界和初始状态，不使用无界整数或引擎隐式默认值。条件在进入节点时判定一次；同一节点内存在状态变更时，按边上声明顺序执行完再判定出口条件。一条边允许包含多个原子状态变更动作（加减、置真、置假），每个动作单独可追溯。单次任务状态搜索上限默认 50,000 个状态；触顶即返回 UNKNOWN，记录触顶原因，不得返回 SAT 或当作通过。
