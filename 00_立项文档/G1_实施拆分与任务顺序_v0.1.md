## 一、G1 初始里程碑目标（重述，口径锁死）

**建设产品内部生成管线**：Brief → 模型调用 → Game Design Package → MechanicDSL / LevelData → 校验 → 接入 Runtime 运行 → 验证可玩性。全程档案留痕，双模型对照定主力。

**本阶段不是**：扩展产品方案文档、第二品类、自由画布、四界面 UI 完善、用 A/B/C/D 预置玩法匹配需求、把 Coding Agent 会话冒充产品内生成。

## 二、模块拆分（每模块独立验收、测完归档）

### M0 沙箱与安全边界（硬前置，最先做）

- **职责**：确定"生成产物如何被安全执行"的完整方案并落地为可测试的约束。
- **方案提案（待曦确认）**：
  1. **数据契约隔离**：生成产物只允许是**数据**（MechanicDSL / LevelData 的 JSON），管线以 `JSON.parse` 严格解析注入固定引擎，**全程无 eval / 无 Function / 无脚本标签注入**——生成的不是代码，是数据；这是本架构相对"生成自由代码"的最大安全优势；
  2. **校验前置**：任何产物进入运行前必须通过 Schema 校验器（结构、白名单、LIMITS、交叉引用），校验不过 = 不组装不运行；
  3. **运行隔离**：游戏页 iframe `sandbox="allow-scripts"`（无 allow-same-origin）+ CSP 禁外联——即使数据被构造出恶意内容，也无网络与同源权限；
  4. **注入样本测试**：构造含恶意内容（脚本标签、原型污染、超 LIMITS）的样本，验证校验器与运行隔离全部拦截。
- **输入**：前置 2 Schema / 前置 5 安全待办（Spike 报告 §11.5）。**输出**：安全边界决定记录 + 拦截测试通过。
- **验收**：曦确认沙箱方案；注入样本全部被拒；确认前**任何生成产物不得运行**。

### M1 生成管线核心（Brief → 模型 → 候选产物）

- **职责**：产品内调用 GLM 模型，把用户 Brief 变成结构化候选产物。
- **内容**：Prompt 工程（品类模板 + 原语词汇表 + 输出 JSON 约束 + 少样本指引）；模型适配层（GLM API 调用、模型名/Prompt 版本/参数登记）；输出解析与修正；**生成档案自动记录**（Brief、模型版本、Prompt 版本、原始输出、Token 消耗——曦指令 4 的前半）。
- **关键约束**：Prompt 只给原语词汇与 Schema 结构，**不提供 A/B/C/D 玩法先例作为可匹配模板**（生成≠匹配红线）；每次调用即建档，无档案的产物视为不存在。
- **验收**：给定一份新 Brief，管线产出 Schema 可解析的候选 MechanicDSL + LevelData，档案五件套齐备。

### M2 校验与验证链（拦截-重试循环）

- **职责**：候选产物 → 合法产物。
- **内容**：
  1. **Schema 校验器**：由 `tools_schema_check.py` 演进为产品级（结构/白名单/LIMITS/交叉引用，GT-1 前置结构闸门）；
  2. **规则检查**：Effect op 白名单、内建函数白名单、fx/overlay 枚举、表达式 LIMITS；
  3. **可解性验证（GT-1）**：混合路线第一步——先对四机制用手写模型回归（保护既有 8/8），新机制探索 **DSL 自动构建状态空间**；覆盖不了 → UNKNOWN/不支持，**禁止静默放行**；
  4. **有限诊断重试**：校验/可解性失败 → 错误分类 → 结构化错误信息回喂模型重试；重试次数与预算挂钩（22 元核销规则），超限即失败归档。
- **依赖**：M1 的档案制度；前置 3 GT v0.4 三值语义。
- **验收**：四机制八关回归全过（不退化）；注入的非法产物被对应层拦截；一次完整"失败→诊断→重试→通过"循环有档案。

### M3 Runtime 接入与运行验证（真实可玩）

- **职责**：合法产物 → 真实运行 → 可玩性证据。
- **内容**：
  1. **组装器**：固定引擎 + 数据注入 → 可运行游戏页（走 M0 隔离方案）；
  2. **GT-2a 结构化断言实装**：autoplay 逐步状态采集（vars/cellProps/entities 差分）、通关见证路径重放断言、机制专项测试路径（对应 GT v0.4 语义：候选路径重放通过才算真实通关证据）；
  3. **GT-3 核销清单首次实跑**：新 Brief 拆原子需求 → 逐条核销 → 人工签字（曦执行，机器只预填落点与证据）。
- **依赖**：M0 隔离方案 + M2 合法产物。**GT-2b 不在本阶段实装**（曦约束）。
- **验收**：至少一个真实新 Brief 全链路跑通：生成 → 校验 → 运行 → 重放断言全绿 → 核销清单签字；档案含最终游戏产物。

### M4 双模型对照与主力建议

- **职责**：GLM-5.3-Flash vs GLM-4.7 同批对照，出主力模型建议。
- **内容**：同一批 Brief 双模型执行（任务口径 38 个生成任务/模型，请求口径 182.4 次/模型期望）；按**生成质量（GT 通过层级）、重试率、成本（Token/金额）**三指标出对照报告；7+3 样本隔离执行（7×5 调优 → 冻结 → 3 验证 → 全量逐条核销）。
- **依赖**：M1–M3 管线贯通；前置 5 核销规则。
- **验收**：对照报告（三指标 + 建议）；全部请求在 22 元内、核销记录可查。

## 四、任务顺序与并行关系

```
M0 沙箱方案 ──确认──┐
                    ├→ M1 生成核心 → M2 校验验证链 → M3 Runtime 接入 → M4 双模型对照
技术依赖确认(§三) ──┘        │              │
   （1/2/3/4 可与 M0 并行确认）└─ Schema 校验器可在 M1 期间先行移植 ──┘
```

- 顺序硬约束：**M0 未确认 → M3 的任何运行都不开始**（沙箱硬前置）；M1 可在 M0 确认期间先行开发（只生成不运行）；
- M2 的 Schema 校验器移植可与 M1 并行；
- 每模块完成 → 测试 → 归档 → 向曦报验收，**不攒大包**。

## 六、预算与样本执行衔接

- 初始验证预算上限 **22 元**（不修改，按前置 5 核销规则执行）；
- 任务口径 38 个生成任务/模型；请求口径 182.4 次/模型期望、两模型合计 364.8 次期望——**超出预期或预算告警即停，报曦裁决**；
- 每次调用的 Token/金额实时入档案（M1 档案制度承载），M4 汇总对照。

## 七、本阶段明确不做

## 修订记录

- **v0.2（2026-11-12，曦审批 + 八条要求，进入编码）**：
  1. M0 沙箱原则认可，补齐：**原型污染防护、文本注入防护、iframe 消息通信校验、宿主页面隔离、CSP 限制**；安全测试区分**非法数据拦截**与**合法文本惰性展示**（不要求所有可疑文本一律拒绝）；安全测试通过前不得运行任何生成产物；
  2. 管线用 **Node.js**；**Python 手写 BFS 暂时保留**，不为统一语言重写；Node 产品校验器按 Schema v1.2.1 **重新实现**，旧 Python 静态核对脚本只作回归参考；
  3. GLM 优先**智谱官方 API**；密钥只放本地环境变量或受保护配置文件，**不进仓库、文档、前端、生成档案**；
  4. G1 只建本地 Web 服务 + 最小操作页，不完善四界面、不做自由画布、不做在线代码编辑；
  5. M2 自动求解器设**独立技术验证点**：已有机制双路线对照 + 新机制测试；不支持语义必须返回 UNKNOWN 或不支持；
  6. **每一次模型调用及失败、重试全部自动留档**，保证 M4 成本与重试率统计真实可追溯；
  7. M4 严格执行 7+3 隔离；22 元为**双模型初始验证总预算上限**；最终报告是**当前样本下的模型建议，不外推为普遍能力结论**；
  8. 保留 S4 产品边界：不加第二品类、不做预置玩法匹配、不把 Coding Agent 能力冒充产品生成能力。
  - 执行口径：本确认 = 实施拆分与技术路线；**M0 安全边界通过后才能执行生成产物**；M0–M4 按模块独立测试、归档、验收；**M1 只允许生成 JSON 数据，不得提前执行生成结果**。
