## 0. 产品究竟是什么（问题一的回答）

**一句话**：用户输入一个游戏创意或需求，AI 协同完成策划、玩法设计、关卡与内容生成、代码开发、资源整合、项目组装、运行测试和后续迭代，最终尽可能交付一个**可以运行、可以试玩、可以继续开发**的游戏。

**四个"不是"，钉死边界认知：**

| 不是 | 是 |
|---|---|
| 不是帮策划写策划案 / PRD / 关节文档 / 配置表的文档工具 | 设计资料只是**中间产物**，可运行游戏才是**交付物** |
| 不是检查配置、分析依赖、发现错误的质检工具 | 检查与诊断是管线内嵌的**质量关卡**和**迭代安全网** |
| 不是设计组织与质量控制中心（v2.0 §20.3 的旧提法） | 代码开发、组装、运行测试属于**产品范围**（通过编排外部工具与运行时模板实现，不必全部自研） |
| 不是小游戏专用工具 | 通用底座 + 品类模块；小游戏/休闲只是**首选切入方向**，塔防/模拟经营/RPG 逐步支持 |

**与 v2.0 的关系（诚实标注）**：
- 一致处：v2.0 §1.3"从游戏创意走向可玩的作品"、§20.1 个人创作者真实用户、§20.3"连接引擎/代码生成/素材工具"。
- 本次纠正点：v2.0 §20.3 把代码/组装/测试列为"长期可能的后续扩展"，并把工作台角色限定为"设计组织与质量控制中心"；**本次将其提升为最终产品的核心定义**。这是定位升级，需在 v2.1 修订记录（见 §9 修改清单）。
- 不变处：多品类架构、通用底座与品类模块分离、评测纪律、人工确认点——全部保留。

## 1. 从创意到可运行游戏：七个环节（问题二的回答）

| 环节 | 输入 → 输出 | 人工参与点 |
|---|---|---|
| **E1 需求与创意解析** | 创意/需求描述 → 结构化游戏概念（玩法循环、品类、范围、平台、风格约束） | 确认概念、砍范围 |
| **E2 游戏设计** | 概念 → 结构化设计对象（玩法规则、数值、关卡结构、任务图、UI 描述），落到品类 Schema | 设计编辑器里审改 |
| **E3 内容生成** | 设计对象 → 配置表、关卡数据、剧情与对话文本、简单素材（占位图/程序化生成） | 抽查、采纳/拒绝 |
| **E4 代码开发** | 设计对象 + 品类运行时模板 → 可执行游戏代码（生成参数填充与逻辑，而非从零裸写） | 代码编辑器审查、微调 |
| **E5 资源整合与项目组装** | 代码 + 素材 + 配置 → 组装成可运行项目（静态打包，web 优先） | 触发组装、看清单 |
| **E6 运行测试** | 可运行项目 → 冒烟测试结果、可玩性验证、错误日志 | **亲自试玩**（人工反馈是最高质量信号） |
| **E7 迭代** | 试玩反馈/测试错误 → 变更请求 → **影响分析（M5）→ 受影响对象重生成** → 回到 E3–E5 | 决定改什么、接受哪些连带改动 |

**关键认知**：E6→E7 的回路是产品成立的关键——游戏不是一次生成完的，是迭代出来的；**迭代时"改一个数、谁要跟着改"正是 M5 的主场**。检查能力从"设计期质检"升级为"迭代期安全网"。

## 2. 每个环节需要的能力（问题三的回答）

| 环节 | AI Agent | 工具 | 数据 | 技术要点 |
|---|---|---|---|---|
| E1 | 需求解析 Agent | Brief 模板表单（结构化优先，自由文本为辅） | 品类知识库 | LLM + Schema 约束输出；提取结果可回填编辑 |
| E2 | 设计 Agent（品类专属） | 游戏设计编辑器；RulePack 作为生成约束 | 品类 Schema、同类参考游戏拆解 | 结构化生成（先规划→人工确认→再细节，即 M4 思路） |
| E3 | 内容 Agent（关卡/文本/数值各一） | 生成后自动跑质量关卡 | 配置表结构、素材库（占位优先） | Schema 约束生成；**Q013 校验关卡/任务可通关、结构检查抓逻辑漏洞**——不可通关的 AI 关卡在出厂前拦下 |
| E4 | 代码 Agent | 代码编辑器；**品类运行时模板**（预置引擎骨架） | 模板 API 文档、代码样例库 | 模板填充式生成优于裸生成；沙箱执行验证语法 |
| E5 | 组装器（脚本为主，弱 AI） | 打包脚本、资源清单核对 | 资产命名规范 | web 端 = 静态文件组装，无安装成本 |
| E6 | 测试 Agent | 无头浏览器冒烟测试集；错误日志回收 | 每品类冒烟用例 | 运行期检查与设计期检查**分开计数**（两种不同性质的问题） |
| E7 | 变更影响 Agent（= M5 已有能力） | 确认单、设计编辑器 | 引用关系图、历史版本 | 影响面 → 触发重生成范围 → 人工确认后重跑 E3–E5 |

## 3. 四个界面的关系（问题四的回答）

```
工作流画布（指挥层）──调度──▶ Agent 执行各环节
      │ 产物落地                    │
      ▼                            ▼
游戏设计编辑器（对象层）     代码编辑器（对象层）
  结构化设计对象              生成的游戏逻辑代码
      │                          │
      └──────────┬───────────────┘
                 ▼
        游戏预览运行环境（验证层）
        组装 → 试玩 → 冒烟测试
                 │ 反馈（人工 + 自动）
                 ▼
          回到工作流画布，触发 E7 迭代
```

- **画布与编辑器严格区分**（曦明确要求）：画布回答"AI 正在做什么、进行到哪、哪里等我确认"；编辑器回答"我的游戏长什么样、数值对不对、关卡怎么改"。一个是过程视图，一个是产物视图。
- MVP 阶段画布按 v2.0 §8.4 走**固定流程视图**（选模板→填需求→运行→看结果），自由编排是长期版本且需用户研究证明。
- 预览运行环境在 web 品类下就是浏览器本身——这是选 web 小游戏做切入的技术理由：零安装、试玩即测试。

## 5. 第一阶段 MVP 应该怎样设计（问题六的回答）

**核心命题：MVP 必须至少一次端到端打通"创意 → 可运行游戏"，哪怕游戏极小、品类极窄。只做检查器永远无法证明"生成游戏"这个方向。**

### 5.1 MVP 提议（垂直切片，待曦拍板）

- **品类**：web 单屏小游戏（放置/点击类优先——与已有多余认知兼容、运行时模板最简单、浏览器即预览环境）
- **闭环**：固定 Brief 表单（玩法参数/目标/风格）→ 设计对象生成（Schema 约束）→ **运行时模板 + 参数填充生成代码** → 静态组装 → 浏览器试玩 → 改一个参数完成一次带影响分析的迭代
- **人工操作 ≤ 5 步**：填 Brief → 确认设计 → 触发生成 → 试玩 → 提迭代

### 5.2 MVP Must（每条可验收）

| # | 内容 | 验收标准 |
|---|---|---|
| V-1 | 品类运行时模板 1 个（HTML5/JS） | 模板本身可玩、参数化程度足够支撑生成 |
| V-2 | E1–E5 管线人工触发打通 | 从 Brief 到浏览器里跑起来，中途不写一行代码、不开命令行 |
| V-3 | 至少 1 个真实可玩产物 | 非开发者（曦本人即可）试玩后判定"是游戏"而非 demo 页面 |
| V-4 | 质量关卡内嵌管线 | 生成产物 100% 通过 Schema 校验 + RulePack + 任务可达性判定；不可通关产物被拦截并给诊断 |
| V-5 | 一次迭代闭环 | 改一个设计参数 → 影响分析列出连带改动 → 确认后重生成 → 试玩验证生效 |
| V-6 | 过程可视化 | 画布固定视图能看到每个环节的状态与产物入口 |

### 5.3 证明标准（面向"产品方向成立"）

> 一个没写过代码的人，用这个工作台在半天内拿到一个可试玩的小游戏，并且完成了一次"改需求→看影响→重新生成→试玩确认"的迭代。做到，方向即验证；做不到，知道卡在哪一环，也是有效结论。

### 5.4 MVP 明确不做

自由画布、多品类、美术资产真生成（占位图/程序化素材即可）、自动发布、复杂玩法（物理/联机）、代码全裸生成。

## 7. 风险（新架构新增的）

| 风险 | 应对 |
|---|---|
| 代码生成质量不可控 | 模板填充式生成（不是裸写）；沙箱执行验证；模板越窄越稳 |
| 运行时模板成为新瓶颈（每品类一份） | 品类模板也算"品类模块"的一部分，与 Schema/RulePack 同等对待；G3 验证其可复用性 |
| 范围蔓延回"造引擎" | §5.4 Not list + 引擎协作走外部工具（v2.0 §20.3 保留有效） |
| "生成物评测"缺 GT | 可玩性用人工试玩判定 + 冒烟测试；质量关卡用变异评测；不宣称"生成的游戏好玩" |
| 检查器已有投入被浪费的担忧 | §4 归位表：每一项都有 E3/E7 的明确岗位，无一废弃 |
