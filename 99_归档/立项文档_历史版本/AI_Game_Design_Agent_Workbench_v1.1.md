# 1. 项目结论与立项卡

## 1.1 最终建议

建议正式项目名称为“AI Game Design Agent Workbench｜AI 游戏策划与研发工作台”。名称采用多品类中性表达，不把产品永久限定在 RPG。产品架构采用“通用能力底座 + 游戏类型专属模块”：通用底座负责项目知识管理、Brief 解析、Agent 编排、工具调用、人工审核、版本管理和导出；不同品类通过独立数据结构、规则集和评测集适配。首期只选择 RPG 任务与剧情策划作为垂直验证场景，做深一条从策划 Brief 到结构化任务包的闭环。

这个定位比单纯的 AI 剧情生成器更接近游戏研发生产力工具，也比一开始做全品类平台或完整 AI NPC 更可控。它同时展示专业工作台设计、Agent 任务规划、知识与上下文管理、工具调用、确定性规则引擎、LLM 语义评估、人工审核和结构化交付能力。

## 1.2 项目立项卡

| 项目项 | 当前定义（待调研验证） |
| --- | --- |
| 目标用户 | 总体面向游戏策划与研发团队；首期核心用户为 RPG 任务策划/剧情策划，次级用户为主策划、技术策划、程序和 QA。 |
| 核心任务 | 把策划 Brief 转成可检查、可编辑、可交付的结构化设计产物；首期产物为 RPG 支线任务包。 |
| 核心痛点假设 | 策划需求、项目设定和历史内容分散；任务结构、分支条件和交付字段容易遗漏；AI 生成内容难验证；反复修改难追踪。以上均为待访谈验证的假设。 |
| 产品价值假设 | 减少从 Brief 到初版设计产物的整理时间；降低结构错误与设定冲突；提高策划审核和跨岗位交接效率。 |
| 主要输出 | 首期为任务设计说明、节点/分支结构、角色引用、对话草稿、校验报告、审核记录和 JSON/CSV/Markdown 导出；其他品类使用专属产物模板。 |
| 核心差异化 | 通用 Agent 底座 + 品类专属 Schema/规则/评测；不是通用写作网站，也不是替代现有游戏引擎或叙事编辑器。 |
| MVP 核心用户 | 单一项目、单人策划工作流；暂不实现多人协作权限和多品类全量功能。 |
| 成功定义 | 至少 3 位目标用户/相关从业者验证具体问题；完成一个端到端可运行场景；固定测试集可重复运行；与基线方案对比并展示有据可查的改善。 |

## 1.3 项目定位边界

> **不要把产品做成什么**
> 不做一个号称支持所有游戏品类的万能策划平台；不做完整游戏引擎；不做首期实时语音 NPC；不做自动生成完整商业游戏；不做美术资产生产平台；不做完整 articy:draft/Unity/Unreal 替代品；不声称已经接入商业游戏研发流水线。

首期定位为“游戏策划工作流中的 AI 助手与质量检查层”。产品可预留多品类适配接口，但首期仅实现 RPG 任务策划模块。未来可与 Twine、Ink、articy:draft 或游戏引擎交换结构化内容；在没有真实接口验证前，只实现通用 JSON/CSV/Markdown 导出，不宣称原生集成。

## 1.4 多品类产品架构：通用底座与专属模块

| 产品层 | 通用/专属 | 职责 | 首期范围 |
| --- | --- | --- | --- |
| 项目与知识管理 | 通用 | 项目、资料、版本、来源、术语、权限边界。 | 实现基础能力。 |
| Brief 与 Agent 编排 | 通用 | 需求解析、任务规划、工具调用、状态管理、人工确认、错误恢复。 | 围绕 RPG 任务链路实现。 |
| 质量与交付 | 通用框架 + 专属规则 | 校验报告、人工审核、版本差异、导出。 | 实现通用问题模型 + RPG 规则集。 |
| RPG 模块 | 品类专属 | 任务、角色、地点、剧情节点、分支、对话、任务状态。 | 完整实现。 |
| MOBA 模块 | 品类专属 | 英雄、技能、装备、地图目标、战斗规则、平衡约束。 | 仅做后续概念验证。 |
| FPS 模块 | 品类专属 | 地图区域、出生点、攻防路线、武器、模式目标、视线与平衡约束。 | 仅做后续概念验证。 |

> **品类边界说明**
> RPG、MOBA、FPS 是不同游戏类型/玩法品类；GBA 是掌机游戏平台，不是与 RPG/MOBA/FPS 并列的游戏类型。同一款 GBA 游戏也可能属于 RPG、动作或策略等类型。产品扩展应按游戏设计对象和规则模型划分，而不是把游戏平台当成品类模块。

多品类不是首期功能承诺，而是产品架构方向。首期只把 RPG 的一条任务策划链路做深；只有当首期闭环完成且有第二种品类的用户证据时，才通过独立 Schema、规则集和小规模概念验证扩展 MOBA 或 FPS。不得仅凭界面上有一个“游戏类型选择器”就声称实现了多品类支持。

## 2.3 一个重要竞品发现：不能重做通用叙事编辑器

articy:draft 已经具备 Flow Editor、游戏对象数据库、变量与脚本、分支剧情组织、检查工具、JSON/Excel/Unity/Unreal 导入导出，并提供 AI 辅助对话与文本生成能力。[R6] Ink 是面向游戏的叙事脚本语言和编辑器，支持分支叙事、运行预览、JSON 导出及 Unity/Unreal 集成。[R7] Twine 是非线性互动故事创作工具，支持变量和条件逻辑。[R8]

> **产品差异化结论**
> 不要把卖点写成“提供角色库、剧情节点编辑器、分支图、导出”——这些能力已经存在。应把差异化放在“从自然语言策划 Brief 到结构化任务包的 Agent 工作流 + 项目设定依据 + 自动校验与错误解释 + 人工审核闭环”。并把现有工具视为潜在协作对象，而非必须取代的竞品。

## 2.4 竞争产品研究要回答的问题

- Articy:draft：用户如何管理角色、实体、任务、对话和分支？已有检查能发现哪些错误？AI 扩展覆盖到什么程度？它的目标用户和团队协作能力是什么？
- Ink / Inky：作者如何表达分支、变量、条件和可运行预览？哪些内容必须使用脚本，哪些可以通过图形工具管理？
- Twine：低门槛互动叙事创作的优势在哪里？其结构化导出和条件逻辑对独立创作者意味着什么？
- 通用大模型：用 ChatGPT/其他模型直接写任务时，哪些工作仍由策划手工完成？生成内容如何转成可执行配置？如何验证正确性？
- 工作流工具：现有策划团队是否已经使用表格、文档、Jira/飞书/Notion/Perforce 等工具？哪些工具是事实上的工作入口？

# 3. 产品定位、用户与价值主张

## 3.1 主要用户画像

| 用户 | 主要工作 | 关心的结果 | 首期是否服务 |
| --- | --- | --- | --- |
| 游戏策划 / 设计师 | 定义玩法、任务、角色、技能、地图或关卡等设计对象。 | 需求清楚、规则完整、产物能进入评审和研发。 | 总体目标用户；首期聚焦 RPG 任务策划 |
| 剧情策划 / 叙事设计 | 维护世界观、角色背景、事件时间线、对话和剧情分支。 | 设定一致、人物不 OOC、内容可追踪。 | 首期核心协作用户 |
| 主策划 / 内容负责人 | 评审设计方案、控制质量、协调上下游。 | 审核效率、版本可追溯、风险可见。 | 首期审核角色 |
| 程序 / 技术策划 / QA | 理解设计数据、实现规则和状态、验证边界条件。 | 结构明确、字段稳定、错误可定位。 | 首期下游接收方，不做其完整工作台 |
| 其他品类策划（MOBA/FPS） | 设计英雄技能、战斗规则、地图与模式目标等。 | 机制无冲突、约束清楚、设计可验证。 | 后续扩展研究对象 |

## 3.2 用户工作任务（JTBD）

当游戏策划收到一份模糊或不完整的设计需求时，他希望结合当前项目的设定、规则和历史设计，产出结构化、可检查、可修改、可交付的设计方案，减少在多个文档、表格和聊天窗口之间手动整理的工作。首期将这一 JTBD 限定到 RPG 任务策划：输出任务节点、触发条件、分支、对话和验收规则。

## 3.3 首期核心价值主张

> **一句话定位**
> 用可扩展的 AI Agent 工作流辅助游戏策划生产结构化设计内容，并对结果进行规则校验、质量评估和人工审核；首期聚焦 RPG 任务设计包。

价值不应只用“生成速度快”表达。需要同时验证：初稿准备时间是否缩短、结构性错误是否减少、设定/规则冲突是否更早发现、交付给下游岗位的信息是否更完整。通用能力指标可以跨品类比较，但内容质量指标必须按 RPG、MOBA、FPS 的不同规则分别定义。没有用户测试前，以上只能写作价值假设。

## 3.4 多品类适配原则

| 能力 | 是否通用 | 需要品类化的部分 |
| --- | --- | --- |
| 项目资料与版本管理 | 通用 | 资料类型和必填元数据可以扩展，但内容字段不同。 |
| 需求解析与 Agent 编排 | 通用框架 | 各品类 Brief 字段、工具链和任务步骤不同。 |
| 工具调用、人工确认、运行日志 | 通用 | 被调用的工具和审批节点由具体工作流决定。 |
| 结构化输出与 Schema 校验 | 通用机制 | Quest、Hero/Skill、Map/Mode 使用不同 Schema。 |
| 规则检查 | 框架通用、规则专属 | RPG 检查任务图；MOBA 检查技能/状态规则；FPS 检查地图与模式约束。 |
| 语义质量评测 | 方法通用、标准专属 | 角色/剧情一致性、技能描述清晰度、地图玩法合理性需要不同 GT。 |

后续扩展必须遵循“新建品类 Schema + 新建规则集 + 新建测试集”的方式。不能把 RPG 任务节点字段直接套在 MOBA 技能或 FPS 地图上，也不能声称一套指标可以衡量所有游戏设计内容。

# 4. 多品类业务知识补课清单

你不需要先成为资深游戏策划，但必须能看懂至少一个首期品类的策划输入、产出和规则，同时理解 RPG、MOBA、FPS 的设计对象差异。学习目标是能画出业务流程、解释数据字段、判断常见错误，而不是泛泛看完游戏设计课程。RPG 首期需要深入；MOBA/FPS 先建立认知地图，暂不要求达到专业策划水平。

| 学习主题 | 必须理解的概念 | 学习后要产出的东西 | 掌握标准 |
| --- | --- | --- | --- |
| RPG 任务与剧情结构（首期深入） | 任务目标、前置任务、触发条件、步骤、目标、分支、失败、奖励、结束状态。 | 一页任务结构拆解图、原创 Quest Brief。 | 能把一条支线任务拆成状态节点和条件。 |
| 角色与叙事（首期深入） | 身份、动机、目标、关系、知识边界、时间线、角色弧光、叙事视角。 | 角色卡、知识边界表、事件时间线。 | 能判断角色是否说出不可能知道的信息。 |
| MOBA 设计对象（认知补课） | 英雄定位、技能机制、冷却/消耗、状态效果、装备、地图目标、团队协作与平衡。 | 一张英雄技能/机制结构图。 | 能解释技能字段和机制约束；不负责做数值平衡裁决。 |
| FPS 设计对象（认知补课） | 地图区域、出生点、攻防路线、模式目标、武器属性、视线、节奏和公平性。 | 一张地图目标与路径示意图。 | 能解释地图/模式设计对象；不负责专业竞技平衡。 |
| 游戏策划交付物 | 任务设计文档、对话脚本、玩法方案、技能/地图配置表、流程图、验收条件和修改记录。 | 一份首期任务包和一份其他品类概念样例。 | 知道不同策划内容最终交付给谁、以什么结构交付。 |
| 游戏研发协作 | 策划、程序、TA、美术、QA 的分工；评审、实现、联调、验收。 | 从设计 Brief 到研发交付的泳道图。 | 知道哪些内容由策划决定，哪些必须由程序/QA 确认。 |
| 设计工具基础 | articy:draft、Ink/Inky、Twine，以及 Unity/Unreal 编辑器和团队文档/表格工具。 | 工具对比记录。 | 能解释本产品与现有工具的边界，不声称要替代它们。 |

## 4.1 建议的学习顺序

- 先选一款你熟悉的 RPG，拆解一条 20–40 分钟的支线任务，记录接取、推进、分支、失败和结束。不要复制游戏原文、角色或受版权保护的设定。
- 再用原创设定重做一条简单任务，尝试用 Twine 或 Ink 做最小分支原型，理解任务图和变量。
- 用一到两次专题学习了解 MOBA 的英雄/技能/装备设计对象，以及 FPS 的地图/模式/武器设计对象；目标是会读懂设计表，不是立即设计完整英雄或地图。
- 研究 articy:draft、Ink、Twine 与 Unity/Unreal 编辑器的分工，区分内容设计工具、脚本工具和游戏引擎。
- 最后才设计 AI Agent：明确哪些步骤适合 AI，哪些必须由品类规则程序执行，哪些必须由人审核。
- 术语说明：GBA 是游戏平台/掌机平台，不是与 RPG、MOBA、FPS 并列的游戏类型；若未来做复古掌机项目，应按实际玩法类型归类。

# 6. 阶段一：招聘市场与目标岗位调研

## 6.1 需要收集多少 JD

先收集 10–15 条高相关 JD，优先最近 3–6 个月发布或更新的岗位。来源包括 BOSS 直聘、猎聘、拉勾、腾讯/网易/米哈游/三七互娱等企业官网、招聘聚合平台。每条 JD 保存截图或文本、链接、采集日期和页面状态。

## 6.2 必须覆盖的岗位类别

- 游戏研发 Agent 产品策划 / AI 游戏研发平台产品经理。
- 游戏策划工具 / 编辑器 / 内容生产平台产品经理。
- AI NPC / AI 角色 / AI+UGC 产品策划。
- AI 游戏内容生产 / 美术生产 / 玩法创作平台产品经理。
- AI 游戏测试、质量评测或研发效率工具产品岗位。
- 通用企业级 Agent / AI 工作流 / AI SaaS 产品经理，作为第二条求职出口对照。

## 6.3 JD 矩阵字段

| 字段 | 填写内容 |
| --- | --- |
| 公司与职位 | 公司、岗位名称、城市、招聘类型。 |
| 时间与来源 | 发布日期/更新日期、采集日期、链接、官方/转载、是否能确认在招。 |

## 6.4 分析方法

把职位要求拆成“硬门槛”和“能力要求”。硬门槛如 3 年产品经验、UE5 实操或游戏行业经历，不能靠作品集完全替代；能力要求如 Agent 流程设计、知识库、评测、专业用户工具设计，可以通过项目提供部分证据。最终不要用“岗位匹配 80%”这类没有权重依据的数字；用差距清单分成可补、需实践、暂不可替代三类。

## 6.5 本阶段完成标准

- [ ] 完成 10–15 条 JD 原文收集，至少 5 条来自游戏公司或游戏工具公司。
- [ ] 区分产品岗、策划岗、研发工程岗，不把 AI Agent 开发工程师当成产品经理 JD。
- [ ] 整理出 5–7 个反复出现的能力要求，并标注出现在哪些职位。
- [ ] 把目标岗位分成冲刺、主攻、备选三档。
- [ ] 明确本项目要证明的 3–4 项能力，不试图满足所有 JD。

# 7. 阶段二：游戏策划业务调研

## 7.1 调研目标

这一阶段不是证明“游戏策划需要 AI”，而是比较不同品类策划人员在设计流程中具体在哪些步骤花时间、容易出错、反复返工，以及现有工具无法解决什么问题。重点先验证 RPG 任务策划，但必须把它与其他候选场景比较，避免因为产品最初想法而提前锁定品类。

## 7.2 访谈对象

| 对象 | 建议人数 | 目的 |
| --- | --- | --- |
| RPG 任务/剧情策划 | 2–3 人 | 首期核心样本：了解 Brief、任务节点、分支、审核和返工。 |
| 独立游戏开发者/小团队策划或游戏工具产品用户 | 1–2 人 | 了解实际工具链、内容生产和 AI 辅助需求。 |
| MOBA/FPS 策划或技术策划/程序/QA（可选） | 1–2 人 | 了解其他品类的设计对象差异，或任务数据如何进入研发实现。 |

如果暂时联系不到商业游戏团队，可以访谈独立游戏开发者、Game Jam 参与者、叙事设计学生或有游戏设计实践的人；在报告中明确对象类型和样本局限。MOBA/FPS 访谈用于判断未来是否值得扩展，不要把少量体验反馈当成该品类的完整业务需求。

## 7.3 访谈前准备

- [ ] 准备一页项目介绍，只说明研究主题，不展示完整产品方案，避免诱导对方赞同。
- [ ] 先问对方实际做过的最近一个任务，不问“你觉得 AI 能不能帮你”。
- [ ] 征得同意后记录访谈；不记录公司机密、未公开剧情、商业数据或个人敏感信息。
- [ ] 尽量请对方展示可公开或脱敏的任务文档、流程图、配置表示例。
- [ ] 访谈后 24 小时内整理事实、原话、推断和待验证事项。

## 7.4 访谈问题清单

| 主题 | 问题 |
| --- | --- |
| 角色与场景 | 你目前负责哪类游戏和策划工作？最近一次完整设计任务/角色/技能/地图内容，从接到需求到交付经历了哪些步骤？ |
| 输入资料 | 设计前通常会拿到哪些资料？世界观、角色卡、任务需求、技能规则、地图约束和历史版本分别在哪里维护？ |
| 核心产物 | 最终需要交付哪些文档、表格、流程图或配置？下游程序、QA、TA 或主策划如何使用？ |
| 返工与错误 | 最近一次返工是什么原因？例如设定冲突、任务条件不完整、技能机制冲突、地图路径问题、字段遗漏或上下游理解不一致？ |
| 频率与成本 | 这些问题多久出现一次？大约造成多少轮修改或时间损耗？请给最近一次实际例子。 |
| 现有工具 | 目前用哪些工具管理剧情、角色、任务和配置？哪些地方仍要手工复制、对照或检查？ |
| AI 边界 | 哪些内容可以让 AI 初稿生成？哪些必须由策划决定？哪些错误一旦进入游戏会造成高成本？ |
| 审核与交付 | 怎样判断一份任务方案可以交付？谁审核？需要哪些字段、引用、版本和验收条件？ |
| 试用意愿 | 若工具只解决一个问题，你最愿意先试哪个？什么结果会让你继续使用？ |

## 7.5 痛点优先级判定

每个痛点从发生频率、处理耗时、错误影响、现有工具缺口、AI 可处理程度五个维度做 1–5 分初评。评分只能帮助排序，不能替代访谈证据。优先选择“频率高、耗时明显、错误可被明确检查、输入资料可获得”的场景。

## 7.6 本阶段通过条件

- 至少完成 3 次有效访谈；若访谈对象不是真实商业策划，需在报告中明确样本局限。
- 至少有 2 个痛点在 2 名以上对象中重复出现，或由一个高可信工作样例充分证明。
- 至少获得一份可公开/脱敏的任务交付物样例，或通过访谈重建出可核验的字段清单。
- 确认用户愿意使用的最小功能，不以“听起来很酷”作为需求证据。

> **停止条件**
> 如果调研发现 RPG 任务策划的主要痛点已被现有工具充分解决，或无法找到目标用户验证流程，就不要为了原定方案硬做 RPG。返回 S4，根据其他品类或游戏研发环节的证据重新选择一个首期垂直场景。

# 8. 阶段三：竞品与替代方案分析

## 8.1 必须研究的工具

| 工具/类别 | 重点观察 | 要回答的问题 |
| --- | --- | --- |
| articy:draft | Flow、对象数据库、脚本变量、对话、检查工具、团队协作、导入导出、AI 扩展。 | 它已经解决了什么？AI 创作和检查覆盖哪里？你不应该重复造什么？ |
| Ink / Inky | 叙事脚本语法、分支、变量、预览、错误检查、JSON 导出、引擎集成。 | 结构化叙事怎样表达？程序如何消费？ |
| Twine | 节点组织、变量与条件、故事预览、发布方式。 | 低门槛创作工具的体验优势是什么？ |
| 通用大模型 | 直接输入 Brief 生成任务、角色和对话。 | 相比直接用模型，本产品增加了哪些稳定、可控、可复用能力？ |
| Unity / Unreal 编辑器与工具链 | 编辑器、可视化脚本/蓝图、资源与项目管理、调试和验证方式。 | 哪些是引擎已有能力？产品应输出什么结构，避免假装替代引擎？ |
| 表格/文档/协作工具 | 角色表、任务表、玩法表、配置表、需求文档、版本记录和审批。 | 用户是否需要新平台，还是需要嵌入现有工具的 AI 辅助层？ |
| AI 美术/内容生成工具 | 图像、3D、音频、视频生成与批量生产流程。 | 本项目是否要进入资产生产？首期明确不做，先识别集成边界。 |

## 8.2 竞品分析维度

- 核心用户与使用场景。
- 输入和输出的内容类型。
- 是否支持结构化角色/任务/实体数据。
- 是否支持分支、条件、变量和可运行预览。
- 是否有内容检查、错误定位和版本能力。
- 是否有 AI 辅助生成，用户能否控制生成范围。
- 导入导出格式与游戏引擎连接方式。
- 团队协作、权限和审阅能力。
- 免费/付费版本及商业模式（如需商业化研究再做，不作为作品集 MVP 前提）。

## 8.3 初步差异化方向

产品不要宣称取代 articy、Ink、Twine、Unity 或 Unreal。建议定位为“游戏策划流程中的 AI Agent 辅助层”：从自然语言 Brief 启动任务，读取项目知识和品类规则，生成符合专属 Schema 的设计产物，自动执行结构校验并给出语义问题证据，再由策划批准并导出/交接到现有叙事工具、表格或研发流程。首期只验证 RPG 任务包，其他品类需重新研究规则与数据结构。

# 9. 阶段四：首期垂直场景与原创内容设计

## 9.1 产品支持多品类架构，MVP 只实现 RPG

本项目定位采用多品类架构，但 MVP 不做多品类全量支持。当前候选首期场景为 RPG 支线任务策划，原因是其内容对象（角色、地点、任务节点、分支、结局）相对容易构造原创数据，并能用确定性规则检查结构。但这一选择仍需 S2 用户调研与 S4 决策闸门确认。若证据不支持 RPG，必须调整，不得仅因已写入方案而继续。

原创演示场景暂定为“雾隐镇失踪事件”。它只是 MVP 测试项目，不代表真实商业游戏业务规范。应避免复用现有游戏的角色、世界观、剧情对白、地图和美术资产。

| 内容资产 | MVP 建议数量 | 说明 |
| --- | --- | --- |
| 世界观条目 | 10–15 条 | 地理、历史、势力、基础规则、时间线、重要事件。 |
| 角色 | 3–4 名 | 每名角色有身份、目标、秘密、知道/不知道的事实、关系。 |
| 地点 | 2–3 个 | 小镇、旧矿洞、诊所等。 |
| 任务 | 1 条完整支线 | 从接取到完成，含至少 2 个分支和 1 个隐藏结局。 |
| 任务节点 | 10–15 个 | 控制复杂度，覆盖对话、选择、目标、奖励、结束。 |
| 对话片段 | 8–12 组 | 用于人设和知识边界测试。 |
| 异常案例 | 初期 15–20 个 | 设定冲突、知识越界、节点断路、条件缺失、ID 引用错误等。 |

## 9.2 RPG 首期内容资产规模

- 00_项目总览：游戏类型、玩家身份、世界观基调、任务体验目标。
- 01_世界规则：时间、地点、势力、科技/魔法限制、重要事件。
- 02_角色档案：身份、动机、关系、公开信息、秘密、已知事实、未知事实。
- 03_地点档案：位置、功能、出入口、可交互对象。
- 04_任务档案：任务 ID、目标、前置、节点、分支、失败条件、结束条件、奖励。
- 05_术语表：专有名词、别名、不可随意改写的定义。
- 06_版本记录：设定版本、变更原因、受影响的任务和角色。

## 9.3 原创世界观资料包结构

- 00_项目总览：游戏类型、玩家身份、世界观基调、任务体验目标。
- 01_世界规则：时间、地点、势力、科技/魔法限制、重要事件。
- 02_角色档案：身份、动机、关系、公开信息、秘密、已知事实、未知事实。
- 03_地点档案：位置、功能、出入口、可交互对象。
- 04_任务档案：任务 ID、目标、前置、节点、分支、失败条件、结束条件、奖励。
- 05_术语表：专有名词、别名、不可随意改写的定义。
- 06_版本记录：设定版本、变更原因、受影响的任务和角色。

## 9.4 Quest Brief 输入模板

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 任务目标 | 玩家最终要完成什么。 | 查明雾隐镇失踪事件的直接原因。 |
| 玩家身份/等级 | 玩家在世界中的身份、能力和阶段。 | 刚抵达小镇的调查者。 |
| 任务类型 | 主线/支线/教学/探索等。 | 支线、调查。 |
| 推荐时长 | 目标游玩时间。 | 15–25 分钟。 |
| 出场角色 | 必须出现的 NPC。 | 药剂师、巡逻队员、矿工。 |
| 必须包含 | 不可缺少的剧情节点或信息。 | 3 条线索、2 次选择、隐藏结局。 |
| 禁止事项 | 不能出现的设定或结果。 | 药剂师不能知道矿洞深处的秘密。 |
| 前置条件 | 接取任务前要满足什么。 | 完成初次到访小镇的引导任务。 |
| 成功/失败条件 | 如何完成或失败。 | 收集两条关键线索并选择提交对象。 |
| 奖励/后果 | 任务结束后的变化。 | 获得线索、改变 NPC 关系或开放后续任务。 |

## 9.5 输出任务包

- 任务概览：任务名、目标、背景、推荐时长、前置条件。
- 任务结构：节点 ID、节点类型、进入条件、执行内容、退出条件、目标节点。
- 分支定义：玩家选择、条件表达式、变量变化、后续路径。
- 角色使用：参与角色、出场节点、该角色允许知道的信息。
- 对话内容：说话人、台词、选项、选项条件、后续节点。
- 奖励与后果：奖励、Flag 变化、关系变化、后续任务解锁。
- 验收标准：任务可接取、可推进、可完成、分支可达、无未定义引用。

# 10. 阶段五：产品需求与交互设计

## 10.1 MVP 功能范围

| 模块 | 必须实现 | 暂不实现 |
| --- | --- | --- |
| 通用项目与知识库 | 创建项目并配置 genre；导入/编辑 Markdown、TXT、CSV 资料；维护来源、版本和术语。 | 复杂权限、多项目企业管理、海量知识图谱。 |

| 知识检索 | 按角色/地点/事件/任务检索设定并展示引用。 | 大型向量数据库、复杂知识图谱。 |
| RPG 任务规划 | 生成任务大纲、节点、分支和前置条件；策划先审核大纲。 | 自动设计完整商业游戏主线。 |
| RPG 内容生成 | 按节点生成任务说明、目标、NPC 对话和选项。 | 批量生成整款游戏文本、自动配音。 |

| 语义检查 | 检查设定冲突、角色知识越界、时间线矛盾，返回证据与建议。 | 完全自动裁决剧情好坏或文学质量。 |
| 人工审核与版本 | 问题列表、采纳/修改/忽略、版本记录；锁定已确认内容。 | 多人实时协作、复杂审批权限。 |
| 导出 | Markdown 任务文档、JSON 结构数据、CSV 节点表。 | 宣称已原生集成 Unity/UE/Articy。 |

## 10.2 页面清单

| 页面 | 核心区域 | 用户动作 | 验收点 |
| --- | --- | --- | --- |
| 项目首页 | 项目、游戏类型、启用模块、资料完整度、最近设计产物和版本。 | 创建/打开项目、选择已支持的品类模板。 | 显示当前项目类型；未实现品类标为规划中。 |
| 项目知识库 | 资料列表、类型、来源、版本、标签和内容详情。 | 新增/编辑/检索。 | 每条资料有 ID、类型和来源。 |
| 新建设计 Brief | 根据品类加载对应输入字段；首期为 Quest Brief。 | 填写并提交需求。 | 缺少关键字段时先澄清，不直接生成。 |
| Agent 执行页 | 当前阶段、输入、检索引用、工具调用、待确认点。 | 查看过程、批准/退回。 | 用户知道 AI 正在做什么及为什么暂停。 |
| 设计产物编辑页 | 首期显示 RPG 任务节点图、节点详情、条件和变量。 | 编辑节点、连线、保存。 | 能看出任务路径和节点关系；底层接口不依赖单一品类。 |
| 质量检查页 | 结构错误、语义疑点、来源证据、严重度。 | 修正/忽略/标记待人工判断。 | 问题可定位到节点和设定来源。 |
| 审核与版本页 | 版本差异、修改人、变更原因、状态。 | 确认、退回、生成新版本。 | 可还原重要版本。 |
| 导出页 | 导出格式、数据预览、校验结果。 | 下载 JSON/CSV/Markdown。 | 导出数据可再次解析。 |

## 10.3 Agent 必须设置的人工确认点

- 需求解析后：策划确认 Brief 被正确理解，尤其是必需节点、分支数量和禁止事项。
- 任务结构生成后：策划确认流程图、前置条件、分支和结束条件，再生成大段对话。
- 语义检查发现高风险冲突时：不得自动改写已确认设定，必须请求用户确认。
- 导出前：必须通过结构校验；如果仍有高严重度问题，要求用户确认或阻止导出。
- 已被用户锁定的节点或角色设定：后续重新生成不能静默覆盖。

# 11. 阶段六：Agent 工作流与技术方案

## 11.1 推荐的最小架构

首版采用“单一工作流编排器 + 确定性工具 + LLM 调用 + 人工审核 + 品类适配器”。不要一开始设计多个自主 Agent 互相协商。多 Agent 会增加调试、状态同步和评测成本，只有在单一编排器的职责边界明显无法管理时才拆分。通用编排器不直接写死 Quest 逻辑，品类专属 Schema、提示词和校验规则通过 RPG Adapter 接入。

```text
用户 / 游戏策划
   │
   ▼
产品工作台（项目、品类模板、Brief、设计产物、审核）
   │
   ▼
通用 Agent 编排器（状态、步骤、重试、人工确认）
   ├── 项目知识检索工具（Project Knowledge Search）
   ├── Brief 解析工具（LLM + 通用字段校验）
   ├── 品类适配器（Genre Adapter：RPG 首期）
   │      ├── RPG 任务规划与结构化生成
   │      ├── RPG 任务/角色/地点 Schema
   │      └── RPG 规则校验与语义评测
   ├── 通用审核/版本工具
   └── 导出工具（JSON / CSV / Markdown）
   │
   ▼
结构化设计包 + 校验报告 + 人工审核记录
```

## 11.2 一条任务的完整状态流

| 状态 | 进入条件 | 允许动作 | 离开条件 |
| --- | --- | --- | --- |
| draft | 用户创建任务。 | 编辑 Brief、保存。 | 必填信息完整。 |
| brief_ready | Brief 完整。 | 解析需求、检索设定。 | 生成解析摘要并由策划确认。 |
| planning | 需求已确认。 | 生成任务大纲和节点计划。 | 大纲通过人工确认。 |
| generating | 结构方案已确认。 | 生成节点内容、对话和分支。 | 输出通过 Schema 解析。 |
| validating | 任务数据已生成。 | 执行结构规则和语义检查。 | 校验报告完成。 |
| needs_review | 存在问题或等待审核。 | 修改、忽略、要求重生成。 | 高风险问题处理完毕。 |
| approved | 策划确认。 | 锁定版本、导出。 | 导出成功。 |
| exported | 文件生成。 | 下载/再次导出。 | 本版本结束。 |

## 11.3 各步骤使用什么能力

| 步骤 | AI/程序职责 | 不能交给 AI 自行决定的事 |
| --- | --- | --- |
| Brief 解析 | 按当前 genre 模板抽取目标、约束、必需元素和禁止项，输出结构化字段。 | 不能替用户补造缺失的关键设计要求。 |
| 项目知识检索 | 检索当前品类相关的项目资料、规则和历史产物，并返回来源 ID。 | 不能把没有来源支持的内容写成既定事实。 |
| 品类适配器 | 调用当前品类的 Schema、Prompt、工具和规则集；首期只启用 RPG。 | 不能把 RPG 任务规则套到 MOBA 技能或 FPS 地图上。 |
| 设计规划 | 首期建议 Quest 节点、分支和任务路径；其他品类未来调用不同规划器。 | 不能擅自更改已冻结设定或用户指定的设计目标。 |
| 内容生成 | 首期生成任务节点、角色台词和选项；其他品类生成专属设计内容。 | 不能越过品类规则、知识边界或更改状态约束。 |
| 规则校验 | 程序检查 JSON、图结构、引用、必填字段和路径。 | 不能用 LLM 的“看起来合理”替代确定性校验。 |
| 语义审查 | LLM 对照设定来源找潜在矛盾，给出证据和置信说明。 | 不能直接将争议解释为确定事实；高风险项交人。 |
| 审核与导出 | 记录审核动作、版本差异，导出用户确认的数据。 | 不能覆盖锁定版本或隐式删除用户修改。 |

## 11.4 技术选型原则

- 先确定通用底座与品类扩展边界，再确定数据结构和用户流程；不要为了使用 LangGraph、Dify、Coze 或 MCP 而反向设计产品。
- 初期设定资料数量较少，可先用结构化文件 + 元数据过滤/关键词检索；只有检索效果成为瓶颈，再引入向量检索和重排。
- 工作流初期可采用单一编排流程，工具作为独立函数；只有状态复杂度上升时再引入专门 Agent 框架。
- 前端优先做可理解的表单、节点列表/简图和问题面板；不必第一版做复杂拖拽图形编辑器。
- 对你当前编程基础，建议先做 Figma 可交互原型，再用 AI 编程工具实现简单 Web/Streamlit 原型。具体框架在需求冻结后再定。
- 所有输出先经过 JSON Schema 或等价结构校验；结构失败要重试/修复或返回错误，不要静默保存破损数据。

# 12. 阶段七：数据结构与校验规则

## 12.1 最小核心对象

| 对象 | 核心字段 | 作用/层级 |
| --- | --- | --- |
| GameProject | project_id, title, genre, genre_schema_version, version, ruleset_version | 通用项目对象；genre 首期为 RPG，未来可扩展 MOBA/FPS。 |
| GenreProfile | genre, design_domains, schema_ref, rule_pack_ref, export_profile | 品类适配配置；定义各品类专属数据结构、规则和导出。 |
| KnowledgeEntry | knowledge_id, type, title, content, source_ref, version, tags | 通用项目知识单元；RPG 可包含世界观、角色、地点、事件。 |
| DesignBrief | brief_id, genre, design_domain, goal, constraints, forbidden_items, required_outputs | 通用设计需求；首期使用 Quest Brief 扩展字段。 |
| DesignArtifact | artifact_id, genre, artifact_type, schema_version, payload, status, version | 通用设计产物容器；payload 由品类 Schema 约束。 |
| QuestDesign | quest_id, title, summary, prerequisites, start_node_id, node_ids, ending_ids | RPG 专属扩展对象，属于首期实现范围。 |
| QuestNode / QuestEdge | node_id, node_type, content, conditions, from_node_id, to_node_id | RPG 任务图专属节点和边。 |
| ValidationIssue | issue_id, genre, rule_id, severity, target_id, evidence_refs, explanation, suggestion, status | 通用问题记录；rule_id 指向当前品类规则集。 |
| ReviewRecord | review_id, target_id, reviewer_action, comment, before_version, after_version, timestamp | 通用人工审核与修改轨迹。 |
| ExportPackage | export_id, artifact_id, format, schema_version, validation_status | 通用导出记录；首期 JSON/CSV/Markdown。 |

> **数据建模原则**
> 通用层只定义项目、知识、Brief、产物、问题、审核和导出等跨品类对象；Quest、Character、Skill、Hero、Map、Mode 等属于品类专属对象。首期只实现 RPG 扩展字段。任何新增品类必须独立定义 Schema 版本、规则包和测试集，不得把不同品类的语义压成一张通用大表。

## 12.2 RPG 首期任务节点类型

| 类型 | 用途 | 例子 |
| --- | --- | --- |
| start | 任务入口。 | 玩家与巡逻队员首次交谈。 |
| dialogue | 对话或信息呈现。 | 药剂师给出第一条线索。 |
| choice | 玩家选择。 | 把线索交给镇长或继续调查。 |
| objective | 玩家要完成的目标。 | 在旧矿洞找到调查记录。 |
| condition | 判断变量/条件。 | 若已收集两条线索，开放隐藏路线。 |
| reward | 奖励或状态变化。 | 获得物品、关系值或任务标记。 |
| end | 任务结束节点。 | 普通结局/隐藏结局。 |

## 12.3 确定性结构检查规则

| 规则 ID | 检查内容 | 严重等级建议 | 失败示例 |
| --- | --- | --- | --- |
| Q001 | 任务必须且只能有一个起始节点。 | 阻断 | 没有 start 或存在两个 start。 |
| Q002 | 所有节点 ID 唯一。 | 阻断 | 两个节点共用 N03。 |
| Q003 | 所有边的 from/to 节点均存在。 | 阻断 | edge 指向不存在的 N99。 |
| Q004 | 任务至少有一个 end 节点。 | 阻断 | 所有路径都没有终点。 |
| Q005 | 所有必需节点从 start 可达。 | 阻断 | 隐藏结局节点未被任何路径连接。 |
| Q006 | 所有 choice 至少有两个有效选项/出口。 | 高 | 选择节点只有一条出口。 |
| Q007 | 条件引用的变量必须定义。 | 高 | 使用 clue_count 但未定义。 |
| Q008 | 角色 ID、地点 ID、任务 ID 引用必须存在。 | 阻断 | 对话引用未定义角色。 |
| Q009 | 任务目标必须有完成条件。 | 高 | 目标写了“调查矿洞”但没有完成判定。 |
| Q010 | 失败/放弃路径需有明确状态或说明。 | 中/高 | 失败后任务无后续状态。 |
| Q011 | 不能存在未解释的死路或软锁。 | 高 | 某选择后无后续且未定义失败结局。 |
| Q012 | 节点内容需满足 Brief 的必需元素。 | 高 | 要求 3 个 NPC，实际只引用 2 个。 |

## 12.4 RPG 首期语义审查规则

- 世界观冲突：生成内容是否违反已确认的设定条目。每个疑点必须引用 lore_id 或说明无依据。
- 角色知识越界：角色是否提及其 knows 列表之外、且在剧情中尚未获得的信息。
- 时间线冲突：事件发生顺序、角色年龄/状态、任务先后关系是否矛盾。
- 人设不一致：角色表达是否与核心性格、动机、语言风格明显冲突。
- 玩家选择无意义：不同选项是否产生相同结果却未明确说明，是否存在承诺了结果但没有状态变化。
- 设定无来源：AI 是否将推测内容写成已确认事实。该类问题应标记为“缺少来源/待策划确认”，不要自动判错。

> **质量控制原则**
> 规则代码负责可确定的结构问题；LLM 负责提出语义疑点和解释；策划负责最终内容判断。不能让生成模型自己给自己打分，也不能把 LLM 评委分数直接当作项目真实准确率。

# 13. 阶段八：MVP 开发执行顺序

开发必须按可验收的小批次推进。你可以使用 WorkBuddy、Trae、Cursor 或其他 AI 编程助手，但每个批次都先让工具给出计划和受影响文件，再确认后执行。开发助手不能自行改变 PRD、测试集标准和已锁定的任务规则。

| 迭代 | 开发内容 | 先验收什么 | 暂时不做 |
| --- | --- | --- | --- |
| M0 静态原型 | 项目首页、设定库、Brief 表单、任务编辑、检查页、导出页。 | 完整点击路径和关键状态能演示。 | 真实模型调用。 |
| M1 通用数据骨架 | GameProject/GenreProfile/KnowledgeEntry/DesignBrief/DesignArtifact + RPG Quest/Node/Edge 扩展。 | 能按 genre 加载 RPG Schema，保存、读取并校验样例任务 JSON。 | MOBA/FPS 完整 Schema、多用户协作。 |
| M2 Prompt-only 基线 | 不接 RAG，先用 Brief 直接生成任务结构和内容。 | 记录失败样本，建立基线结果。 | 不要一开始加入复杂 Agent。 |
| M3 设定检索 | 检索 lore 条目、角色卡和任务规则，展示引用。 | 生成内容能说明依据来自哪些 lore_id。 | 不盲目上知识图谱。 |
| M4 结构化生成 | 先出计划，人工确认，再生成节点和分支。 | 结构化 JSON 可解析，用户能修改。 | 不一次性生成长篇剧情。 |
| M5 规则校验 | 实现 Q001–Q012 中首批确定性规则。 | 异常任务能稳定触发对应问题。 | 不把确定性检查交给 LLM。 |
| M6 语义检查 | 加入世界观冲突、人设和知识边界检查。 | 每条问题有目标节点和证据引用。 | 不自动覆盖已确认设定。 |
| M7 审核与版本 | 采纳、修改、忽略、重生成、版本差异和导出。 | 用户改动不被重生成覆盖；可导出。 | 复杂权限、多版本协同。 |
| M8 整体回归 | 全流程跑固定用例，记录成本、时延、失败和恢复。 | 稳定复现评测报告。 | 不做没有数据支持的效果宣称。 |
| M9 跨品类概念验证（可选） | 在 RPG MVP 稳定后，选 MOBA 或 FPS 中一个小设计对象，验证 Genre Adapter、Schema 和规则包是否可插拔。 | 产出一个最小概念验证和扩展差异报告。 | 不开发第二个完整品类，不把 RPG 功能复制粘贴改名。 |

## 13.1 每次让 AI 编程助手执行的纪律

- 先阅读当前 PRD、数据模型和验收用例，不允许它自行补充未确认需求。
- 先输出实施计划、文件变更清单、数据结构变化和风险；用户确认后再改。
- 一次只做一个迭代，不让它“顺便优化”其他模块。
- 每次修改后运行单元测试、结构校验和对应回归用例。
- 发生失败时先定位原因，保留错误日志和最小复现案例，不通过修改测试预期掩盖 Bug。
- 文档、代码、测试集和 Prompt 版本号保持一致；重要修改要写变更记录。

# 14. 阶段九：评测集与效果验证

## 14.1 评测目标

评测要回答：结构化 Agent 工作流是否比直接 Prompt 生成更符合策划需求？检索是否减少设定冲突？规则引擎是否发现了 LLM 容易漏掉的结构问题？人工审核后，交付内容是否更可用？

## 14.2 评测方案分层

| 版本 | 方案 | 目的 |
| --- | --- | --- |
| Baseline A | 单轮 Prompt：Brief → 任务内容。 | 建立最简单的生成基线。 |
| Version B | 结构化 Prompt：先解析需求，再生成固定 Schema。 | 观察结构约束带来的变化。 |
| Version C | 加入 Lore 检索和来源引用。 | 观察知识依据和设定一致性变化。 |
| Version D | 加入确定性结构校验与语义检查。 | 观察错误检出、可修复性和人工工作量变化。 |

每次对比只改变一个关键因素，使用同一批测试 Brief、同一版本世界观资料和相同模型配置。若模型版本、温度、Prompt 或检索参数变化，必须记录，避免把多项变更的效果归因给某一项。

## 14.3 测试集规模与分组

| 类型 | 建议数量（首轮） | 测试什么 |
| --- | --- | --- |
| 正常任务 Brief | 8–10 | 标准任务生成、角色引用、分支和结束条件。 |
| 需求约束冲突 | 4–5 | 需求中的 NPC 数量、分支数量、禁止事项是否被遵守。 |
| 世界观冲突 | 4–5 | 已知设定被违反、时间线冲突、地点信息冲突。 |
| 角色知识越界 | 4–5 | 角色提前知道秘密、提及未接触事件。 |
| 结构异常 | 5–8 | 断路、孤立节点、ID 重复、引用缺失、变量未定义。 |
| 歧义/信息不足 | 3–5 | 系统是否先澄清，而不是自行编造。 |

首轮可先用 25–35 条案例建立开发集。另留 20% 作为保留集，最终有条件时由第二位评审者做盲评。测试集真值由人根据原创设定、明确规则和任务要求独立制定，不得根据模型输出反向修改标准。

## 14.4 核心指标与定义

| 指标 | 计算口径建议 | 注意事项 |
| --- | --- | --- |
| 需求覆盖率 | 满足的适用必需约束数 / 适用必需约束总数。 | 约束项需要事先明确，不允许模型自行解释扩大分母。 |
| 结构 Schema 通过率 | 通过数据结构校验的任务包数 / 生成任务包总数。 | 由程序判定。 |
| 任务图有效率 | 通过 Q001–Q012 约定规则的任务包数 / 测试任务包总数。 | 报告每条规则的错误分布。 |
| 设定冲突 Precision/Recall | 与人工 GT 对比，计算检出的真实冲突比例和漏检比例。 | 需固定冲突样本和无冲突样本；报告类别分布。 |
| 知识越界检出率 | 被系统正确识别的角色知识越界案例 / GT 越界案例。 | 不能将未明确的剧情推断算成知识越界。 |
| 人工接受率 | 无需重大修改即可接受的输出 / 所有被评审输出。 | 由目标用户或明确评分规则评审，不让模型自评。 |
| 人工修改量 | 每个任务包发生的重大修改项数量或修改分钟数。 | 定义“重大修改”，保持同一计时方法。 |
| 单次生成成本/时延 | 模型/API 实际用量和从提交到结果完成的时间。 | 同时报告失败重试和人工等待时间。 |

## 14.5 人工评审表

| 评审维度 | 评分（1–5） | 判断标准 |
| --- | --- | --- |
| 需求符合 | 1–5 | 是否满足 Brief 的目标、约束和必需元素。 |
| 结构可执行 | 1–5 | 任务入口、节点、条件、分支和终点是否完整。 |
| 设定一致 | 1–5 | 是否遵循世界观、时间线和人物知识边界。 |
| 角色可信 | 1–5 | 角色行为和对白是否符合已定义动机与性格。 |
| 可交付性 | 1–5 | 程序/QA 是否能理解字段和验收条件。 |
| 修改成本 | 记录分钟 | 从打开结果到评审者认为可交付的时间。 |

## 14.6 评测结果怎么写

报告必须包含测试集版本、模型版本、Prompt 版本、检索配置、品类 Schema 版本、规则版本、样本数量、失败案例和指标计算口径。可以展示提升，也必须展示没有改善或变差的类别。RPG 首期结果只能支持对当前 RPG 任务场景的判断，不得据此宣称适用于所有游戏类型。

# 16. 项目风险、停止条件与变更纪律

| 风险 | 可能表现 | 应对方式 |
| --- | --- | --- |
| 业务调研不足 | 自己想象策划痛点，做出的功能无人需要。 | 前置 3–5 次访谈；样本不足则标记验证限制。 |
| 竞品能力重叠 | 功能看起来像 articy/Ink/Twine 的简化版。 | 不重做编辑器；聚焦 Brief→任务包 Agent 与质量检查。 |
| 范围膨胀/多品类失控 | 同时加入 RPG、MOBA、FPS、NPC 实时对话、美术、语音和引擎插件。 | 首期只做一条 RPG 任务策划链路；其他品类仅作为后续概念验证。 |
| AI 内容不可靠 | 设定幻觉、分支不闭环、角色越界。 | 来源引用、确定性校验、LLM 语义检查、人审。 |
| 技术实现失控 | 为了复杂前端和引擎接入消耗大量时间。 | 先静态原型和简单 Web MVP；不要求首版原生引擎集成。 |
| 评测注水 | GT 来自模型输出，LLM 自己评自己。 | 人制定 GT；保留集盲测；至少一个独立评审者。 |
| 版权风险 | 复制商业游戏剧情、角色、资源或内部资料。 | 原创世界观；只研究公开工作方式；引用公开资料并记录来源。 |
| 求职表达夸大 | 把原型描述成商业化产品或真实游戏管线集成。 | 明确是作品集原型、模拟数据和验证范围。 |

## 16.1 必须暂停或转向的情况

- 3–5 次有效访谈后，没有任何重复出现的游戏策划痛点，或 RPG 任务策划并非最值得先解决的场景。
- 访谈证明现有叙事工具/引擎已满足主要需求，而 AI 只是锦上添花，无法形成可验证价值；此时回到品类决策闸门，不要硬做 RPG。
- 为了实现“多品类”而必须同时建设 MOBA/FPS 专业规则，但缺少对应用户和样本；应保持单品类 MVP，不把规划能力包装成已实现能力。
- 目标用户不愿意提供任何可脱敏的任务样例，也无法通过原创数据构造可信测试。
- 核心效果只能靠 LLM 自评，无法设计独立规则或人工评审。
- 项目必须依赖完整 UE5 插件或商业游戏内部接口才能证明价值，而当前资源不具备。

## 16.2 变更纪律

项目范围或数据结构变更必须写明：变更原因、证据来源、影响页面、影响数据、影响测试集、是否改变成功指标。未经确认，不允许 AI 编程助手擅自扩大功能或改变评测口径。每个阶段形成冻结版本，后续修改通过变更记录进行。
