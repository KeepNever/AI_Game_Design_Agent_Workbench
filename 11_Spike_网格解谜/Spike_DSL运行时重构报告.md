## 三、运行时模板设计（为什么它能承载不同玩法）

引擎与规则的职责切分是 Spike 的核心架构假设：

| 引擎管（写一次） | 规则模块管（每玩法一份） |
|---|---|
| 底图与墙体渲染、网格线 | 特殊静态字符（目标点红框 / 门与出口） |
| 方向输入、回合调度 | `tryMove`：本玩法的移动/碰撞/状态变更规则 |
| 撤销（JSON 快照）/ 重开 / 切关 | `isWin`：本玩法的胜利条件 |
| 事件日志、胜负面板、autoplay 重放 | `status`：本玩法的状态栏；动态实体绘制 |

引擎对"箱子/钥匙/门"**一无所知**。两个游戏的 `engine/grid_engine.js` 是**同一个文件**（md5 `a6dcea1b…`，字节一致），差异全部在 rules 模块。

## 四、生成结果与代码改动（A/B 两 Brief 差异 · v1 手写阶段历史记录，现均 DSL 化见 §十）

| 项 | 游戏 A · 推箱 | 游戏 B · 钥匙门 |
|---|---|---|
| 核心动作 | **推动**——改变他物位置 | **收集**——改变自身状态 |
| 状态模型 | 箱子位置集合（世界状态） | 钥匙库存计数（玩家状态） |
| 约束机制 | 位置约束：被墙/他箱挡住推不动，可卡死（靠撤销挽救） | 门锁逻辑：库存 < need 拒绝通行；出口集齐前不放行 |
| 胜利条件 | 全部箱子落在目标点 | 走到出口 且 集齐全部钥匙 |
| 交互体验 | 顺序规划推动路线 | 规划取钥匙顺序、门锁门槛 |
| rules.js | 63 行 | 82 行（**两文件零共享机制代码**） |
| levels.js | 31 行 | 31 行（同一 JSON 结构，仅实体类型不同） |

**结论：两个玩法在机制、交互、胜利条件上有实质差异，不是换皮**——同一引擎 + 两份规则模块 + 同构关卡数据，正是 S4 v2 想验证的架构形态。

## 七·五、Brief C · 碎裂地板（MU-10 新机制生成记录）

# 十、Spike v2 · DSL 化重构与正式验收（2026-11-11 19:20–19:45，按曦"Spike 执行指令"执行）

## 10.1 为什么重构

曦 19:09 指令第 3 条：**优先结构化规则描述或受约束 DSL，再由程序执行，不要让模型直接生成不受约束、未经验证的代码**。
v1 的三套 rules.js 是手写 JS——机制可运行，但"AI 生成物"与"预置引擎"的边界无法通过代码审查证明。
重构后：**玩法语义 100% 位于数据（mechanic.js 的 DSL 文档），执行器（dsl_runtime.js）不含任何具体玩法分支**。

## 10.2 架构终态

```
预置（引擎能力原语，人工编写）
```

# 十一、验收复核（2026-11-11 21:55，回应曦四项核查与三关验收框架）

## 11.1 四项核查的如实回答

**核查 1：三份 DSL 文件究竟怎么产生的？**
如实回答：**前者**。三份 `mechanic.js` 与 `levels.js` 由开发会话中的 GLM-5.3-Flash 辅助编写、经多轮人工调试形成（调试记录见 §10.5 的 8 项）；**产品生成管线（接收 Brief → 调用模型 → 输出规则数据 → 校验 → 运行）尚不存在**。
因此本 Spike 的准确表述为：**DSL 执行能力与玩法表达能力验证通过**；"AI 游戏生成链路"只取得了间接证据（机制可以被表达为受约束数据），不能声明链路已通过。原 §10.7 "Spike 通过"的表述已按此纠正。

**核查 2：执行器是否真的通用？**
已复核（逐节自审 `dsl_runtime.js`）：移动管线（墙体 → 实体推/挡 → DSL deny 规则 → 移动 → 拾取 → enter 规则 → turn 逐格规则 → win 判定）全部由 DSL 数据驱动；碎裂地板的**计时、触发、状态更新全部位于 mechanic.js**（crack 属性 + turn 规则），执行器中无对应硬编码。
预置词汇两类，均为能力原语：① 实体能力旗标（pushable/pickup/solid——数据声明）；② 视觉样式原语（target/door/exit/stone/crate/key——相当于 sprite）。审查方法局限如实说明：grep + 人工逐节审，"通用性"最终要靠**第四个新机制 Brief 的生成测试**持续检验（列入 G1）。

**核查 3：BFS 与 Autoplay 是否构成有效交叉验证？**
BFS（Python）从关卡数据**独立求解**，不读取运行时任何状态；Autoplay 把 BFS 解法路径作为**输入按键序列**喂给 JS 运行时，**胜负由运行时自己的规则判定**，不是核对预写答案。两个实现独立写出（Python/JS），语义一致才会 6/6 通过——若运行时语义有误，重放即失败（§10.5 的 8 个 bug 中 3 个正是这样暴露的）。
**独立性边界如实说明**：两者独立的是**实现**，共享的是**规格理解**——如果我对 Brief 机制的理解本身错了，两个实现会一起错。所以规格正确性仍需试玩 + G1 的产品管线验证，交叉验证不覆盖这一层。

**核查 4：DSL 安全边界？**
已补齐并复验（6/6 重放通过）：表达式长度 ≤400 字符、括号嵌套 ≤24、缺失/超长表达式直接报错；单条规则效果数 ≤64；格子属性规模 ≤20000；地图 ≤4096 格。效果词汇白名单（未知 op 抛错）、函数白名单（未知函数抛错）、标识符白名单（未知变量抛错）——**规则描述无法执行任意 JavaScript**。
仍缺（如实列出）：单回合效果执行总数没有聚合上限（受地图上限间接约束）；无运行总时长计数器（浏览器环境由用户操作驱动，风险低）；上述 LIMITS 值是拍脑袋的初值，G1 按实测调。
