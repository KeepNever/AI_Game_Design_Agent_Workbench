## 0. 决策摘要与性质声明

**暂定首期场景：「从游戏创意输入到可运行 web 小游戏原型的最小生成闭环」**——MVP 核心验收目标是**一个真实可运行、可试玩的游戏原型**，而不是配置文件、任务图、检查报告或变更确认单。

> **决策性质**：延续 v1 的定性——这是 S2 访谈无法继续收敛情况下，基于现有证据做出的**有明确限制的例外降级决策**，不认定场景已充分验证，不代表市场需求已验证，可被第 6 节任一条件推翻。
>
> **相比 v1 的关键变化**：v1 把"已建成的检查能力"当成了首期场景本身；本包把首期场景还给产品目标——**生成可运行游戏**，已有检查能力降为管线内嵌质量关卡。

**生成与匹配的红线（2026-11-11 19:05 曦追加，产品定义级约束）：**

> 曦原话："我的希望是生成可玩的游戏，而不是把需求告诉之后，匹配到想玩的游戏。"
> 据此钉死边界：**允许预置的是引擎能力原语**（网格、移动、回合、碰撞、事件、**状态变量**、渲染——这是"游戏引擎"，任何游戏都用）；**玩法规则（实体、交互、胜利条件）与关卡必须由 AI 从 Brief 生成**，不得通过预置完整玩法规则模块来替代 AI 生成；新机制必须由 AI 根据 Brief **组合或生成**规则逻辑。
> Spike 中的推箱/钥匙门两个游戏在 G1 中降级为**测试样例**（用来验证模板与验证器），**不是可选游戏库**。
> 试金石 = MU-10 新机制生成测试：给一个预置玩法中不存在的新机制 Brief，系统必须生成出可玩、可解、可验证的新游戏。

**2026-11-11 15:52 曦审意见落实**：① 四项决策确认（品类同意 / Must 有条件同意 / v1 作废同意 / Spike 先行强烈同意）；② 新增 **MU-9 玩法差异验证**（防模板换皮——两个不同玩法 Brief 必须产出机制不同的游戏）；③ MU-7 强化为**玩法层面**的迭代；④ 前置条件新增第 0 项"玩法边界确定"，Spike 必须双玩法输入；⑤ ★第一阶段最重要的开发成果是可运行的游戏，不是更完整的质量检查面板。

## 3. MVP 范围（MoSCoW，每项带验收标准）

### 3.1 Must（共 10 条，缺一不可；验收物 = 可玩游戏原型 + 一次迭代）

| # | 内容 | 验收标准 |
|---|---|---|
| MU-1 | **品类运行时模板 ×1**（web 单屏，参数化骨架） | 模板本身可玩；设计参数（数值/关卡/规则）可从外部注入 |
| MU-2 | **游戏策划 Agent 最小版**：固定 Brief 表单 → 结构化设计对象 | 产物通过品类 Schema 校验；人工确认点真实存在；**设计对象由 Brief 生成，不得来自预置玩法库匹配** |
| MU-3 | **内容生成 Agent 最小版**：设计对象 → 配置/关卡数据 | **最终交付候选**必须通过适用的 Schema、RulePack 和专属可解性验证。**初次生成失败可被拦截并重新生成——必须逐次记录失败、诊断和重试结果**；**初始生成通过率与最终交付通过率分开统计，不得混为一谈**。⚠️ RulePack 与 Q013 不是通用游戏验证器，按实际建模范围适用；实际运行测试与人工试玩不可替代 |
| MU-4 | **代码生成**：设计对象 + 运行时模板 → 可执行代码（依托现成 AI Coding） | 生成代码通过沙箱执行验证；人工可审查微调；**生成的规则代码实现的是 Brief 描述的机制，而非调用预置玩法库** |
| MU-5 | **项目组装与质量检查**：资源清单核对 + 静态检查 + 打包 | 组装产物在浏览器中直接运行；缺资源/断引用被报告 |
| MU-6 | **运行测试与预览**：浏览器试玩 + 冒烟测试 | 非开发者从打开页面到玩起来 ≤ 1 分钟；冒烟结果自动记录 |
| MU-7 | **一次迭代闭环**：试玩反馈 → 影响定位（M5）→ 受影响对象重生成 → 试玩验证 | 至少一次**玩法层面**的修改（规则或机制，不止改标题/皮肤/数值微调）：连带改动被列出并确认，重生成后游戏仍可玩且改动生效 |
| MU-8 | **固定工作流视图**：八段管线状态可视化（§8.4 MVP 档） | 能看到每段状态、产物入口与人工确认点 |
| MU-9 | **玩法差异验证（防模板换皮，曦审意见）**：两个玩法机制不同的 Brief 各自走完全管线 | 产出的两个游戏在**玩法机制、交互方式、目标或规则**上有实质差异（如实时动作 vs 回合制策略），而非仅外观/数值/标题不同；差异点由人工试玩判定并记录 |
| MU-10 | **新机制生成测试（生成≠匹配的试金石；⏩ 前移至 Spike 阶段执行）**：Spike 除推箱、钥匙门外，增加第三个**预置玩法中不存在**的新机制 Brief——「踩过的格子在两回合后碎裂成洞，洞不可通行，抵达出口获胜」 | 验证 AI 能否根据 Brief 生成对应的**状态变量**（碎裂倒计时）、**触发条件**（踏入→开裂；倒计时归零且无人→碎裂）和**规则逻辑**，并最终生成**可运行、可解**的游戏（BFS 可解性验证 + 运行重放 + 试玩）。若只能靠匹配既有玩法完成，判定为未通过 |

### 3.2 Should（不阻塞 P1 验收，P2 优先）

- 设计编辑器 UI 增强（结构化对象的可视化编辑）
- 测试 Agent 自动化加深（错误自动分类定位）
- 多套模板参数预设、素材程序化生成增强
- H0 对照实验（人工基线 vs 生成流程）

### 3.3 Could

- 第二品类模板（P3）
- 演示视频、导出分享打包
- 画布受控配置（§8.4 后续版本档）

### 3.4 Not in MVP

- 自研游戏引擎、UE/Unity 深度插件
- 多品类同时支持；美术/音频真实资产生产
- 自动发布与商业化；多人协作/权限/多租户
- 自由节点编辑器与多 Agent 编排画布
- **预置完整玩法库 + 需求匹配**（这是"游戏推荐器"，不是生成工作台——引擎能力原语可以预置，玩法规则必须生成）

- 公告文案生成检查（候选池不变）

## 4.3 规则生成的技术路线（曦 19:09 指定）

- **第一版优先采用结构化规则描述或受约束 DSL**：AI 先产出结构化的规则描述（实体、状态变量、触发条件、效果），再**编译成可执行逻辑**——而不是直接生成自由代码。
- 若某环节采用 AI 生成代码，则**必须经过受控沙箱执行、规则检查和运行测试**三道关卡，**不允许未经验证直接执行**。
- Spike 的 Brief C（碎裂地板）即按此路线产出：结构化机制描述 → 规则逻辑 → 引擎契约内实现 → BFS 可解性验证 → 运行重放。

## 7.5 首期玩法边界（✅ 已拍板，2026-11-11 16:01）

**Web 单屏回合制网格解谜**——不把消除、策略、解谜等多个不同玩法混为一个模糊范围。

Spike 使用两个不同机制的 Brief（共享网格地图、玩家移动、回合操作和基础运行时，但玩法规则、交互和胜利条件必须有实质差异）：

| Brief | 核心机制 |
|---|---|
| **A · 推箱到目标点** | 物体推动、位置约束（推不动/卡死）、目标达成（全部箱子就位） |
| **B · 收集钥匙开启出口** | 物品收集、状态条件（钥匙库存）、门锁逻辑（按需开门）、目标解锁（集齐才放行出口） |

选 B 路线（网格解谜）的理由：首期技术复杂度可控、操作结果可重复，便于验证 AI 生成、规则检查、关卡验证和迭代能力。
