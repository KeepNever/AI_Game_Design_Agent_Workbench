## 二、口径定义（沿用 v4，曦已确认部分不再重复论证）

**每次"用户 Brief → 可玩游戏"生成的 4 次基础模型调用**：① 策划 Agent（Brief → Game Design Package）② 内容生成（设计对象 → 关卡数据）③ 规则生成（设计对象 → mechanic DSL）④ 组装描述生成（⚠️ 待确认：可能由 MU-5 脚本化组装承担，若确认则基础调用降为 3 次，预算按保守 4 次保留）。

**确定性代码校验不计入模型 API 请求（0 费用）**：Schema 校验、DSL 白名单校验、BFS 可解性验证、autoplay 冒烟重放。

**条件诊断与重生成单独计费**：校验失败后 1 次诊断调用 + 1 次重生成调用。

**重试发生概率 40% = 任务级**（每次完整生成中至少发生一次需诊断+重生成的概率，非节点级），期望重试 = 0.4 × 2 = **0.8 次/生成**，G1 真实调用日志验证回填。

**期望请求数 / 生成 = 4 + 0.8 = 4.8 次**（节点 ④ 脚本化则 3.8）。

估算假设（全部**待 G1 实测校准**）：单请求输入 6K / 输出 2K tokens（估算值）；缓存命中率 30%（只折输入不折输出）；GLM-4.7 输出 2K 适用 ≥0.2K 档 14 元。

## 六、G1 初始验证预算与后续研发预算的区分（曦指令 6/7 新增）

**两阶段预算分开管理，不叠加混用：**

### 阶段一 · G1 初始验证预算（主力模型核定用）

**口径**：两个候选模型（GLM-5.3-Flash 与 GLM-4.7）在**同一批 Brief** 上走完整生成管线对照——同输入、同校验、同判定标准，产出质量/重试率/成本三项实测数据，据此核定主力模型。

| 假设 | 取值 | 性质 |
|---|---|---|
| 验证 Brief 数 | 10 个（覆盖四机制类型 + 至少 1 个新机制） | 估算假设，待 G1 实测校准 |
| 每 Brief 请求 | 4.8 次 × Prompt 调试 5 轮重跑 = 24 次 | 估算假设 |
| 每候选请求合计 | 240 次 | — |

**预留口径（曦核定 16:05 明确）：两个候选**分别预留、分别向上取整**，不合并取整**——便于控制各候选模型各自的消耗：

| 候选 | 基础费用（精确 → ceil） | 预留精确值（基础 × 50%） | 预留 ceil | 候选小计 |
|---|---|---|---|---|
| GLM-5.3-Flash | 2.2498 → **3 元** | 1.12488 | **2 元** | **5 元** |
| GLM-4.7 | 10.0032 → **11 元** | 5.0016 | **6 元** | **17 元** |
| **G1 初始验证预算上限** | | | | **3 + 2 + 11 + 6 = 22 元** |

⚠️ 口径说明：若两候选预留合并后统一取整（7.1265 → 8），总额为 21 元。两种口径均非算术错误，**核定采用分别预留口径（22 元）**，理由 = 便于分候选控制消耗与核销。

### 阶段二 · 主力模型确定后的后续研发预算

主力核定后，按选定模型的五科目表执行（GLM-5.3-Flash → 42 元 / GLM-4.7 → 184 元，见 §五）。**阶段一的实际支出从对应模型的开发科目中核销**，不重复立项。

**说明**：初始验证预算量级极小（二十余元人民币），这正是两候选对照在成本上可行的直接证据——核定主力模型不需要大额预算前置。

**预算性质声明（曦核定意见）**：42/184 元不是两套预算同时全部投入的批准，而是 **G1 实测选定一个模型后采用对应预算档**。

**核销规则（曦核定意见）**：22 元初始验证费用核销到**对应模型**后续预算的开发科目，且**只能核销同一模型实际发生的费用**——未选中模型的测试费用不得扣到另一个模型的预算中。

**评测设计要求（曦核定意见补充）**：10 个验证 Brief 必须区分**调试样本**与**最终验证样本**——不能让同一批样本全部参与 Prompt 调优后又把成绩当独立验证结果。预算仍按 240 次请求估算，验收时保留未参与调优的测试样本（建议 7 调试 + 3 验证分离），最终对照成绩以验证样本为准。
