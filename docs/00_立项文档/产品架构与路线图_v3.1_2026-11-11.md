## 一、完整产品架构（主链路）

**产品定义**：用户输入游戏创意和需求 → AI 辅助完成游戏策划、玩法设计、关卡和内容生成、程序代码生成、资源整合、项目组装、运行测试和后续修改迭代 → **产出一个可以运行、可以试玩、可以继续开发的游戏**。

### 主链路（八段）

```
C1 创意与需求解析 → C2 游戏策划与玩法设计 → C3 关卡与内容生成 → C4 程序代码生成
→ C5 资源整合与项目组装 → C6 运行测试与预览 → C7 问题修复 → C8 迭代再生成 →（回到 C3/C4）
```

| 段 | 输入 → 输出 | 人工参与点 |
|---|---|---|
| C1 创意与需求解析 | 创意/需求 → 结构化游戏概念（玩法循环、类型、范围、平台、风格） | 确认概念、砍范围 |
| C2 游戏策划与玩法设计 | 概念 → 结构化设计对象（玩法规则、数值、关卡结构、任务图、界面描述），通过品类 Schema 校验 | 设计编辑器审改、确认 |
| C3 关卡与内容生成 | 设计对象 → 配置表、关卡数据、剧情文本、素材（占位/程序化优先） | 抽查、采纳/拒绝 |
| C4 程序代码生成 | 设计对象 + 运行时模板 → 可执行游戏代码 | 代码审查、微调 |
| C5 资源整合与项目组装 | 代码+素材+配置 → 可运行项目包 | 触发组装、看清单 |
| C6 运行测试与预览 | 项目包 → 试玩、冒烟测试结果、错误清单 | **亲自试玩**（最高质量信号） |
| C7 问题修复 | 错误 → 定位（设计对象 or 代码）→ 修复补丁 | 决定采纳 |
| C8 迭代再生成 | 试玩反馈/新需求 → **影响定位** → 受影响对象重生成 → 回 C3/C4 | 决定改什么 |

**交付物定义（与旧定位的本质区别）**：C2 产出的策划文档、配置表、检查报告全部是**中间产物**；只有 C6 通过的**可运行游戏**是交付物。

## 二、Agent 体系（五个 Agent 的职责与协作）

> 原则：第一版不要求每个 Agent 独立实现（可以是提示词管线 + 脚本），但**架构按 Agent 划分**，保证未来扩展。

| Agent | 核心职责 | 输入 → 输出 | 与其它 Agent 的协作 | 第一版形态 |
|---|---|---|---|---|
| **① 游戏策划 Agent** | 创意 → 结构化设计；维护设计意图；收到测试反馈时修订设计 | 创意/Brief → 设计对象包（过 Schema 校验） | 是 ②④ 的**意图源头**；接收 ⑤ 的反馈修订设计 | LLM + 固定 Brief 模板 + Schema 约束输出；人工确认必需 |
| **② 内容生成 Agent** | 设计对象 → 配置表、关卡数据、剧情文本、素材 | 设计对象 → 内容产物包 | 消费 ① 的输出；产物过 ④ 的质量关卡后才能出厂；不可通关内容被拦截回炉 | LLM 结构化生成 + 占位素材 |
| **③ 代码生成 Agent** | 设计对象 + 运行时模板 → 游戏代码；修复请求 → 代码补丁 | 设计对象 → 可执行代码 | 消费 ① 输出；遵守 ④ 的静态检查；缺陷来自 ⑤ | **依托现成 AI Coding 能力 + 品类运行时模板**（模板填充式生成，非裸写） |
| **④ 项目组装与质量检查 Agent** | 资源清单核对、组装、静态质量检查（Schema/引用完整性/规则/可通关性） | 内容+代码+素材 → 可运行项目包 + 检查报告 | 是 ②③ 产物出厂的**必经关卡**；报告供 ⑤ 使用 | 脚本为主；**复用 M5 依赖索引、RulePack、Q013** |
| **⑤ 测试与迭代 Agent** | 运行预览、冒烟测试、错误分类定位、发起修复/迭代循环 | 项目包 → 测试报告 + 迭代建议 | 错误分流：设计问题→①、代码缺陷→③；迭代影响定位用 M5 | 无头浏览器冒烟 + 人工试玩反馈入口 |

**协作关系一句话**：① 定意图 → ②④ 产出内容 → ③ 出代码 → ④ 组装并把关 → ⑤ 验证并回流；**质量检查不是独立环节，而是嵌在每个 Agent 输出点的关卡（生成即检查）**——这是 RulePack/Q013/M5 在新架构中的存在方式。

### 二·五、开发工具 ≠ 产品能力（曦审意见 #2，防混淆）

> 现在（曦与助手）用 GLM-5.3-Flash 等 AI 辅助**开发这个工作台本身**，属于开发阶段工具。
> 而 Agent ③"代码生成"是**面向最终用户的产品能力**：它必须能接收 Game Design Package、调用模型、读写项目文件、修改代码、执行运行时验证并把结果反馈给工作流。
> **"用 AI 写出了工作台"不等于"工作台具备游戏代码生成能力"**——两者在架构与验收中严格分开：前者是工程手段，后者是 MU-4 的验收对象。

### 二·六、四类数据契约（曦审意见 #5，五 Agent 协作的语言）

> 五个 Agent 之间**不靠自然语言传话**，靠以下四类结构化数据契约衔接。第一版冻结 Schema 后实现，版本号管理。

| 契约 | 主要内容 | 产出方 → 消费方 |
|---|---|---|
| **Game Brief** | 游戏类型、玩法目标（核心体验）、范围（关卡数/内容量）、风格（视觉/题材）、约束（平台=web、操作方式、时长） | 用户+① → ①②③ |
| **Game Design Package** | 玩法机制（规则/状态机）、游戏状态与变量定义、关卡结构、数值表、任务图（节点/边/条件）、界面描述；**过品类 Schema 校验** | ① → ②③④ |
| **Game Build Package** | 代码文件清单与内容、资源清单（素材/占位）、配置产物、运行入口、组装清单与静态检查报告 | ④ → ⑤ 及用户 |
| **Test & Iteration Report** | 运行结果（冒烟通过/失败）、错误清单（分类：设计/代码/资源）、人工试玩反馈、待修改对象清单（含 M5 影响定位结果）、迭代建议 | ⑤ → ①③④ 及工作流 |

**编排**：第一版用固定管线（状态机，节点=上述五 Agent 的调用点）；画布可视化编排按 v2.0 §8.4 分阶段开放（MVP 固定视图 → 后续受控配置 → 长期自由编排需用户研究证明）。

## 三、技术实现路径

| 层 | 第一版选择 | 理由 | 后续升级 |
|---|---|---|---|
| 运行时/引擎 | **web（HTML5/JS，轻量库如 Phaser 或纯 Canvas）**，品类运行时模板 | 浏览器即预览环境（C6 零安装）、迭代最快、符合小游戏切入；**不自研引擎** | 品类适配器接 Godot/Unity 导出（外部引擎协作） |
| 代码生成 | 现成 AI Coding 能力（LLM）+ 运行时模板 API + **沙箱执行验证** | 模板填充式生成远比裸写可控 | 多模板、更复杂逻辑生成 |
| 数据 | gdw 对象模型扩展为**游戏项目对象图**（设计对象+配置+代码文件+素材清单）；SQLite | M1 骨架直接复用 | 对象图加入代码引用/素材引用关系 |
| 质量关卡 | RulePack + Q013 + 结构检查嵌入 C3/C4/C5 输出点；运行期冒烟单独计数 | 已有能力直接归位 | 每品类专属规则包 |
| 前端 | 轻量 Web UI：固定工作流视图 + 简版设计编辑器 + 代码查看 + 预览 iframe | 四界面 MVP 版 | 按 §8.4 分阶段开放画布 |
| 评测 | 设计期检查（变异评测已有）+ 运行期检查（新增）+ 可玩性人工判定 | 两类问题分开计数，不混 | H0 对照实验 |

## 八、风险

| 风险 | 应对 |
|---|---|
| 代码生成质量不可控 | 模板填充式生成 + 沙箱验证 + 模板越窄越稳 |
| 运行时模板路线走不通（某品类模板化成本过高） | P0 期做一次模板可行性验证（品类选型即验证）；走不通则评估引擎插件路线，触发 S4 重开 |
| 范围蔓延回"造引擎/造编辑器" | S4 v2 的 Not list；引擎协作一律走外部工具 |
| 可玩性无 GT | 人工试玩判定 + 冒烟测试 + 质量关卡变异评测；不宣称"生成的游戏好玩" |
| 已有投入被浪费的情绪成本 | §四归位表：每项都有明确岗位，M5/Q013 在生成侧的价值反而放大（拦截打不通的 AI 关卡） |
