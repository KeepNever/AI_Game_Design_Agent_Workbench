**两个已内嵌的正确意识（草案沿用）**：
1. **三值结果**：BFS 输出 可解 / 不可解（UNSAT）/ **UNKNOWN（超状态上限，明确"不算通过"）**——三值不允许塌缩成二值；
2. **求解器独立性**：四个求解器**按 Brief 语义独立手写、不读 mechanic.js**（solve_switchgate 注释明示），靠与 DSL 运行时交叉验证对齐——这是实现级独立性的来源。

**观测面现状口径（v0.2 补，曦指令：新增内容不得冒充现有实装能力）**：四面观测面（logs / 快照 / 错误通道）存在于运行时内部，Spike 期间供**人工核查**；**自动化逐步状态采集与结构化断言工具当前未实装**——GT-2a 是标准设计，其实装属 G1 范围，能力缺口登记 V-3.2。

**Spike → 产品的核心差距（GT 草案必须正面回答）**：现有 BFS 是**每机制手写建模**。四机制可行，产品化后每个新机制都要求人手写求解模型 = **不可规模化**。自动化路线（从 DSL 数据构建状态空间）与独立性路线（手写建模）存在结构性张力，见 §二 GT-1 与 V-3.1。

## 二、GT 分层判定标准

### GT-1 可解性（机器判定）

- **判什么**：关卡在求解器建模范围内，是否存在从初始态到胜利态的可达解法。
- **三值结果语义（v0.2 收紧、v0.3 加覆盖前置、v0.4 PASS 降为候选语义，三种结果含义不同、不得混用）**：
  - **PASS**：求解器找到**到达胜利态的候选路径**——这是建模范围内的**候选可达**结论，**不等于真实通关证据**（区分见下条）；
  - **UNSAT**：**完整覆盖相关机制语义** + **完整穷举**可达状态空间后确认无解——两个条件同时成立才是确定性结论（v0.3 收紧）；
  - **UNKNOWN**：因状态超限、预算耗尽等原因**无法确定**——既不是 PASS 也不是 UNSAT。UNKNOWN 重试仍未解决时，**保持未通过、禁止放行，不得改写为 UNSAT，也不得当作"不可解"的失败证据**（它只表示"没查清"，不是任何一种查清了的结果）。
- **候选 PASS 与真实通关的区分（v0.4 补，曦指令二）**：
  - 求解器候选 PASS（**含部分模型覆盖下找到的路径**）可作为 GT-2a 的输入候选，但**不得宣称为完整状态空间证明**；
  - **候选路径必须通过 GT-2a Runtime 重放，才能作为真实通关证据**——求解器结论（模型内搜索）与运行时行为（真实执行）是两个证据层级，不可互替。
- **模型覆盖状态（v0.3 补，曦指令五）**：求解器对机制语义的覆盖分三档显式声明——**完整支持 / 部分支持 / 不支持**。**只有"完整支持相关机制语义"且"完整穷举无解"同时成立，才允许判 UNSAT**；不支持的语义**不得被转换成确定性不可解结论**（只能输出 UNKNOWN 或"不支持"）。
- **通过标准（v0.2 补，v0.4 标注层级）**：多关卡游戏 = **全部必交付关卡 GT-1 PASS** 方为 GT-1 通过——这是**候选层**通过；真实通关证据由 GT-2a Runtime 重放给出（见 GT-2）。任何一关非 PASS，整体即未通过。
- **求解器路线（v0.2 曦裁定：混合路线，作为待验证方案）**：
  1. A/B/C/D 四个手写 BFS **保留为独立参考求解器**（实现级独立性的锚点）；
  2. 新机制探索**从 DSL 数据自动构建求解状态空间**；
  3. G1 在**已有机制上做双路线对照**（同一机制手写模型 vs 自动模型，比对结果一致性）；
  4. 自动建模无法覆盖某种 DSL 语义时，返回 UNKNOWN 或"不支持"，**禁止静默放行**；
  5. **不提前宣布自动建模技术路线已经可行**——可行性由对照实测回答（V-3.1）。
- **建模范围声明义务**：每个求解器必须**显式声明建模了哪些机制语义、没建模哪些**（如：不含 turn 规则的全局效果、不含 deny 表达式求值的完整语义）。结论只能表述为"**建模范围内可解**"——建模范围外的问题 BFS 沉默，不等于不存在。
- **硬规则**：**BFS 通过 ≠ 游戏质量合格**。GT-1 只是后续所有层的必要前置，不是充分条件。

### GT-2 机制生效（机器判定）

- **判什么**：Brief 要求的目标机制是否在真实运行时中**实际触发**并**产生可观测影响**——防"机制写进数据但从未生效"的装饰性生成物。
- **原子需求三类型（v0.3 补，曦指令二；GT-2a 断言覆盖与 GT-3 核销清单共用同一套类型）**：
  - **核心机制**：Brief 中定义"这个游戏之所以是这个游戏"的最小玩法单元（如碎裂倒计时、闩锁闸门、拾取开门）；
  - **支撑规则**：为核心机制服务的辅助约束（如 deny 拦截、实体推动/阻挡行为）；
  - **结果规则**：胜负判定与结果呈现（win 表达式、status 模板等）。
  - 类型在 Brief 拆解为原子需求时标注（GT-3 清单），**人类可改判**。
- **判据（两档，v0.2 调整定位：2a 为唯一硬门槛，2b 移出硬门槛）**：
  - **GT-2a 触发断言（MVP 硬门槛）**：
    - **断言覆盖方式（v0.3 按需求类型分层，曦指令二）**：

      | 需求类型 | 断言覆盖方式 |
      |---|---|
      | 核心机制 | **全部**设置结构化触发断言（逐步观测 + 四要素）；通关见证路径与机制专项测试路径都要求 |
      | 支撑规则 | **逐条覆盖（v0.4 收紧）**：每条**影响核心机制正确性**的支撑规则，至少有一个结构化断言证明其生效；**不得仅以支撑规则类别中任意一条通过，就认定所有支撑规则均已覆盖** |
      | 结果规则 | win：GT-1 PASS + 通关见证路径**终点结构化断言**（胜利判定实际触发）；status 等呈现类不作机器硬断言，归 GT-4 基础可试玩人审确认 |

    - **逐步状态观测（v0.2 补）**：对操作序列做**逐步**状态观测与断言，**不只对比初始和最终状态**——只有中间态序列才能定位机制在哪一步、以何种方式生效；
    - **两类路径区分（v0.2 补，v0.4 措辞对齐候选语义）**：**通关见证路径**（GT-1 候选路径的 Runtime 重放，证明机制不妨碍按解通关；重放通过方为真实通关证据）与**机制专项测试路径**（针对目标机制构造的专门操作序列）——断言目标不同，**不可互替**；
    - **机制专项测试路径（v0.3 细化，曦指令三）**：
      - **构造责任**：机器生成测试路径候选，**人类可补充或确认**（人签认后才作为证据）；
      - **证据要求**：逐步状态序列 + 四要素断言；
      - **不要求通关**，但必须证明目标机制**实际触发并产生预期状态变化**；
      - **无法构造合法路径时：返回 UNKNOWN 或转人工，不得静默跳过**；
    - **覆盖要求（v0.2 补）**：**每个核心机制至少有一个可观测触发断言**；
    - **断言内容四要素（v0.2 补）**：触发条件是否成立、状态变化是否发生、后续效果是否传导、最终结果是否符合预期；
    - **断言依据（v0.2 收紧）**：以**结构化状态差分**（vars / cellProps / entities）为硬断言依据；**普通文本日志（A.logs）只作辅助线索，不得作为唯一硬断言依据**；观测面是否支持完整结构化断言待验证（V-3.2）；
    - 观测面按机制类型的映射（设计参考）：

      | 机制类型 | 结构化断言观测面 |
      |---|---|
      | 状态变量型（钥匙计数、闸门闩锁） | 重放逐步 vars 序列（keys 递增、ga/gb 翻转） |
      | 格子属性型（碎裂、洞） | 逐步 cellProps 序列（crack 计数出现、hole=1 出现） |
      | 实体型（拾取、推动） | 逐步 entities 序列（key 被移除、box 位移） |
      | 事件日志型 | 仅辅助线索，硬断言须落到上述结构化面 |
  - **GT-2b 必要性诊断（v0.2 移出硬门槛；v0.3 修正比较口径）**：
    - **比较口径（v0.3 修正，曦指令四）**：反事实对比采用**可复现的结果与状态指标**——可解性三值结果、最少步数、结构化状态指标集合；**不得仅因 BFS 输出的路径字符串不同就判为中依赖**（同关卡多解下，路径差异不代表语义差异）；
    - **适用前提**：仅对**可明确隔离**的目标机制执行（机制规则可从数据中干净摘除；与其他机制强耦合时不做）；
    - **结果解释**：依赖程度分档按"结果 + 指标"解释——剔除后 UNSAT = 强依赖；PASS 但最少步数/关键状态指标改变 = 中依赖；结果与指标均不变 = 低依赖提示。**低依赖不直接断定机制是装饰**——是否合理结合 GT-3 意图核销由人类判断；
    - **UNKNOWN / 不支持处理（v0.3 补、v0.4 收紧，曦指令四）**：反事实求解结果为 UNKNOWN 或不支持时，**输出"无法判断"，不进行强/中/低依赖分级**（依赖分档只建立在确定性结果上）；反事实侧的 UNSAT 仍必须满足 GT-1 的完整覆盖与完整穷举条件；
    - **比较指标事先确定（v0.4 补）**：用于依赖分档的指标集合必须在执行反事实求解**之前**确定并留痕，**不得事后挑选**——防"先看结果再选有利指标"；
    - **定位保持不变**：非硬门槛诊断工具；成本待实测（V-3.3 保留）。
- **硬规则（v0.2 更新）**：**GT-2a 是唯一放行硬门槛**；GT-2b 已移出硬门槛、定位为诊断工具，是否实装取决于实测成本（V-3.3），不在本前置预先承诺。

### GT-3 意图符合（机器预核销 + 人类裁决）

- **判什么**：生成规则是否真的实现了 Brief 描述的玩法——不是"跑得通"，而是"跑的是用户要的那个"。
- **判据（v0.2 细化）**：Brief 拆解为**原子需求**（每条 = 一个可独立核对的最小玩法陈述，标注需求类型：核心机制/支撑规则/结果规则——类型定义见 GT-2，人类可改判），建立**逐条核销清单**，每条映射到生成规则的具体落点（对照框架 = 前置 2 §六字段映射表）。
- **职责切分**：
  - 机器**仅检查需求落点是否存在**（结构级），**不负责语义正确性**；
  - 落点语义（时序、条件、边界语义是否真符合 Brief）由人类核对——AI 自判与生成同源（规格理解同源教训），不可外包给机器；
  - **人类是 GT-3 最终放行者**。
- **审查深度与样本生命周期（v0.3 收紧，曦指令一；沿用前置 5 的 7+3 分离口径）**：
  - **7 个调优样本**：参与 **5 轮 Prompt 调试**，用于调优与问题定位；
  - **3 个独立验证样本**：只在 **Prompt 和 GT 标准冻结后**运行；其结果**不得用于本轮 Prompt 调整**；
  - **样本污染隔离规则（v0.3 补）**：若验证后据此调整了 Prompt，原验证样本即**转为调优样本**，**必须另准备新的独立验证样本**再作验证——验证样本一经污染不复位；
  - 3 个独立验证样本**全部逐条审查、不抽检放行**——每份核销清单逐条人签字。
- **逐条核销清单模板（v0.3 补，曦指令七）**：每份样本一份，八列——

  | Brief 原文 | 原子需求 | 需求类型 | 生成落点 | 预期行为 | 实际证据 | 人工结论 | 修正意见 |
  |---|---|---|---|---|---|---|---|
  | Brief 中原文摘录 | 最小玩法陈述 | 核心机制 / 支撑规则 / 结果规则 | mechanic / levels 中具体字段与条目 | 该落点应表现的行为 | 结构化断言输出 / 重放记录 | 通过 / 退回 + 签字 | 退回时必填 |

  填写分工：机器预填「生成落点、实际证据」（结构级）；人类核对「预期行为」并填写「人工结论、修正意见」；「需求类型」标注人类可改判。**人工结论列空缺 = GT-3 未通过。**

### GT-4 体验质量（人类判定 + 机器辅助指标）

- **判什么（v0.2 拆分两层）**：
  - **基础可试玩**：操作（方向键/WASD 有效）、反馈（移动与阻挡有视觉反馈）、运行（无报错、不白屏）、重开（撤销 Z / 重开 R / 换关可用）——功能性检查清单，机器可自动化其中大部分，**最终由人类确认**；
  - **体验质量**：趣味、难度、节奏、策略空间——**纯人类试玩评价**。
- **机器辅助指标（只参考，不设门槛）**：解法长度与状态空间规模之比、机制触发密度、死路/分支数量。这些指标与"有趣"的**相关性未经验证**（V-3.5），不得据其自动通过或否决。
- **判定方式**：人类试玩（先基础可试玩清单、后体验质量评价）。**最终裁决权：人类**。
- **能力口径声明（v0.3 补，曦指令六）**：基础可试玩的机器自动化检查属于 **G1 待建设目标**；当前 Spike 的 8/8 autoplay 只证明 **BFS 解法路径在运行时重放通关**，**不代表基础可试玩检查已实现**——两者不得混同表述。

## 三、职责矩阵（本文核心交付，v0.2 更新）

|---|---|---|---|---|---|

**总原则四条（v0.2 更新原则 2）**：
1. **递进拦截**：GT-1 → GT-2 → GT-3 → GT-4 串行，机器层失败不消耗人审资源；
2. **机器负责可形式化、可独立观测的事实**（可解性、结构化触发断言）；**人类负责需求语义和体验价值**；**机器证据不足时由人类裁决**（UNKNOWN 即证据不足，不得放行）；
3. **任何单层通过都不等于整体合格**；BFS 通过 ≠ 游戏合格，机制触发 ≠ 意图符合，意图符合 ≠ 值得玩；
4. 机器结论必须带**建模范围/断言范围声明**，禁止越界表述；自动建模覆盖不了的语义必须显式返回 UNKNOWN 或不支持，禁止静默放行。

## 四、与生成链路和预算的衔接（设计级，不实装）

- **拦截-重试衔接**：GT-1/GT-2 失败回到生成环节重试（机器层拦截）；重试引发的请求与预算消耗按下方口径列示与兜底；
- **样本执行与预算口径（v0.4 修正统计单位，曦指令一；单位不得混用）**：
  - **任务口径**：7×5 + 3×1 = **38 个完整生成任务**（7 个调优样本 × 5 轮 Prompt 调试 + 3 个验证样本 × 1 次）——单位是**生成任务**，不是 API 请求；
  - **请求口径**：**每个候选模型分别执行 38 次生成任务**；按每次生成期望 **4.8 次** API 请求计算，**38 × 4.8 = 182.4 次/模型**；两个候选模型合计期望 **364.8 次** API 请求；
  - **口径隔离**：原 **240 次/候选模型**（前置 5 核定时的请求估算口径 = 10 个 Brief × 5 轮调试 × 每次生成期望 4.8 次 API 请求）与新 **182.4 次/模型**（本轮预期请求量）是不同口径的两组数字，**不得混用**；
  - **22 元 = 已核定的保守预算上限**，本文**不修改原核定**；实测回填（V-3.6）；
- **评测样本分离**：沿用前置 5 的 7+3 分离口径——GT 标准的调优样本与验收样本分离，防标准过拟合；样本生命周期与污染隔离规则见 GT-3；
- **与 MU 链路的关系**：MU-2/MU-3 的 Schema 校验闸门（前置 2）是 GT 的上游前置；GT 四层构成 MU-10"新机制生成"验证的**质量半边**（结构合法半边已由前置 2 承担）。
