## 为什么单独记这一份

访谈最容易的结局是「聊得很愉快，然后写进记录，然后没有然后」。

这份文件做的是另一件事：**把他描述的工作机制，直接翻译成可执行的检查项。** 这样访谈的产出不只是文字，是可以跑的东西。

## R-01 活动/任务必须声明解锁条件

| 项 | 内容 |
|---|---|
| 来源 | F7「每个关卡有一个锚点」、F8「打完前置任务才能认识」 |
| 检查 | 每个活动或支线任务，必须显式声明 `unlock_condition`（前置任务 ID 或玩家进度门槛）。为空则告警。 |
| 为什么重要 | 没有声明不等于没有门控，只等于门控在脑子里。而脑子会漏。 |
| 实现难度 | 低。字段必填校验。 |
| 误报风险 | 中。有些任务确实无门槛（主线第一环），需要 `unlock_condition: none` 这个合法值。 |

---

## R-02 解锁条件引用的对象必须存在

| 项 | 内容 |
|---|---|
| 来源 | 同上 |
| 检查 | `unlock_condition` 引用的任务 ID / 剧情节点 ID / 变量，必须在同一项目内存在且版本一致。 |
| 为什么重要 | 引用不存在的对象，是「玩家永远触发不了」最常见的原因。 |
| 实现难度 | 低。引用完整性校验。 |
| 误报风险 | 低。这是硬错误。 |

---

## R-03 角色关系必须双向

| 项 | 内容 |
|---|---|
| 来源 | F9–F10「与主角发生的关系」「身边是否存在其他朋友」 |
| 检查 | 若 A 的关系列表包含 B，B 的列表必须包含 A；若一方标注为「朋友」，另一方的对应档位不能是「陌生」。 |
| 为什么重要 | 单向关系是设定冲突的典型形态：她认识他，他的剧情里却没有她。 |
| 实现难度 | 中。需要先有「关系档位」的枚举定义（F 未确认是否有固定档位）。 |
| 误报风险 | 中高。单向关系有时是设计意图（暗恋、监视、单方面认知），需要「允许单向 + 注明理由」的例外机制。 |

---

## R-04 角色出现次数与剧情节点计数一致

| 项 | 内容 |
|---|---|
| 来源 | F9「女角色在游戏中出现的次数」 |
| 检查 | 若角色声明 `planned_appearances = N`，则统计所有剧情节点中该角色的出场次数，与 N 比对；不一致则提示。 |
| 为什么重要 | 「出现次数」是他明确说的维护维度，说明这个数字会被用来判断角色重要度与戏份。 |
| 实现难度 | 中。需要定义「出场」的判定口径（被提及算不算、回忆算不算）。 |
| 误报风险 | 高。口径不清就会天天误报，必须先定口径再实现。 |

---

## R-05 新角色的引入事件必须早于其首次出场

| 项 | 内容 |
|---|---|
| 来源 | F11「通过事件认识新角色」 |
| 检查 | 若角色 R 的 `introduced_by_event = E`，则 E 必须在所有 R 出现的节点之前可达；若 R 在某节点出现但 E 尚未发生，报「角色提前出场」。 |
| 为什么重要 | 这是「角色说了他不该知道的事」「角色出现得太突然」的结构性成因。 |
| 实现难度 | 中高。需要事件与节点的时序关系，本质是图上的先后判定。 |
| 误报风险 | 低。逻辑上成立即成立。 |

---

## R-06 剧情节点必须显式映射到关卡（或标注无关卡）

| 项 | 内容 |
|---|---|
| 来源 | F6「这一步怎么和关卡去做切分」 |
| 检查 | 每个剧情节点必须有 `level_id` 或 `level_id: none`；反向检查每个关卡是否至少被一个剧情节点引用（避免「关卡做了但剧情没接上」）。 |
| 为什么重要 | 他明确说切分要花时间思考，说明这个映射现在是人工维护、没有对照表。 |
| 实现难度 | 低到中。字段 + 双向引用检查。 |
| 误报风险 | 低。但需要先确认他们的剧情节点和关卡是不是一对一、一对多还是多对多。 |

## 六条的分布说明什么

| 检查类型 | 规则 | 数量 |
|---|---|---|
| 结构与引用完整性 | R-01、R-02、R-06 | 3 |
| 关系一致性 | R-03、R-05 | 2 |
| 计数与统计 | R-04 | 1 |

**三条属于「引用完整性」类**——这类是确定性检查，实现简单、误报低，而且现有工具基本不做（它们查图，不查剧情与角色的引用关系）。

**这正是差异化能落地的地方**：不是比谁的图论算法强，是比谁懂「剧情里哪些东西必须互相引用」。
