Case Study　2026.11

AI 游戏设计工作台
把设计对象之间的引用关系，变成可检查、可交接的东西

面向游戏策划的 AI 辅助工作台。核心不是生成内容，而是回答一个问题： 改了一个设计对象之后，还有哪些地方要跟着改，谁改。

阶段：可运行产品 v0.2（切入点内功能齐） 访谈：5 份（游戏行业 3 份）+ 7 例公开事故 产品：命令行 + 本地工作台　原型并入产品：3 / 3 测试：157 个，全绿　变异评测检出率：4/5 角色：独立完成（研究 / 设计 / 开发 / 测试）

一、问题从哪来 不是猜想，是三个人说出来的

「每个关卡都有一个锚点，你需要触发这个锚点之后，才能引出下一步……这个 NPC 你只有打完前置任务才能认识。」 叙事关卡策划 · 小型团队
「出了新的机制我们会考虑是否能和之前已有的机制做联动，这个需要重新做设定，一般靠灵光乍现。」 放置类活动策划 · 中型团队
「长期更新的项目，剧情积累越多越容易出现细节遗漏。」 剧情策划 · 大型团队
公开案例（2025-10，台服端游）：福袋公告里的奖项名称与数量写错，厂商确认「系統運作無異常」——系统没错，错在公告，仍要对期间购买者统一补偿。
另一例的整改办法更能说明问题：某厂公告把 100000 写成 10000，补发并开放退款之后，改进措施是「在数字后面加中文大写（如 100000（十万））」——防错落在了写公告的人身上。（这只能说明业内有这种人工关卡，不能说明他们没有别的校验工具。） 这类问题的成本几乎全在「找出哪里没同步」，而不在「改」。

二、做了什么 三个能跑的东西，不是三份方案

① 路径条件可满足性判定 三态

给定任务图与状态变量，判断某个结局是否真的能被触发。输出不是「通过 / 不通过」，而是 SAT（存在合法路径）/ UNSAT（不存在）/ UNKNOWN（搜索触顶）。

UNKNOWN 不降级为通过——这是它和普通校验工具最大的区别。

实测：四个用例分别命中 SAT / UNSAT / UNKNOWN / SAT，UNSAT 会指出阻断边与变量观测到的最大取值。✅ 已并入产品内核（gdw/quest.py，命令行 + 工作台均可调）。
② 任务结构检查报告 可读诊断

一条 16 节点、3 个变量、3 个结局的完整支线，被查出 3 处设计错误。

其中一处是循环依赖：进「守林人草棚」要求「见过守林人」，而「见过守林人」只有进了草棚才会获得——要进去才能得到，要得到才能进去。

输出：不是「不可满足」，而是「差 1 条线索，卡在 n2 → hidden_end 这条边」。能修的诊断才有人用第二次。✅ 已并入产品内核（gdw/structure.py，S1–S5 五类结构检查，移植时还新发现一处原报告漏掉的设计错误）。
③ 配置变更影响分析 可交接

改一个活动数值，系统列出所有引用它的下游对象（排行榜、发奖邮件、公告、客服 FAQ），区分「已同步」和「待确认」。

最有力的一屏：规则全部通过，但仍有 3 处没同步——合规与一致是两个问题。

输出：一份可粘进群的变更确认单，逐项列负责人空位。从「检查器」变成「派活的东西」。

二·五、从原型到产品 同一个下午：内核、压测、界面、用户实测修复

原型证明"能做"，产品才谈"有用没用"。变更影响分析被验证后，我把它的内核重写成了一个 带 157 个测试的 Python 包：命令行 + 本地工作台，读真表、扛脏表，当天被第一位用户实测抓出 bug、当晚修复。 随后另两个原型也并入同一内核，并用变异评测给检查器出了第一份定量成绩单。

④ 本地工作台 上传 → 改数 → 勾选 → 导出

一条命令 python -m gdw web 起一个本地工具：拖入任意配置表（xlsx / yaml / json）， 每个字段可直接改，点一下算出影响面，逐项勾「已同步」，导出带勾选状态的确认单。

扛脏表：合并单元格标题、表头不在第一行、中文表头、数字存成文本、引用分隔符混用—— 用一份故意做脏的表压测并钉进测试。

数据入口：xlsx / yaml / json 三种；跨表引用支持多跳 （改道具名，引用它的浮窗和掉落预览会一起进影响面）。零第三方运行时依赖。
⑤ 一键确认单报告 先说人话，再看字段

跑一条命令得到自包含网页：开头一段自然语言（改了什么、哪里不对、谁得跟着动——按负责人分组）， 后面才是规则表和字段路径。来源分层展示，不把 8/8 合成一句话。

勾选框是真实的——收件人直接勾，打印出来就是纸面确认单。

实测记录：上线第一天用户抓到「换规则包清空配置、页面却不刷新」的状态错位 bug， 当晚修复并把新语义钉进测试。设计对不对，要等有人真的走一遍才知道。

v0.2 追加（2026-11-11）：任务可达性三态与结构检查并入同一内核（三原型 3/3）； 新增变异评测——往任务图基准里注入 5 处确定性破坏，强检出 3 / 仅提示 1 / 漏报 1（如实报告并写明原因）， 检出率 4/5；工作台补上勾选状态落盘（重传同一配置自动恢复）与两版本一键 diff。 到此切入点内功能收口，后续迭代只等真实使用反馈。

三、验证到哪一步 诚实标注，不凑结论

表里只回答「我知道什么、不知道什么」。事故证据（问题存在）和能力证据（原型做到什么）分开看——两组材料不互相顶替：公开事故证明问题真实，证明不了原型有用。

假设状态依据与限制
V-01 设计对象之间存在需要人工维护的依赖 已验证 一位活动策划明确描述了「改奖励人数后，回头查排行榜、邮件、公告」的实际动作。
V-02 这种维护会漏，且漏了有后果 已验证仅问题层 五例公开事故公告（剑网一 / 三国群英传2 / 武林同萌傳 / 龙图智库 / 全民小镇），厂商自认「公告与实际不一致」并补发、退款、甚至把实际概率永久上调。限制：五例全部发生在运营公告环节，没有一例是策划改配置表后下游没跟。证明的是「不一致会发生且有代价」，不是「策划岗普遍如此」，更不是「本原型能解决」。
V-03 现有方式需要持续人工投入 已验证 核对依赖「配置表 + 需求文档 + 历史版本」逐项进行，有载体但检查动作由人完成。这条是独立证据（访谈），不由 V-02 代替。
当前组合：A——依赖存在、会漏、漏了有代价、且现在靠人维持。但 A 只成立在「问题层」：不包含岗位层（策划侧只有一位受访者口述），也不包含方案层（原型价值未验证，见第四节第 4 条）。 能写到这一步：问题真实存在且有成本。不能写「策划岗普遍如此」，也不能写「现有工具能解决」。

四、边界 这些是限制，不是待办

只做显式依赖影响分析只沿「已登记」的引用推导。文案里写死的数字、公告图、截图里的旧数值，本版查不出来。
数据是分层的口述 / 模拟 / 推断三层标注。服务器人数、占比区间等都是占位值，不能当真实业务规则使用。
样本只有 1 份有效访谈来自一位活动策划。其他两位岗位不同，不能合并成「受访者普遍认为」。
公开事故不在本版的能力范围内五例事故的错都长在「公告里手写的数字和描述」上，而本版只检查已登记的字段引用。问题最密集的地方，正好在它的边界外——这是下一版要解决的，不是已经解决的。
v0.1 已冻结边界到这里为止，不再为了多覆盖几个案例而扩功能。「让配置直接生成公告」记进下一版候选池，先不动手。
下一步：v0.1 就地冻结（2026-11-10）。两件事按顺序：① 用一份真实或脱敏的活动配置表替换模拟数据，验证 Schema 与规则能否迁移； ② 问清「公告是模板套字段、还是每次手写」——这句话决定边界要不要改。在此之前不扩功能。
