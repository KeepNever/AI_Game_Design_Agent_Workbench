## 一、为什么做这个样例

S2 第一轮三份游戏行业样本（叙事关卡、放置活动、大厂剧情）呈现同一条线索：**设计对象之间存在引用关系，改一处要知道哪些下游要跟着改。** 这一条比「生成一份策划案」更值得优先验证，因为它同时解释了三类岗位的返工。

放置类活动策划提供了唯一带真实数字的样本，适合当第一个载体：

| 他给出的 | 可检查性 |
|---|---|
| 产出比 1:10:100 | 纯算术，误报极低 |
| 头奖只有一个 | 计数判定 |
| 中档要有固定人数 | 声明值与配置值比对 |
| 其余奖励按服务器人数比例 | 推导式校验 |
| 固定活动按开服天数推进 | 门槛判定 |
| 提前一个月排期 | 排期约束 |

六条里有五条可以直接写成程序规则，这是选它而不选叙事场景做第一版的唯一理由。

## 二、字段与来源（三层标注，不能混）

| 字段 | 值 | 来源 | 说明 |
|---|---|---|---|
| `activity.type` | 固定循环活动 | **口述** | 「固定活动是每个服务器都要有的，根据开服那天往后推」 |
| `activity.lead_time_days` | 30 | **口述** | 「节庆要在开始前一两个月安排……也按照一个月左右」 |
| `activity.open_day_min` | 30 | 模拟 | 口述只说按开服天数推进，未给阈值 |
| `activity.server_open_days` | 45 | 模拟 | 用于验证门槛规则 |
| `activity.server_population` | 1200 | 模拟 | 口述提到按人数做比例，未给人数 |
| `activity.duration_days` | 7 | 模拟 | — |
| `tiers[].ratio` | 100 / 10 / 1 | **口述** | 「占比在 1:10:100」 |
| `T_HIGH.count` | 1 | **口述** | 「最厉害的那个……只能出现一个」 |
| `T_MID.count` | 5 | 模拟 | 口述只说「要有固定的人数」，未给数字 |
| `T_MID.declared_count` | 5 | 模拟 | 用于检查「声明的口径」与「实际配置」是否一致 |
| `T_MID.quota_pct_min/max` | 0.3% / 0.6% | 模拟 | 口述说「占比不能高也不能低」，未给上下界 |
| `T_LOW.population_ratio` | 0.1 | 模拟 | 「其他奖励按当前服务器的人数去做比例判断」 |
| `downstream[].refs` | 见 JSON | **推断** | 下游对象的存在有口述依据（见下），具体字段引用为推断 |

### 下游对象的口述依据

样本 04 讲过一次事故：国庆活动，三十几个玩家打完活动 boss 没拿到奖励，但排行榜上有名次，最后靠补发解决。

这条案例能说明的是：**榜单状态与奖励发放曾经出现过不一致**，因此把排行榜列为关联对象有事实依据。

但它**不能**直接证明排行榜引用了某个具体配置字段——「榜上有名、手上没有」也可能来自发奖流程、邮件队列、结算时序，不一定是配置字段的引用。所以 `OBJ_RANK` 的**存在**有事实依据，**具体字段引用仍待验证**，仍标 `infer`。

其余五个对象（公告、商店、邮件、掉落、FAQ）是按常识补的，全部标 `infer`。**在拿到真实配置表或脱敏样例之前，它们只能算假设。**

## 三、这份样例不能证明什么

1. **不能证明真实项目的字段结构。** 真实活动配置表有几十上百个字段，这里只留了与「变更影响」相关的 8 个。
2. **不能证明规则是行业通用的。** 1:10:100 是一个受访者的说法，不是规范。
3. **不能证明下游对象就这么几个。** 六个对象是推出来的，不是数出来的。
4. **不能证明系统能自动发现依赖。** 本版做的是**显式依赖检查**：只沿配置里已经声明的引用关系推导影响面。文案里手写死的数字、公告图上的旧数值、截图里的比对，这类隐式依赖查不出来，也**不能写成已具备的能力**——它是另一个待验证问题。
5. **不能证明 8 条规则都是行业规则。** 其中 4 条来自口述、3 条是原型自建的工程规则、1 条的阈值是模拟值。分层见 RulePack 文档。

## 四、下一步怎么用

- 拿这份数据去问受访者：「你们的活动配置表长这样吗？多了什么、少了什么？」
- 拿原型里的四个用例去问：「用例 04 这种规则全过但三处没同步的情况，你们实际会遇到吗？」
- 得到真实字段后再扩 v0.2，**不要在没有样例的情况下继续加字段**，那只会把假设堆得更厚。

## 五、怎么给别人用（v0.1 的完整回路）

1. 原型打开「用例 05 自己改一个数」→「导出 JSON」，得到一份符合本 schema 的配置（含 `activity` / `tiers` / `downstream`）。
2. 把这份文件发给策划，让他把里面的数字改成他们真实的（或者他愿意公开的那部分）。
3. 他改完传回，用「导入配置」读回原型，立刻能看规则判定和影响面。

**导入会换掉基线**：之后所有「变更」都是相对这份导入配置算的，不再是相对内置示例。
卡片右上角会显示当前基线来自哪个文件。

导入校验只认 v0.1 schema（固定三档 T_HIGH / T_MID / T_LOW + `activity.server_population`）。
字段对不上会直接报错，不会静默忽略——这是故意的：schema 不一致却照跑，比报错更危险。

**还没做的**：真实表结构是几十列，本 schema 只有 6 个可变字段。导入只是让这一版能闭环，
不等于支持真实配置表。真表结构要拿到样例再定。
