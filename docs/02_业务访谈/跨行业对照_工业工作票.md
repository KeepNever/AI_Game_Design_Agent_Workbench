# 跨行业对照：工业工作票 ↔ Quest 任务包

> 样本：汽机（汽轮机）检修方向从业者口述，1 人。
> 采集：2026-11-08，聊天中获取，**回忆整理，非同步记录**。
> 性质：跨行业对照案例。**不能用来证明游戏策划有痛点**，只能用来验证「结构化产物 + 分级确认 + 留痕」这套设计在别的高要求行业里是否成立。

---

## 一、对方描述的工作流

要检修或调整某个设备 → 先办工作票 → 办完才能去拿对应工具。

票面必填项（对方提到的）：

- 监护人
- 第一负责人
- 安全条件（含所需工具等）
- 危险条件（危险点）

配套机制：

- 安全措施清单**提前写好、上报批准**，清单由老师傅编制
- 签发与许可环节有四到五个人签名
- 有 ERP 系统，同时保留纸质与电子记录

**未获取的信息**：是否出现过措施漏项、漏了谁发现、后果如何（对方未谈及，不补写）。

---

## 二、字段对照

| 工作票 | Quest 任务包 | 同构点 |
|---|---|---|
| 第一负责人 | 任务负责人 | 必须有唯一责任人 |
| 监护人 | 审核人 | 监督角色，不是执行者 |
| 作业内容 | 任务目标 | 要做什么 |
| 设备 / 位置 | 涉及地点、NPC | 作用对象 |
| **危险点** | 禁止事项 | **显式声明哪里会出事** |
| **安全措施清单** | 前置条件 / 约束条件 | **必须逐项满足才允许执行** |
| 所需工具 | 前置道具 / 资源 | 执行依赖 |
| 签发（4–5 人签名） | 分级审核 | 不同角色分别确认 |
| 许可 | 导出前校验放行 | 系统校验 + 人确认 |
| 终结 | 验收 | 完成判定 |
| 纸质 + 电子双留痕 | 版本记录 | 可追溯 |

## 三、三个可以直接借的设计点

### 1. 措施清单是「预编制」的，不是每次现想

老师傅先把安全措施写好，上报批准，之后成为标准清单。

**对应到你的产品**：校验规则不该每次由 AI 现生成，而应该是**预先定义、版本管理、可复用的规则集**。你的 Q001–Q013 就是这个东西。工业界的做法印证了这个设计不是多余的抽象，而是必需——因为临时想的措施一定会有漏项。

**可以直接写进方案的一句话**：规则库不是产品的实现细节，是产品能成立的前提。

### 2. 「危险点」是必填项，不是隐含信息

票面上单独一栏叫危险条件。这意味着一份合格的作业凭证，必须**显式说明哪里可能出事**，而不是默认读者自己知道。

**对应到你的产品**：Quest Brief 里的「禁止事项」字段，工业实践直接印证了它的必要性。而且可以更进一步——不只写禁止什么，还要写**为什么禁止**，否则 AI 生成时会绕开字面但违反意图。

### 3. 纸质与电子双轨，说明产物要能落进旧流程

对方单位有 ERP，但仍然保留纸质记录。

这条最有价值，也最容易被忽略：**再好的系统，短期内也没法取代既有的签字与归档习惯。**

**对应到你的产品**：导出 Markdown / JSON / CSV、而不是要求用户搬进一个新平台，这个决定是对的。产品定位应该是「嵌入现有工作流的辅助层」，不是「替代现有系统」——这和文档 2.3 得出的竞品结论完全一致，现在又多了一个跨行业例证。

---

## 四、四到五个签名说明什么

一开始我以为这是流程冗余。想清楚之后不是：

- 不同签名对应不同责任：谁编制、谁审核、谁许可、谁执行
- 每一层签字都是一次独立判断，不是重复确认
- 责任可追溯到具体的人

**对应到你的产品**：文档 10.3 列的五个人工确认点，结构上和这套签字制度是同一件事。你可以在作品集里直接说：分级确认不是流程繁琐，是让每一层判断都有责任人。

---

## 五、这份材料能用在哪儿

**能用**：

- 证明「结构化产物 + 分级确认 + 留痕」是跨行业通用的设计范式，不是产品经理的臆想
- 为「规则库必须预定义」「禁止事项必须显式」「导出而非替换」三条设计决策提供外部依据
- 面试时讲产品设计依据，比讲界面好看有说服力

**不能用**：

- 证明游戏策划存在这些痛点
- 证明你的具体字段设计是对的（工业与游戏的对象不同）
- 当作「用户研究」——这是 1 人、跨行业、回忆整理

**报告里的正确写法**：

> 在设计任务包结构与确认流程时，参照了工业工作票制度的组织方式（1 位汽机检修从业者口述，2026-11-08）。该制度以固定票面字段、预编制的安全措施清单、四至五级签发许可和纸质电子双留痕为核心。本项目据此确认三项设计决策：规则集预定义、禁止事项显式化、产物导出而非替换现有流程。跨行业样本仅用于设计参照，不作为游戏策划痛点的证据。

## 七、第二个案例：高压电工的操作票与唱票

> 样本：高压电工，1 人。采集 2026-11-08，聊天中获取，回忆整理。
> 与汽机的工作票构成一对：**工作票管「修」，操作票管「倒」。**

## 7.1 两个案例的分工

| | 工作票（汽机检修） | 操作票（高压电工倒闸） |
|---|---|---|
| 触发场景 | 要在某台设备上作业 | 要改变设备运行状态 |
| 核心问题 | 这个地方现在**允许**动吗 | 这一步现在**能做**吗 |
| 产物 | 工作票 | 操作票 |
| 保障方式 | 安全措施清单 + 多级签发 | 唱票、复诵、监护执行 |
| 节奏 | 一次性审批，全程有效 | **逐项确认，一项一做** |

## 7.2 三栏对照

| 环节 | 工作票 | 操作票 | 你的产品 |
|---|---|---|---|
| 触发 | 要修设备 | 要倒闸 | 收到设计需求 |
| 产物 | 票面（固定字段） | 操作票（逐项列表） | Quest 任务包 |
| 前置校验 | 安全措施清单，预编制 | 设备状态确认 + 五防 | Q001–Q013 + 前置条件 |
| 确认方式 | 4–5 人签发许可 | 唱票 → 复诵 → 监护执行 | 分级人工确认点 |
| 执行粒度 | 按票作业 | **逐项操作、逐项打勾** | 逐节点生成 |
| 收尾 | 终结、验收 | 操作完毕汇报 | 导出前全量校验 |

## 7.3 唱票复诵对应的三个设计点

### 1. 逐项确认，而不是最后一起查

操作票是一步一确认的：唱一项、做一项、勾一项。不是全部做完再回头检查。

**对应到你的产品**：校验不该只在导出时做一次全量检查。你的 10.3 已经分了四个确认点（需求解析后、结构生成后、语义检查时、导出前），方向是对的——**工业界用几十年的实践证明了「分段阻断」比「终检」可靠**，因为越晚发现问题，返工成本越高。

这条可以作为「为什么要在中间插入人工确认」的直接依据。

### 2. 唱票复诵 = 用另一双眼睛、另一种方式重复一遍

一个人念，一个人做，一个人核对。同一件事被说了两遍、做了两遍。

**对应到你的产品**：AI 给出检查结论后，要求人复述确认（「我看到的问题是 X，你确认吗」），而不是让人在一堆结果里点个「全部接受」。**冗余不是为了保险，是因为单一通道一定会漏。**

这正好解释了你文档里为什么写「不能让生成模型自己给自己打分」——单通道的自我确认在工业界是被明令禁止的。

### 3. 倒闸操作本质是状态迁移

运行 → 热备用 → 冷备用 → 检修，每一次迁移都有前置状态要求。状态不对，操作就不允许。

**对应到你的产品**：这就是 Q013 的现实版。差别在于工业界的设备状态是有限且明确的（就那么几种），而任务的状态变量是设计者自己定的——**所以你必须先约束变量的定义域，才能做可满足性检查。**

这一条从外部印证了你 12.5 里「变量域必须显式声明」的规定，不是多余的约束，而是能在工业界找到同构做法的必要前提。

## 7.4 报告里可以这么说

> 除工作票制度外，另参考高压电气倒闸操作的操作票流程（1 位高压电工口述，2026-11-08）。该流程以逐项唱票、复诵核对、监护人确认执行，且每一步都有前置状态要求。本项目据此确认三项设计：校验分段进行而非终检一次、AI 结论需人工复述确认、状态变量必须显式声明定义域。上述为跨行业设计参照，不作为游戏策划场景的证据。
