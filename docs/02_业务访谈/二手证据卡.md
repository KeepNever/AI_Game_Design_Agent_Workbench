## 一、什么算二手证据

**收：描述了「谁、在什么情况下、具体怎么做的」的材料。**

- 从业者自己写的「我做一条任务的完整流程」
- GDC / 开发者大会演讲里的真实管线案例
- 游戏设计教材里的流程拆解与失败案例
- 招聘 JD 里对「任务设计 / 配置表 / 评审」的职责描述
- 工具官方文档里的工作流说明（它假设用户怎么用）

**不收：只有观点、判断、预测的材料。**

- 「AI 将颠覆游戏策划」这类趋势文
- 「十个提升效率的技巧」这类列表文
- 厂商宣传页（aricy 说自己能做什么 ≠ 用户实际怎么用）
- 没有署名的搬运内容

**判断方法**：读完问自己一句「这里面有没有一个具体的人在做一件具体的事」。有就收，没有就丢。

## 二、证据强度分三级

| 等级 | 定义 | 用法 |
|---|---|---|
| A · 一手自述 | 从业者以第一人称讲自己怎么做 | 可单独支撑一条假设 |
| B · 二手转述 | 媒体或第三方描述某个团队怎么做，有具体细节 | 需两条互相印证 |
| C · 厂商材料 | 工具商/服务商描述客户用法 | 只能用来判断「工具已具备什么」，不能证明痛点 |

**两个 C 级不能凑成一个 A 级。** 这是最常见的自欺方式。

## 三、证据卡模板

每条材料一张卡，编号 E-01 起。存成一张表，或每条一个 md 文件都行，字段不能少。

| 字段 | 说明 |
|---|---|
| 证据编号 | E-01 |
| 采集日期 | 你看到它的日期 |
| 来源类型 | 从业者自述 / GDC演讲 / 设计书 / 招聘JD / 工具文档 / 媒体 |
| 标题 | 原文标题 |
| 作者与身份 | 谁写的，他是什么岗位——这决定证据等级 |
| 链接 | 原始链接，不要只存截图 |
| 发布日期 | 材料本身的日期，用于判断是否过时 |
| 证据等级 | A / B / C |
| 原文摘录 | **一段原文，逐字复制，不改写。** 这是整张卡的核心 |
| 支持的假设 | H-01a / H-01b / H-02 / H-03 / H-04 |
| 关键数字 | 材料里出现的频率、耗时、返工次数，没有就写「无」 |
| 局限 | 哪个品类、哪个规模团队、是否过时、作者是否利益相关 |

## 四、采集纪律

1. **只摘不改。** 一旦用自己的话转述，就变成了你的推断，不再是证据。
2. **必须记作者身份。** 一个执行策划的自述和一个培训机构讲师的文章，分量完全不同。
3. **必须记日期。** 2019 年的工作流文章，不能用来描述 2026 年的现状。
4. **每条只服务一个假设。** 一条材料想支持三个假设，通常三个都支持不牢。
5. **每个假设至少两条独立来源。** 同一作者的两篇文章不算两条。
6. **C 级材料单独归类。** 它们的用途是「判断竞品已具备什么」，不是「证明用户痛点」。

## 七、什么时候算「够了」

单条假设达到下面任一条件，可以停止对这条的二手采集：

- 2 条 A 级来源互相印证；或
- 1 条 A 级 + 2 条 B 级；或
- 4 条 B 级，且分别来自不同团队、不同品类

**达不到，就在报告里写「该假设未验证」，不要凑数。**

## 八、报告里怎么写

正确的写法：

> 本阶段完成一手访谈 2 次（RPG 任务策划 1 名、独立开发者 1 名），公开材料研究 7 条（A 级 2 条、B 级 4 条、C 级 1 条）。受样本规模限制，H-01a 判定为「已验证（弱）」，H-03 判定为「未验证」，原因是一手样本中仅 1 人提供了带三要素的冲突案例，未达判真门槛。

错误的写法：

> 通过调研，我们验证了策划在任务设计中存在高频痛点。

第二句没有任何信息量，而且暗示了一个你没做到的事。

| 证据等级 | A（开发者第一人称讲自己的制作流程） |
| 支持假设 | H-03 内容相互牵连导致后续修改；H-04 前提 |

**原文摘录**

> 举个抽象的例子：一个用于配置电脑玩家的新工具被集成到项目中。这个工具可以更灵活地定制由 AI 操控的角色，但这意味着所有任务中的所有的电脑玩家都必须再次进行调整。全局改动可能影响项目中的很多方面。这就是为什么我们持续会对旧任务的错误进行修复。

**它说明什么**：这是目前最扎实的一条。它证明「改一个机制 → 所有存量任务要跟着改」是真实存在的成本，而且团队靠人工回头修。这正好是你产品能切入的位置：不是生成新任务，而是**在改动发生后定位受影响的旧任务**。

**局限**：射击品类（Caliber 是战术射击），任务结构与 RPG 支线不同；不能直接外推到 RPG。

## 这一轮的缺口（比收获更重要）

**1. 没有任何一条材料带着「耗时」或「频率」数字。**

H-01a 的判真条件要求「每周不少于 3 次」或「单次不少于 30 分钟」这类具体数字。七条材料一条都没有。这意味着 **H-01a 目前仍是「未验证」**，二手材料只能证明「步骤存在」，不能证明「高频」。

**2. 你最想验证的那件事——任务结局不可达——在公开材料里没有策划侧记述。**

我专门搜了「隐藏结局触发不了 / 条件未满足 / 分支死路」，返回的全是玩家攻略站，讲玩家怎么排查、怎么读档，没有一篇是策划讲「我们怎么保证结局一定能触发」。

这件事有两层含义：
- 坏消息：Q013 这个卖点缺少公开证据支撑，你现在讲它会显得像自己想出来的。
- 好消息：**正因为公开材料里没有，一个真实访谈案例的价值极高。** 如果你能问出一位策划亲口说「确实有过结局触发不了、最后是玩家反馈才发现」，这一条就能撑起整个产品的立论点。

所以这条不要用二手材料凑，留着等访谈。

**3. 全部材料都指向「流程」，没有指向「具体错误长什么样」。**

七条里没有一条给出真实的错误样例（哪条任务、哪个条件、怎么错的）。这类材料几乎不会公开——它涉及未上线内容。这也是为什么访谈里「要一份脱敏样例」比问十个问题都值钱。

## 这批材料的整体判断

**十个问题里，三个的答案是「通常」「常见」「行业中存在」。**

这说明一件事：**公开领域确实没有更细的东西。** 谁在什么条件下改了什么、花多久、谁发现的，这些只在人脑子里。

- 「一位叙事关卡策划描述了他的实际做法」→ 放用户研究

# 附录 C：火影忍者手游「策划说」检索（2026-11-08）

> 来源：官方策划直播的玩家转述与官方栏目文章。**证据等级 C（厂商口径 + 玩家转述）**，只能证明「机制存在」，不能证明「痛点强度」，不得当作策划本人自述引用。

## C-01 改动分两类，且互相挤占精力

大版本更新包含两部分：**忍者平衡性调整** 与 **体验优化（通用规则、金刚体时长等）**。玩家与转述均指出，后者的工作量会挤占前者。

- 有价值之处：说明「改动」不是一件事，而是两类——**个案调整**与**规则调整**。规则调整的影响面是个案调整的数倍。
- 不能引用之处：「精力有限」是玩家推测，不是策划原话。

## C-02 「通用规则」是跨对象共享的

原文提到「一大部分都是通用规则或者判定高度的变化」。

- ★这是本批最重要的一条：**存在一类规则，改动它会同时影响所有对象**（所有忍者）。
- 与本项目的关系：这正是「变更影响面」问题的现实形态——改一条通用规则，谁受影响无法预先列出。

## C-03 跨组改动时「不会想太多」

转述中策划提到：策划在自己项目组内会考虑得更全面；若不在该项目组，其他策划改动时「可能不会想太多」。

- ★这条指向一个具体缺口：**改动者不掌握被改对象的完整上下文**。
- 证据等级：C。属于转述，且语境是回应「护犊子」质疑，不能过度解读为流程缺陷。

## C-04 设计方法是个案定制的

多位策划的设计特征是「用特殊机制还原角色特色，以技能效果调控强度」，每个忍者单独设计。

- 说明：战斗策划的工作是 **case by case 的机制设计**，不是套模板。因此「机制冲突」不是规则能穷举的，需要逐对检查。

## 对本项目的意义

三条独立来源（叙事关卡策划、放置类活动策划、火影战斗策划）指向同一个结构：

| 来源 | 对象 | 问题形态 |
|---|---|---|
| 叙事关卡策划 | 剧情、角色、关卡 | 锚点前置、承接关系、剧情关卡映射 |
| 放置类活动策划 | 机制、活动、奖励 | 新机制与旧机制联动，靠灵光乍现 |
| 火影战斗策划 | 忍者技能、通用规则 | 改通用规则影响全体；跨组改动缺上下文 |

**共同点：改一处，怎么知道影响了哪些地方。**
**差异点：对象不同（内容 / 数值 / 机制），规则无法通用。**

这与 S4 草案的判断一致，并进一步支持把产品定位从「品类模块化」调整为「变更影响分析」。

**它说明什么**：整改措施是「在数字后面加中文大写（如 100000（十万））」——一种**人工防错**手段，让写的人多核一遍。

⚠️ **不能推得更远。** 这条只能证明「公开材料里提到了一种人工复核 / 防错措施」。公告既没说他们有没有自动校验，也没说公告是不是从配置生成的。**不能据此推断厂商完全依赖人工，更不能拿它当 V-03 的证据**（V-03 要的是「现在靠人持续投入」的独立证据，出处是访谈记录 04）。

**局限**：小厂；公开披露只到「整改措施」这一层，内部工具形态完全未知。

## 这批的证据力：能判什么，不能判什么

**汇总**

| 编号 | 载体 | 是不是"下游未同步" | 有没有后果 | 等级 |
|---|---|---|---|---|
| D-01 剑网一 | 公告（绑定状态） | 是（公告与配置不一致） | 有（补发实物+全服补偿） | A |
| D-02 三国群英传2 | 公告（概率数值） | 是 | 有（**实际数值被永久改成错的**） | A |
| D-03 武林同萌傳 | 公告（奖项名称/数量） | 是（系统正常，仅公告错） | 有（统一补偿） | A |
| D-04 龙图智库 | 公告（金额数字） | 是 | 有（补发+开放退款） | A |
| D-05 全民小镇 | 公告（五档位数量） | 是（批量改动） | 有（补发差额） | A |
| D-06 云顶之弈 | 配置本身 | **否**（配置填错） | 有（下架+回收+补偿） | A |
| D-07 鬼怪世界 | 公告文本 | 是 | 有（道歉+改描述） | B |

**V-02 判定：已验证（限定范围）。**

判真条件要求「一次具体事故：什么漏了、谁发现、怎么处置」。D-01～D-05 五例三要素齐全，均为厂商自认公告，逐案已回源核对正文（D-07 为第三方整理稿，已降 B 级）。

**允许写的原话（照抄，不加修饰）：**

> 公开案例已证明：游戏内容或配置与对外信息不一致的情况实际发生过，并产生了补偿、退款或修正等后果。

**不许扩写成下面任何一句：**

- ❌「已证明策划日常维护依赖关系时经常出错」——七例没有一例是「策划改配置表后下游策划内容没跟」。
- ❌「已证明这类问题高频」——公开公告只覆盖被玩家发现、且需要补偿的那部分（生存者偏差），证明的是**下限**，不是发生率。
- ❌「已证明现有工具缺失」——公告从不披露内部工具形态，连"有没有校验"都看不到。

**组合：C → A，但必须注明 A 验证的是哪一层。**

| 层 | 内容 | 当前证据 | 能不能说 |
|---|---|---|---|
| 问题层 | 不一致会发生，且有代价 | D-01～D-05（公开公告，A 级） | ✅ 「问题真实存在且有成本」 |
| 岗位层 | 策划改配置后，下游内容没跟 | 访谈 04（1 人、口述） | ⚠️ 只能说「一位活动策划的实际做法」 |
| 方案层 | 本原型能解决这类问题 | **无** | ❌ 不能说。事故载体在边界外（见下第 3 折） |

**V-03 不因 V-02 判真而成立。** 两条问的不是一件事：V-02 问「会不会漏、漏了有没有代价」，V-03 问「现在靠什么维持、这一步要不要持续投入人」。V-03 的证据仍只有一处——访谈 04 描述的「配置表 + 需求文档 + 历史版本逐项核对」，单样本口述，位置不变。

**但必须同时打三个折（缺一个就是吹）：**

1. **岗位不同。** 这七例全部发生在**运营/公告**环节，没有一例是「策划改配置表后下游策划内容没跟」。机制相同（同一事实写两遍），岗位不同。写报告时要说「同类机制在运营侧已多次发生」，不能说「策划岗普遍如此」。
2. **生存者偏差。** 只有被玩家发现、且需要补偿的才会公开。没被发现的那种漏，不会出现在官网。所以这批材料证明的**是下限**，不是发生率。
3. **★最要命的一条：事故载体几乎全是"公告里手写的数字和描述"——而原型明确声明查不出这一类。**
   D-01～D-05 的错都长在文案里，不是长在配置表的字段引用上。原型的显式依赖检查，对这批事故**基本无效**。
   换句话说：**真实事故最密集的地方，正好落在原型画的边界外面。**

**处理决定（2026-11-10，曦定）：选乙，v0.1 冻结。**

- **乙 · 守边界（已采纳，即刻生效）**
  v0.1 冻结，不再扩功能。产品边界写死为：**配置表内部、已登记引用的下游对象**。对外文案 / 公告的数值一致性，明确列为**另一个问题**，不属于 v0.1 能力。D 批证据只用于「问题背景」，不用于「证明原型有效」。

- **甲 · 进候选池（不现在做）**
  未来研究「配置数据能否直接生成公告 / 邮件 / 对外内容」。★这会从「识别已登记依赖」跨到「内容生成与发布」，涉及新的工作流和能力边界——**不能为了迎合这批事故案例塞进 v0.1**。
  触发条件：拿到「公告是模板套字段、还是每次手写」的答案，或有第二个样本愿意给脱敏模板。在此之前只记录，不动手。

- **丙 · 搁置**
  那个唯一要问的问题（公告是模板套字段还是每次手写）渠道已断，短期问不到。等新渠道出现再问，不为此单独找人。

## 两组证据怎么摆（不许互相顶替）

| 组 | 材料 | 用来证明 | **不能**用来证明 |
|---|---|---|---|
| **事故证据** | D-01～D-07 公开事故公告 | 问题存在、有代价、行业公开可见 | 原型有用 |
| **能力证据** | Q013 三态判定 / 任务结构检查报告 / 影响分析器 | 技术上能做到什么、边界在哪 | 有人需要它 |

两组合起来才是一句完整的话：

> **问题是真的（D 批）；我做的这一小块是能跑的（能力批）；但它只覆盖问题的一部分，剩下的部分我标出来了，没有假装解决。**

分开摆反而更可信——能说清「哪些问题当前方案能解决、哪些暂时不能」，比把七件事都说成自己的战绩强。写进报告和作品集时，两节的标题也要分开：一节叫「问题背景」，一节叫「技术能力与边界」，不要合成「验证结果」。
