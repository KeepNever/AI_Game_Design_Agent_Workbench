## 0. 决策摘要

**暂定首期场景为「游戏策划的配置与任务设计变更影响分析及质量检查」**，以显式依赖关系建模和变更影响识别为核心切入点，并冻结 MVP 的 Must / Should / Could / Not 范围。

**决策性质声明（最重要的一段，先读这个）：**

> 本次决策是在 S2 访谈无法继续收敛（渠道断裂）的情况下，基于现有证据做出的**有明确限制的例外降级决策**。它**不认定场景已经充分验证**，也**不代表市场需求已经验证**。它低于 v2.0 原文预设的证据强度（原文要求 S2 收敛后再冻结场景），是一种在受限条件下的推进策略：宁可带着标注前进，也不无限期停滞。本决策可被推翻，推翻条件见第 7 节。

## 1. 首期场景定义

| 项 | 内容 |
|---|---|
| 场景名称（暂定） | 游戏策划的配置与任务设计变更影响分析及质量检查 |
| 核心切入点 | **显式依赖关系建模 + 变更影响识别** |
| 场景描述 | 策划修改一个配置或任务设计对象后，系统沿**已登记**的引用关系列出受影响下游对象、执行确定性规则检查、给出任务可达性三态判定与结构检查，人工逐项确认同步后导出可交接的变更确认单 |
| 首期品类 | 放置类活动配置（已建 Schema/RulePack）+ 任务图结构（雾隐镇 GT）；**小游戏/休闲游戏为优先市场研究方向，但产品定位保持多品类工作台，不缩小为小游戏工具** |
| 明确不做 | 公告文案数值检查与生成（候选池，触发条件见 `二手证据卡.md` 附录 D 末尾）；隐式依赖自动发现；LLM 替代确定性检查逻辑 |

## 2. 证据登记（三类分开呈现，不得互相顶替）

| 证据类型 | 内容 | 能证明什么 | **不能证明什么** |
|---|---|---|---|
| **① 公开事故公告（7 例）** | 剑网一、三国群英传2、武林同萌傳、龙图智库、全民小镇、云顶之弈（对照）、鬼怪世界（`02_业务访谈/二手证据卡.md` 附录 D，D-01～D-07，带链接） | 游戏内容、配置与对外信息不一致的情况**实际发生过**，并产生了补偿、退款、修正等实际后果（问题层） | 不能证明策划普遍依赖记忆维护依赖关系；**不能证明本产品能解决这些事故**——七例的错大多长在公告文案的手写数字上，本版边界查不出 |
| **② S2 访谈（5 份）** | 游戏行业 3 份（叙事关卡 / 放置活动 / 米哈游剧情）+ 工业对照 2 份 | 策划工作中存在关联关系与变更影响线索：H-01b（质量可判定）、H-02（重复维护）、H-03a（设定冲突存在）已验证；受访者 A 口述下游核对做法 | 样本小（岗位层仅 1 人有效且带锚定污染）；H-01a（高频）未验证且"无固定周期"的口述反而削弱它；渠道断裂后无法继续收敛 |
| **③ 原型与产品实测** | 157 个测试、脏表压测、PokeAPI 真数据 1260 行、变异评测检出率 4/5（漏报如实报告）、曦实测抓出状态错位 bug 当晚修复 | **技术可行性**与具体使用反馈（方案层的"能做"部分） | 不能证明市场需求；变异评测的对象是检查器本身，不是真实用户价值 |

**使用纪律**：① 只进"问题存在"论证；② 只进"工作流关联"论证；③ 只进"方案可行"论证。任何汇报、作品集、简历不得将三者合并表述为"需求已验证"。

## 4. MVP 范围（Must / Should / Could / Not + 验收标准）

### 4.1 Must（首期闭环缺一不可；任何一项缺失，第一阶段不算完成）

| # | 内容 | 验收标准 | 现状 |
|---|---|---|---|
| MU-1 | **首期场景完整闭环可运行**：Brief（结构化输入）→ 生成/载入设计对象（配置+任务图）→ 检查 → 诊断 → 人工审核 → 导出 | 一个具体场景从输入到导出全程点得通，中途不需要离开工具 | 部分达成（检查→诊断→勾选→导出已有；Brief 输入与生成缺失） |
| MU-2 | **M1 数据骨架**：通用对象模型 + 首期品类 Schema + RulePack 元数据 | 样例可保存 / 读取 / 校验；校验错误一次性列全 | ✅ 基本达成（`gdw/model.py` + `loader.py`，含结构校验），正式验收时跑一遍并记录 |
| MU-3 | **M5 确定性检查与影响分析** | ① 注入异常能稳定命中规则（变异评测记录在案：强检出 3 / 仅提示 1 / 漏报 1，漏报原因写明）；② **变更影响结果与人工 GT 对照一致**（人工 GT 未建，见 6.2）；③ 不用 LLM 替代确定性逻辑 | 大部达成；② 的人工对照是缺口 |
| MU-4 | **M2 Prompt 基线**：Brief 直接生成首期设计对象 | 有基线输出和错误记录；生成产物符合 Schema 且能被 MU-3 的检查器校验；token 与金额逐轮记录 | ❌ 未做。**检查与生成协同建设**（曦已纠正过"先检查后生成不是架构原则"），生成是闭环的必要一环，不得因 M5 已强而继续推迟 |
| MU-5 | **M0 工作台壳与关键点击路径**：首页 / 项目资料 / Brief / 工作流视图（固定展示）/ 设计编辑 / 检查 / 导出 | 关键点击路径完整；无真实模型调用时可用模拟数据走全流程（v2.0 M0 验收原文） | ❌ 未做（现有 09 工作台是 M5 段的操作界面，不是完整 IA 的壳） |
| MU-6 | **M7 最小版**：诊断呈现 + 采纳/修改/忽略留痕 + 版本差异 + 导出 | 用户修改不会被覆盖；审核状态跨会话恢复；导出包含勾选状态 | 雏形达成（勾选落盘、CLI diff、三种导出），缺"采纳/忽略"的区分留痕 |
| MU-7 | **评测最小版**：固定测试集 + GT + 可重复记录 | 同一输入两次运行结果一致；漏报 / 误报如实记录，不美化 | 雏形达成（变异评测）；结果已可复现 |

### 4.2 Should（首期内尽量做；不做不阻塞闭环验收）

| # | 内容 | 验收标准 |
|---|---|---|
| SH-1 | M3 项目检索（项目规则 / 资料 / 历史设计，SQLite + FTS5） | 输出能引用来源 |
| SH-2 | M4 结构化生成（先规划 → 人工确认 → 再生成细节） | 产物符合 Schema 且可编辑；确认点真实存在 |
| SH-3 | M6 语义审查（LLM 对照项目资料查内容冲突） | 问题有位置、证据和说明；不自动裁决主观体验 |
| SH-4 | M7 完整版（多版本管理增强；不做复杂多级审批） | — |
| SH-5 | H0 对照实验（人工基线 vs AI 组，S7 完整版） | 记录问题首次发现阶段 / 返工次数 / 质量评分三类数据（v2.0 §866） |
| SH-6 | 工作流画布受控配置（按 §8.4"后续版本"档：可配置参数、启停步骤；**不做自由节点编辑**） | 用户能看懂流程、能运行、能配置 |

### 4.3 Could（有时间再做，不承诺）

- M9 第二品类轻量验证（S8，验证通用层可复用，不做第二品类完整开发）
- 3–5 分钟演示视频、安装打包打磨
- 工作流画布自由编排（仅在用户研究证明其价值后，长期版本档）

### 4.4 Not in MVP（明确不做，防止范围蔓延）

- 完整游戏引擎、UE/Unity/Godot 引擎插件、实时 NPC 运行时
- 美术 / 3D / 动画 / 音频生产平台
- 多人实时协作、企业级权限、多租户管理
- 自动生成并发布成熟商业游戏；广告投放与发行运营
- 自由节点编辑器、节点市场、多 Agent 协作画布（首发）
- 用 LLM 替代确定性检查逻辑；未经证据支持的自动影响推断
- 公告文案数值的生成与检查（甲候选池，未触发）

## 5. M0–M9 首期优先级评估（对应要求 4）

> 原则：结合完整工作台愿景排优先级，**不围绕现有 M5 继续扩展**。生成（M2）与壳（M0）优先级高于 M5 的任何加深。

| 迭代 | 内容 | 首期优先级 | 排序理由 | 现状 |
|---|---|---|---|---|
| M0 | 工作台壳、关键点击路径、固定工作流视图 | **Must，进入开发后第一优先** | 没有壳，MU-1 闭环无处安放；也补 24.3 第 7 项的 IA 缺口 | 未做 |
| M1 | 数据骨架 | Must（先行） | 一切的地基 | ✅ 基本达成 |
| M2 | Prompt 生成基线 | **Must，与 M5 同级** | 闭环必需；也是"生成-检查协同"的另一半；有基线才能评检查器的真实价值 | ❌ 未做 |
| M3 | 项目检索 | Should | 提升生成与检查的上下文质量，但不阻塞闭环 | 未做 |
| M4 | 结构化生成（规划→确认→生成） | Should | 在 M2 基线验证后升级 | 未做 |
| M5 | 确定性检查与影响分析 | Must | 已验证的差异化候选 | **大部完成**；余项 = 影响面人工 GT 对照 |
| M6 | 语义审查 | Should | 依赖 LLM 与 API 预算（17.8）；在 M2 立起来之后才有对照意义 | 未做 |
| M7 | 诊断、审核、版本 | Must（最小版） | 闭环的"人工审核与交付"环节 | 雏形 |
| M8 | 整体回归评测 | Must（最小版） | 可复现是验收底线 | 变异评测雏形 |
| M9 | 第二品类轻量验证 | Could | 验证多品类架构边界，不挤占首期闭环 | 未做 |

**推进顺序建议**：补齐 S4 前置条件（见 6.2）→ M0 壳 + IA → M2 生成基线 → MU-1 闭环打通 → M7 最小版补全 → M8 回归收口 → 之后按 Should 逐个上。

## 7. 重新开启 S4 的条件（对应要求 6）

以下任一条件触发，即重开 S4（回到场景与范围决策），**不视为项目失败**（v2.0 §22.2：触发暂停应回 S4 调整，而不是继续扩大投入）：

| # | 触发条件 | 说明 |
|---|---|---|
| R1 | 获得新的有效用户证据 | 新访谈、真实脱敏工作样例、或多位受访者口述指向不同场景，或否定本场景前提 |
| R2 | 原型试用否定核心假设 | 真实策划试用后表示：不靠记忆维护依赖 / 现有工具已覆盖 / 对确认单无真实需求 |
| R3 | 品类工作流重大差异 | 小游戏/休闲游戏的实际设计流程与首期场景假设不符（如变更影响不是其真实痛点） |
| R4 | S2 渠道恢复并完成补充收敛 | 新访谈结论需要修订场景或 MVP 范围时 |
| R5 | M2 生成基线数据改变价值重心 | 如生成质量是主要瓶颈（错误率远超预期），重心应移向生成侧而非检查侧 |
| R6 | 评测或真表验证暴露场景假设错误 | 真实配置表结构使显式依赖建模不成立，或变异评测边界与真实错误形态严重脱节 |
